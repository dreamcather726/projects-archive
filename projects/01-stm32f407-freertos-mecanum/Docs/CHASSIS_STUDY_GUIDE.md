## 1. 先理解这个项目是什么

这是一个“接收运动意图、控制四轮驱动器、采集IMU、监督设备与主控健康”的下位机，不是完整自动驾驶系统。

当前系统分成三部分：

- 电脑上位机：提供人工调试界面，编码运动命令，显示IMU与安全状态。
- STM32下位机：解析命令、检查权限、分解四轮速度、推进电机事务、执行安全保护。
- 外部设备：JY61P提供惯性数据；Emm_V5驱动器接收命令并控制电机。

主要连接关系：

~~~text
电脑调试程序
    │ 板载CH340 / USART1，115200
    ▼
STM32F407 + FreeRTOS
    ├── USART3，9600 ─── JY61P IMU
    ├── USART6，115200 ─ Emm_V5四电机总线
    └── USART2，115200 ─ 视觉接口预留，当前没有视觉业务
~~~

你操作“底盘前进”时，STM32不是直接输出四路电机PWM，而是给Emm_V5发送串口控制帧。电机驱动器内部的闭环，与STM32是否实现“整车运动闭环”是两回事。

当前STM32没有把Yaw误差送入PID来自动保持车头方向。IMU的主要用途是采集、显示、静止Yaw修正，以及作为在线健康检查的一部分。

## 2. 完整功能与实现边界

### 2.1 当前可以通过主控协议使用的功能

| 功能类别 | 已实现功能 | 关键边界 |
|---|---|---|
| 底盘运动 | 前后、横移、旋转、组合运动、四轮等比例限幅 | 输入是归一化分量，不是m/s和rad/s |
| 四轮同步 | 逐轮下发同步暂存命令，收到四轮正确应答后广播触发 | 不是测量四轮实际启动时刻的同步闭环 |
| 单电机 | 使能、失能、速度、相对/绝对位置、立即停止、同步暂存/触发 | 普通ACK成功仅表示接受/入队 |
| 原点操作 | 当前位置清零、模式0～3回零 | 回零参数及机械限位须先在驱动器侧确认 |
| 参数查询 | 版本、电压、电流、速度、位置、位置误差、FLAG、系统状态、回零状态 | 返回的电机数据经E2原样转发，界面不是所有字段的完整解析仪表 |
| IMU | 加速度、角速度、Roll/Pitch/Yaw、温度、版本、校验统计、完整样本发布 | 不提供绝对航向保证，也不是连续无损数据记录器 |
| 自检 | 启动/显式重新自检，四电机FLAG检测和新鲜完整IMU检测 | 在线不等于使能，更不等于机械安装与闭环性能合格 |
| 运行监督 | 电机FLAG巡检、IMU完整样本新鲜度、主控链路和运动授权监督 | 电机巡检不是每2ms检查四个电机 |
| 停车保护 | 普通全车STOP、急停锁定、通信/授权超时停车、事务失败停车、待停车重试 | 总线断线或驱动器异常时，软件广播不保证送达 |
| 系统保护 | 独立看门狗、任务存活监督、栈溢出/断言故障入口 | 看门狗复位不是独立硬件急停 |
| PC调试 | 串口连接、自检显示、手动控制、日志、鲜红色全部急停、显式持续授权 | 人工测试工具，不是自主导航主控 |

### 2.2 电机库有接口，不代表当前上位机已经开放

[Emm_V5.h](../Libraries/StepperMotor/Inc/Emm_V5.h)还声明了解除堵转保护、修改驱动控制模式、设置回零原点、修改回零参数、打断回零等接口。库枚举还包含相电阻/电感、PID、编码器、目标位置、驱动配置等查询项。

当前主控协议及GUI只开放上一表列出的子集。例如READ只接受9种查询项；不能把库枚举任意数值填进READ，就认为固件一定支持。

这样的限制有意义：修改驱动模式、回零参数或解除保护，可能改变安全条件，不应作为普通调试动作无条件开放。

## 3. 硬件接口与四轮编号

### 3.1 串口与DMA

| 用途 | 外设 | STM32 TX / RX | 波特率 | RX DMA |
|---|---|---|---:|---|
| 主控/板载CH340 | USART1 | PA9 / PA10 | 115200 | DMA2 Stream2 Channel4 |
| 视觉预留 | USART2 | PA2 / PA3 | 115200 | DMA1 Stream5 Channel4 |
| JY61P | USART3 | PB10 / PB11 | 9600 | DMA1 Stream1 Channel4 |
| Emm_V5 | USART6 | PG14 / PG9 | 115200 | DMA2 Stream1 Channel5 |

统一为8个数据位、1个停止位、无校验、无硬件流控，即8N1。当前BSP统一初始化四路串口；功能开关主要决定对应应用逻辑与任务是否编译运行。

外接UART要按实际设备要求交叉连接TX/RX并共地，确认电平、供电和驱动器总线接法。不要把动力电源接到串口引脚，也不要让CH340和另一个主控同时驱动USART1。

### 3.2 四轮地址、正方向和掩码

站在车体上方看，车头朝前：

~~~text
                  车头 / X正向
                       ↑
          左前LF(2)          右前RF(1)

          左后LR(3)          右后RR(4)
          ← Y正向；绕Z逆时针为正
~~~

| 轮子 | 默认地址 | 前进时Emm方向位 | 在线掩码位 |
|---|---:|---:|---|
| 左前LF | 2 | 0 | bit0 |
| 右前RF | 1 | 1 | bit1 |
| 左后LR | 3 | 0 | bit2 |
| 右后RR | 4 | 1 | bit3 |

地址0保留作广播，不能分配给某一轮。四轮全在线的掩码是0x0F。

注意“数组顺序”和“地址大小顺序”不同：代码按左前、右前、左后、右后排列，对应2、1、3、4。不能把bit0理解成1号电机。

左右方向位不同是默认镜像安装假设，必须架空实测。修改四轮地址/方向在[app_config.h](../Config/Inc/app_config.h)；改地址后，PC的固定显示映射也要同步调整。

### 3.3 时钟不要按芯片最高频率想当然

当前SystemInit主要处理FPU与向量表，工程没有在应用初始化中配置168MHz PLL。SystemCoreClock初值为16MHz，main调用SystemCoreClockUpdate读取实际时钟寄存器。

按正常硬复位、没有其他启动程序改时钟的情况理解，当前使用默认HSI时钟。分析性能时应检查实际寄存器和SystemCoreClock，而不是把“F407可以运行到168MHz”等同于“这个工程已经运行在168MHz”。

### 4.3 依赖方向

~~~text
main → App/AppTasks
          ├── HostProtocol → Mecanum → Emm_V5 → BSP_UART
          ├── HostProtocol ─────────→ Emm_V5 → BSP_UART
          ├── App/Data → IMU ─────────────────→ BSP_UART
          └── AppTasks → BSP_Watchdog

底层：BSP_UART → STM32标准外设库 / CMSIS

~~~

上层描述“要做什么”，底层描述“怎样操作硬件”。Emm_V5主要编码设备命令，Mecanum决定四轮事务，HostProtocol决定当前请求是否允许执行。

不要把主控命令解析写进USART中断，也不要把业务逻辑改进FreeRTOS内核文件。

## 5. 从上电到允许运动

### 5.1 启动流程

~~~text
复位 → 启动文件/SystemInit → C运行环境 → main
    → SystemCoreClockUpdate + NVIC优先级分组
    → App_Init
        → BSP_Init：初始化四路串口、DMA与中断
        → HostProtocol_Init：初始化状态，先请求全车STOP，启动自检状态
        → IMU_Init：上电等待、配置IMU、清旧RX数据
        → 上报READY，应用状态设为READY
    → AppTasks_StartScheduler
        → 静态创建已启用任务
        → 启动IWDG
        → FreeRTOS调度器运行
    → Control逐周期推进四电机/IMU自检
    → 自检通过后才允许使能/运动
~~~

### 5.2 两种READY不是一回事

App的READY表示应用初始化完成，E0 READY也只是初始化事件。真正的运动许可由HostProtocol的自检状态、急停锁、底盘故障锁和待停车状态共同决定。

因此看见READY，仍可能收到运动ACK=07。

### 5.3 初始化不是完全无延时

正常运行时，主控/电机事务采用非阻塞状态机。但IMU上电配置发生在调度器启动前，使用DWT延时：

- 上电等待500ms。
- 每个受保护寄存器：解锁后等200ms，写入后等200ms。
- 配置三个寄存器，合计延时约1700ms，再加少量执行/传输开销。

自检5秒总期限从Control首次推进时开始，不把调度器启动前这段IMU配置等待算进去。

IWDG是在创建任务后、启动调度器前开启，不覆盖更早的整个上电初始化阶段。不能把“工程启用了看门狗”理解为每个初始化步骤都已被看门狗监督。

## 6. FreeRTOS任务与运行时序

### 6.1 当前任务

| 任务 | 默认周期 | 优先级 | 默认栈 | 核心工作 |
|---|---:|---:|---:|---|
| Control | 2ms | Idle+3 | 384 words = 1536B | 主控、电机、安全与底盘事务 |
| IMU/Data | 2ms | Idle+2 | 384 words = 1536B | IMU解析与数据上报 |
| Watchdog | 250ms | Idle+4 | 128 words = 512B | 检查任务存活，决定是否喂狗 |
| Idle | 无业务周期 | 0 | 128 words = 512B | 空闲调度，由应用提供静态内存 |

节拍1kHz，即1 tick=1ms。任务数值越大优先级越高；NVIC中断则数值越小优先级越高，两套规则不要混淆。

当前USART中断优先级为8，DMA中断为9。FreeRTOS可调用内核API的中断优先级边界配置为5；当前串口中断主要处理硬件和缓冲状态，不直接执行复杂业务。

### 6.2 一个Control周期做什么

App_ProcessControl先执行HostProtocol_Process，再执行Mecanum_Process。

协议处理顺序为：刷新待发上报→读取电机回复→安全/自检/巡检→主控输入→待停车重试。之后App才调用Mecanum_Process推进事务。先处理电机回复，底盘状态机才能确认上一轮并推进下一轮。

每个合法主控帧刷新链路时间前还会检查授权/链路是否已经过期，避免一个很长的输入批次把过期事实覆盖掉。

### 6.3 一个Data周期做什么

IMU_Process从DMA区取出已经到达的字节；收齐51/52/53后发布完整快照。App用IMU_TryRead取新样本，格式化成ASCII，再装入E1二进制事件上报。

2ms表示任务多久检查一次，不表示传感器每2ms产生一组数据。

### 6.4 为什么用DelayUntil

vTaskDelayUntil依据上次计划唤醒时刻安排下一周期，避免“执行耗时+固定睡眠”逐圈累积漂移。但周期仍受抢占、临界区和实际执行时间影响，不能视为硬实时零抖动承诺。

### 6.5 静态分配和看门狗

任务TCB、任务栈与Idle内存由静态对象提供，FreeRTOS动态分配关闭。这个结论针对STM32，不是说Python上位机不使用动态内存。

Control/Data正常完成一次处理后设置各自存活位。Watchdog每250ms取出并清零存活掩码，只有所有已启用任务都在窗口内运行过才刷新IWDG。

某任务卡死后不能由另一个“永远喂狗”的任务掩盖。标称复位期限为2秒，受LSI误差影响；调试暂停时配置为冻结IWDG，调试器暂停试验不能等同于脱离调试器的真实故障试验。

## 7. 麦克纳姆运动分解

### 7.1 输入的意义

CHASSIS输入：

- forward：-1000～1000，正为前进。
- left：-1000～1000，正为向左。
- ccw：-1000～1000，正为逆时针。
- max_rpm：0～100，允许的轮子最大RPM。
- acceleration：0～255，传给Emm_V5的加速度参数，不是SI单位的m/s²。

这是一套归一化控制量。代码中没有轮半径、轴距、轮距或减速比，所以不能直接把forward=500解释为0.5m/s。

### 7.2 当前X型公式

设前进分量为F，左移为L，逆时针为C：

~~~text
raw_LF = F - L - C
raw_RF = F + L + C
raw_LR = F + L - C
raw_RR = F - L + C

D = max(1000, |raw_LF|, |raw_RF|, |raw_LR|, |raw_RR|)

wheel_rpm = raw_wheel × max_rpm / D
~~~

实际代码按幅值做整数四舍五入，再恢复符号。四轮共用D，因此不会分别截断某一轮后破坏原来的组合比例；但整数RPM量化仍有舍入误差。

### 7.3 算几个实际例子

以下顺序始终为左前、右前、左后、右后，max_rpm=40：

| F,L,C | 四轮RPM | 对应动作 |
|---|---|---|
| 1000,0,0 | +40,+40,+40,+40 | 前进 |
| -1000,0,0 | -40,-40,-40,-40 | 后退 |
| 0,1000,0 | -40,+40,+40,-40 | 左移 |
| 0,0,1000 | -40,+40,-40,+40 | 逆时针 |
| 500,0,0 | +20,+20,+20,+20 | 半幅前进 |
| 1000,1000,0 | 0,+40,+40,0 | 前进与左移，D=2000 |
| 600,200,100 | +12,+36,+28,+20 | 平移与旋转组合，D=1000 |

轮子正RPM表示“向车体前进方向滚动”，不是一律对应驱动器方向位0。

方向转换：RPM>=0使用该轮配置的前进方向位；RPM<0则把方向位异或1，幅值取绝对值。

### 7.4 哪些条件会导致实际动作不符合公式

公式假定当前X型轮组、轮子安装和四轮方向正确。滚子安装不符、车轮打滑、负载差异、地面摩擦和驱动参数不一致，都会影响实际轨迹。

当前固件没有依据实际车体速度反馈修正这些误差。应先逐轮验证方向，再测试前进、横移、旋转，最后测试组合动作。

## 8. 四轮同步控制状态机

### 8.1 从按钮到驱动器的完整调用链

~~~text
PC：_drive_chassis
  → 参数检查 → _send_command → SerialWorker.send_frame
  → build_frame + PC发送FIFO → _write_loop → CH340/USART1

STM32：USART1 RX DMA
  → Control → HostProtocol_ProcessHostInput
  → 长度/DEST/CRC校验 → HostProtocol_ExecuteFrame
  → 自检/锁定/模式/忙状态门禁
  → Mecanum_Drive：计算并保存四轮目标，建立事务
  → 返回CHASSIS ACK；此时不保证四轮已收到命令

后续Control周期：Mecanum_Process
  → Emm_V5编码 → BSP_UART整帧入队 → USART6 TXE发送
  → USART6 RX DMA → 电机解析器 → HandleMotorResponse
  → 下一轮 → 四轮通过 → 广播SYNC → E4结果事件
~~~

### 8.2 为什么不一次塞入四条速度命令

当前按2、1、3、4顺序逐台确认。这样能明确哪台电机没应答，避免四条命令拥挤在总线上而难以识别问题。

每台轮子的命令使用同步暂存标志，四台正确应答后才广播同步触发。目标为0的轮子发送同步STOP，而非普通0 RPM速度帧。

### 8.3 发送完成和回复超时

~~~text
整帧入队
  → 等软件TX队列为空且硬件TC完成
  → 开始10ms回复等待
  → 地址/功能码/长度正确，电机状态0x02：推进下一轮
  → 超时或00 EE无效命令应答：原轮重试一次
  → 再失败或明确错误状态：全车STOP + 故障锁定
~~~

TXE只表示发送数据寄存器可继续写；TC才表示最后字节已经发送完成。不能把“入队成功”作为开始等待电机回复的时刻。

整个事务还受200ms总期限限制，包含排队、TX等待、回复与重试。该期限不是电机转完某个位置目标的期限。

### 8.4 Busy、Cancel与结果

- Mecanum_IsBusy表示四轮命令事务还在推进，不表示车轮物理上还在运动。
- Mecanum_Cancel只取消软件事务，不发送STOP、不清UART待发动作、不清故障锁。
- Mecanum_FailStop才负责事务失败后的广播停车和故障锁。
- 控制模式可能在事务结束后仍保持CHASSIS，切换单电机模式前仍应全车STOP。

E4的DATA有3字节：原CHASSIS请求SEQ、结果、故障地址。E4帧头中的事件SEQ不是原请求SEQ。

result=2表示四轮应答通过、同步触发已经入队；result=3表示失败并请求停车；result=4表示取消。成功不是实际速度、到位或停车确认。

## 9. 单电机功能如何使用

### 9.1 使能与失能

EN包含地址、enable和sync。enable取0/1，当前固件要求sync=0，即使能必须立即执行。

自检通过也可能所有电机仍未使能。测试底盘前要使能全部目标轮子，可以按当前驱动器广播配置使用地址0，或逐台使能。

失能请求在STM32侧允许走安全路径：先全车停车，再发失能。PC本地急停门禁更严格，会阻止EN类发送，因此急停期间不能据此推断GUI还能发送失能；现场必须保留独立硬件手段。

### 9.2 速度控制

VEL参数为地址、方向、RPM、加速度、sync。RPM上限默认100。

sync=0立即执行；sync=1暂存等待同步触发。非零速度被接受时进入单电机控制模式并建立运动授权。

单电机速度命令的主控ACK不是Mecanum那种逐轮确认事务；电机原始回复由E2转发，运行健康由巡检监督。

### 9.3 相对与绝对位置

POS在速度参数外，包含32位脉冲数、absolute和sync。

- absolute=0：相对位置动作，重复执行可能多走一次。
- absolute=1：绝对位置动作，目标0也可能引起运动，仍受授权保护。
- 脉冲数与机械位移关系取决于驱动细分、传动与机构；当前STM32不把它转换为米。

动作长于500ms时也需要续租。不能为了保活不断重发相对位置命令。

### 9.4 单电机同步动作

先给一个或多个目标发送sync=1的运动命令，再发送SYNC。固件跟踪暂存轮掩码，SYNC必须对应当前单电机模式中确实暂存过的目标。

同步暂存本身也可能建立授权，拖太久再触发会过期。SYNC被成功接受后，当前授权SEQ会更新为这次SYNC的SEQ，续租须使用新的SEQ。

### 9.5 STOP、ZERO与HOME

STOP包含地址和sync。地址0、sync=0是普通全车停止，解除授权并退出模式，但不清已有故障锁。

协议保留单电机STOP；底盘模式下STOP会按全车停车处理。单电机模式中的局部STOP不等于完整退出控制模式，切换模式应使用全车STOP。

PC“停止当前”和底盘停止都使用全车STOP；底盘零向量或最大速度0同样转换为STOP。普通停止不必像急停那样重新自检，前提是没有其他故障锁定。

ZERO只是把驱动器当前坐标清零，不是让车轮转回零点；自检、运动授权、底盘事务或巡检忙时可能返回忙。

HOME启动驱动器回零，模式允许0～3。当前代码不在GUI中建立新的回零参数配置功能，具体模式适用性需结合驱动器设置和机械限位。

### 9.6 READ查询项

| PC名称 | item十六进制 | 内容 |
|---|---|---|
| VER | 00 | 软硬件版本 |
| VBUS | 03 | 总线电压 |
| CURRENT | 05 | 相电流 |
| SPEED | 09 | 实际转速 |
| POSITION | 0A | 实际位置 |
| PERR | 0B | 位置误差 |
| FLAG | 0D | 使能/到位/堵转等标志 |
| STATE | 0F | 系统状态 |
| ORG | 10 | 回零状态 |

PC不允许用广播地址READ。自检、底盘发送或运行巡检等待回复时，READ可能返回05，不会为了查询而取消底盘事务。

## 10. IMU采集配置与Yaw修正

### 10.1 数据是否要发送查询命令获取

正常采集不需要每次发送“读取姿态”命令。JY61P按自身配置主动上传，STM32通过USART3接收。

IMU_Init会发送配置命令，不是每组数据的查询命令。代码当前配置：

| 作用 | 命令HEX | 说明 |
|---|---|---|
| 解锁 | FF AA 69 88 B5 | 每次受保护寄存器写入前执行 |
| 开启陀螺自动校准 | FF AA 63 00 00 | 不执行Yaw归零 |
| 加速度滤波值300 | FF AA 2A 2C 01 | 16位参数低字节在前 |
| 开启三类输出 | FF AA 02 0E 00 | 加速度、角速度、姿态 |

当前不发送修改波特率、修改输出频率、保存或Yaw归零命令；设备须预先与STM32的9600配置一致。以上解释对应当前实现，不替代你实际模块型号/固件的设备说明。

### 10.2 11字节帧和单位转换

~~~text
55 | 类型 | 8字节数据 | 校验和
~~~

51为加速度/温度；52为角速度；53为Roll/Pitch/Yaw/版本。原始16位数据低字节在前，按有符号数解释。

当前代码换算：

~~~text
加速度[g] = raw / 32768 × 16
角速度[deg/s] = raw / 32768 × 2000
角度[deg] = raw / 32768 × 180
温度[℃] = raw_temperature / 100
~~~

IMU帧用前10字节累加后取低8位作为校验，不是主控协议的CRC16。失败时计数并滑动寻找下一个55。

### 10.3 单帧与完整样本不同

51、52、53分别更新工作样本与更新掩码。三类都至少更新过一次后，复制到发布样本，计一次完整样本，供应用读取。

- VALID：校验通过的单帧累计数。
- IMU_GetSampleCount：完整样本累计数，供安全新鲜度判断。
- IMU_Read：可反复读取最近完整值。
- IMU_TryRead：每次有新快照才返回true并清新数据标志。

完整样本表示字段已经收齐，不表示三帧有共同的硬件采样时间戳。没有新快照时不能用历史非零VALID证明IMU当前仍在线。

### 10.4 为什么刷新速度不会达到500Hz

8N1每字节约占10个线路位。三帧一组共33字节，9600波特率下，仅串行传输就约需：

~~~text
33 × 10 / 9600 = 0.034375秒
理论完整组上限约29组/秒
~~~

这个上限只是假设连续输出三类帧、无额外间隔和其他数据的线路预算，不是传感器当前实际输出频率。实际还受模块输出设置、滤波、任务处理与GUI快照刷新影响。

只把Data任务从2ms改成1ms，不能突破9600线路带宽。后续提速需一起核对设备输出频率、设备/STM32波特率匹配、DMA容量和上报负载，当前工程没有实现自动波特率切换。

### 10.5 静止Yaw修正

连续20组完整样本满足下面条件，STM32进入静止Yaw锁定：

- 三轴角速度分别在±2.5°/s内。
- 合加速度在0.90g～1.10g内，代码比较平方量避免开方。

锁定时保存输出Yaw，反向吸收原始Yaw缓慢漂移；检测到运动即解锁，保留修正量并对角度作边界处理。

20组是样本数，不是20ms。该规则可能把足够慢的匀速旋转判为静止；YAW_LOCK=1不是“绝对航向测量正确”或“车头控制已锁定”。

### 10.6 上报格式

应用将完整样本格式化为三位小数文本：

~~~text
ACC[g]=0.000,0.000,1.000;GYRO[dps]=0.000,0.000,0.000;YPR[deg]=0.000,0.000,0.000;TEMP[C]=25.000;VER=18455
~~~

注意原始53中为Roll/Pitch/Yaw，而上报文本为Yaw/Pitch/Roll。此文本在E1的DATA内，外层仍是5A二进制协议，不能把整条USART1链路视为纯文本串口。

## 11. 主控通信协议与状态字段

### 11.1 帧结构

~~~text
5A | LEN | DEST | SEQ | INDEX | DATA | CRC_L | CRC_H
~~~

- LEN为整帧字节数，7～255；DATA最多248字节。
- DEST：00上位机，01下位机，FF广播。
- SEQ是请求序号，应答原样返回；事件使用独立事件序号。
- INDEX区分命令、应答和事件；普通应答为请求INDEX或上0x80。
- DATA中多字节整数大端，CRC自身低字节先发。
- CRC16-Modbus初值FFFF，多项式A001，覆盖LEN到DATA，不包含5A。
- 协议没有帧尾。不要把电机的6B当成主控协议帧尾。

### 11.2 全部主控命令

| INDEX | 名称 | DATA字节数 | 内容 |
|---|---|---:|---|
| 01 | PING | 0 | 测试/维持链路 |
| 02 | STATUS | 0 | 状态与计数器 |
| 03 | SELF_TEST | 0 | 停车并重新检测 |
| 04 | RENEW | 1 | 原运动SEQ |

| 12 | POS | 11 | address:u8、direction:u8、rpm:u16、acceleration:u8、pulses:u32、absolute:u8、sync:u8 |

| 02 | CRC错误 |
| 03 | 不支持的命令 |
| 04 | 参数错误/超范围/续租SEQ不匹配 |
| 05 | 系统或发送队列忙 |

### 11.4 全部事件

| INDEX | 事件 | 内容 |
|---|---|---|
| E0 | READY | 初始化完成 |
| E1 | IMU_TEXT | ASCII完整样本 |
| E2 | MOTOR_REPLY | 电机完整原始回复 |

import struct
from PC_Tools.jy61p_motor_test import (
    build_frame, COMMAND_CHASSIS, COMMAND_RENEW, COMMAND_STOP,
)

# 低速前进：DATA为9字节；这里只打印，不控制硬件。
motion = build_frame(0x01, 0x23, COMMAND_CHASSIS,
                     struct.pack(">hhhHB", 1000, 0, 0, 20, 10))
# 请求SEQ与原动作SEQ是不同概念。
renew = build_frame(0x01, 0x24, COMMAND_RENEW, bytes((0x23,)))
stop = build_frame(0x01, 0x25, COMMAND_STOP, bytes((0, 0)))
print(motion.hex(" "))
print(renew.hex(" "))
print(stop.hex(" "))
~~~

导入PC模块仍需先安装pyserial/Tkinter。任何字段修改都要重新计算CRC；串口助手必须HEX发送且关闭自动换行。手动连续发送示例前还要满足自检、使能与授权条件。

## 12. 自检故障停车与运动授权

### 12.1 启动/重新自检

自检先请求全车停止，再清理旧电机回复、记录IMU完整样本计数基线，并进入RUNNING。

按2、1、3、4顺序发送只读FLAG查询。每台等待500ms，最多尝试2次；完整回复必须对应当前地址、功能3A和末尾6B。

没有回复的轮子不会被标记在线，检查仍可继续到其他轮子，但只有四轮全在线、IMU有新鲜完整样本、停车不再待入队，才能PASSED。总期限5秒。

FLAG存在不代表健康：当前代码把0xFC范围内的标志位视为异常，包括堵转/保护位及保留高位；运动目标电机的使能位为0也会触发故障。空闲电机未使能可以通过自检。

故障后必须显式SELF_TEST重新进入检测，通过才清急停/底盘故障锁；不会恢复历史运动。

### 12.2 运行巡检

运动布防时且底盘事务不忙，周期查询四电机FLAG。完成一轮四电机检查后再等待500ms，单台等待500ms、重试一次。

因此500ms不是“四个电机任何断线都保证500ms内检测出来”。实际受巡检相位、其他轮回复、重试和底盘事务占用影响。

巡检等待回复时新运动或READ可能返回05。匹配RENEW维持当前动作授权，但不会重置巡检进度。

自检通过后，即使当前空闲，IMU完整样本超过1秒未更新也会进入故障停车与锁定。编译关闭IMU时不检测IMU，状态用2说明该情况。

### 12.3 两个独立的500ms计时

| 计时 | 由什么刷新 | 什么不能替代 |
|---|---|---|
| 链路500ms | 目标正确、CRC有效的主控帧 | 不能证明主控控制任务仍健康 |
| 运动授权500ms | 新接受的运动动作或匹配原动作SEQ的RENEW | PING、STATUS、READ、普通使能不能续期 |

~~~text
发运动SEQ=23 → STM32建立授权23
    ├── 只发PING：链路正常，但授权到期仍停车锁定
    ├── RENEW(DATA=23)：未过期且状态允许时续期
    ├── RENEW(DATA=其他SEQ)：拒绝，不续期
    └── 已过期再RENEW：不能恢复旧动作
~~~

新的动作或SYNC接受后可能更新motion_seq。上位机必须跟随最新匹配成功ACK，不能永远续租第一次动作。

非零VEL、可能运动的POS、HOME、SYNC和非零CHASSIS建立授权。绝对位置目标0也会建立授权；同步暂存同样不能无限期等待。

### 12.4 停车与急停的区别

| 动作 | 撤销授权/退出模式 | 请求全车停车 | 新增急停锁 | 清已有故障 |
|---|---|---|---|---|
| STOP 0 0 | 是 | 是 | 否 | 否 |
| 合法零底盘请求 | 是 | 是 | 否 | 否 |
| ESTOP | 是 | 是 | 是 | 否 |
| 失联/授权过期/设备故障 | 是 | 是 | 不一定设急停位，但会故障锁定 | 否 |
| 重新自检开始 | 是 | 是 | 不立即清锁 | 否 |
| 重新自检通过 | 保持无旧动作 | 不重放旧运动 | 清急停锁 | 清相应运动故障锁 |

STOP不等于绕过故障。ESTOP会丢弃当时主控DMA区已缓存的后续请求，防止“急停+旧运动粘包”被接着执行。

停车暂时入队失败则保留请求继续尝试，不能只取消流程就认为停车完成。

### 12.5 故障原因编码

| safety_fault | 含义 |
|---:|---|
| 0 | 无 |
| 1 | 自检超时/设备缺失 |
| 2 | 电机通信/底盘事务故障 |
| 3 | IMU完整样本停更 |
| 4 | 急停 |
| 5 | 运动授权过期 |
| 6 | 主控链路失联 |
| 7 | 电机FLAG异常/运动目标失能 |

### 12.6 有限动作去重

POS、HOME、SYNC最近8条成功接受的请求，在2秒内按SEQ、INDEX、DATA去重：

- 相同请求：仅重新ACK，不再执行，也不续期。
- 相同SEQ/INDEX但不同DATA：返回04。
- 超过期限、缓存被覆盖或STM32重启：不能保证仍去重。

它降低短时间重发的风险，不是永久事务日志。上位机不能因超时就无限重试相对位置动作；同一个动作停止后要作为新操作发送新SEQ，而不是借旧ACK恢复授权。

### 12.7 软件Fault入口与硬件边界

App_EnterFault记录错误并关闭中断。此时不能只向TX环形队列放STOP，因为TXE中断已经不工作。

因此故障入口调用有界硬件轮询停车：尽可能完成已开始帧的尾部，再尝试3次广播STOP，然后保持故障循环。IWDG已经开启且未被调试冻结时，后续不再喂狗可导致复位。

硬复位、掉电或电机总线断开，不一定能执行/送达这条停车路径。需要驱动器自身失联保护或独立硬件急停/使能切断，并验证制动距离。500ms软件期限不是整车完全停止的时间承诺。

## 13. 串口DMA队列与并发保护

### 13.1 RX：DMA生产，任务消费

每路RX有256字节循环DMA区。DMA写入字节，DMA中断记录圈数/错误；任务依据生产和消费计数调用TryReadByte非阻塞读取。

任务落后太多，旧字节被覆盖会累计drop，保留可读的新数据。读取函数无数据就返回false，不一直等待下一字节。

主控半帧和电机半帧50ms未完成会复位对应解析器并计错，不直接把线路噪声升级成全系统Fault。

电机解析器最多64字节，按功能码固定长度或43帧的长度字段取帧，再检查最后6B。数据内部出现6B是合法可能，不能遇到6B就立即截帧。

### 13.2 TX：整帧原子入队

每路TX软件环形数组为256字节，留一个空槽区分满/空，有效可排队容量255字节。

BSP_UART_Write检查是否能装下整段数据：不够则整段不入队，返回ERROR；够则复制完整数据并使能TXE中断。调用者正常情况下不阻塞等待发送完成。

环形算法保存帧末尾标记。全车STOP会丢弃未开始的旧帧，仅保留正在发送帧的尾部，之后加入停车帧，避免把STOP拼到旧命令中间。

### 13.3 不是所有数据都要求无损FIFO

| 数据 | 当前处理策略 |
|---|---|
| 主控普通应答/多数事件 | 固件8帧发送FIFO，按入队顺序发送 |
| 固件待发IMU E1 | 可替换尚未发送的同类旧快照 |
| PC待发命令 | 最多128帧FIFO，ESTOP独立优先槽 |
| PC普通接收事件 | 最多256项有界队列 |
| PC IMU显示 | 最新快照邮箱和合并计数 |
| PC重复协议错误 | 汇总计数，不逐条挤满事件队列 |

所以本系统优先保障控制响应与界面最新值，不承诺每组IMU历史数据都完整保存。若以后要做离线轨迹估计，需要另设计时间戳和可靠记录通道。

### 13.4 谁可以修改哪些状态

- Control独占主控接收、安全状态、巡检与底盘事务状态。
- Data负责IMU解析/发布，只通过HostProtocol_SendEvent进入共享上报队列。
- TXE中断修改串口发送消费状态；DMA中断修改接收统计。
- 共享环形队列/事件队列用短临界区保护，并恢复原PRIMASK。
- PC只有Tk主线程操作控件；后台线程通过队列/邮箱交接数据。

volatile可以让编译器保留相应访问，但不是互斥锁，也不保证多步更新是原子的。学习并发时要一起看状态所有者和临界区，而不只看变量是否带volatile。

## 14. 上位机调试程序的工作方式

### 14.1 三个类

| 类 | 职责 |
|---|---|
| ConnectionSelfTest | PC连接检查，新固件读取STM32自检，旧固件做只读逐台探测 |
| SerialWorker | 连接、后台收发、帧解析、队列、IMU邮箱、急停本地门禁 |
| TestApplication | Tk界面、参数校验、请求匹配、运动授权意图和显示 |

函数build_frame和crc16_modbus用于编解码。按钮最终经_send_command进入SerialWorker，而不是在Tk回调里等待电机转完。

### 14.2 持续授权

持续授权默认未勾选。需要长动作时先勾选，发送动作；只有收到匹配成功ACK才记录可续租的动作SEQ。

每200ms发送PING。若新固件支持授权、已有有效动作SEQ且复选框勾选，额外发送RENEW。发送的是续租，不是再次执行相对位置动作。

STOP、ESTOP、失能、自检、故障和断线会撤销PC授权并取消勾选。底盘停止/零分量/零最大速度现在统一走STOP，清掉未发旧运动与续租，不会把旧授权留在界面。

成功周期RENEW应答静默；拒绝、未知状态或载荷格式异常会记录原因、撤销授权并提示查询状态。撤销PC变量不是物理停车确认，必要时使用全车STOP/急停。

### 14.3 急停如何优先

ESTOP进入独立优先槽，清待发FIFO并锁定本地运动发送。当前已经开始写入串口的一帧允许写完，下一帧优先发急停。

发送SELF_TEST本身不解除本地锁：当前新固件恢复路径要求按序观察RUNNING和无急停/待停车的PASSED，防止历史PASSED误解锁。STM32自身仍是最终执行门禁。

### 14.4 为什么现在比逐条刷日志更不容易卡

- 串口读超时50ms、写超时100ms，不使用可能无限等待的flush。
- 读写在后台线程，控件在Tk主线程。
- GUI通常每20ms刷新，一次最多64个普通事件或约5ms预算，然后让出事件循环。
- IMU合并为最新快照，不为每个样本执行一串控件操作。
- 日志批量更新，最多保留500行。
- 异常处理和断开有界等待，不无期限卡住主线程。

这些措施限制了常见积压，不代表能排除所有驱动/操作系统/Tk故障。自动控制不应依赖人工GUI持续健康作为唯一安全链路。

### 14.5 在线颜色和日志

绿色是本次自检确认在线，红色是缺失/错误，黄色检测中，灰色未连接。历史绿色不保证设备现在仍正常；运行中还应看STM32故障/状态。

~~~text
QUEUE：PC已构帧并入队
TX：串口写调用已完整提交
RX / ACK：STM32返回数据
E2：电机原始回复
E3：自检/安全阶段或故障
E4：四轮命令事务结果
~~~

PC固定按2/1/3/4解释新固件轮掩码；旧固件PC探测地址默认1/2/3/4。改固件地址后需检查两处显示/探测映射，不能只修改C配置。

### 16.3 建议的硬件验收顺序

1. 架空车轮，准备独立硬件急停/使能切断，确认回零限位。
2. 启动时验证先停车、再自检；缺任一电机或IMU应禁止使能/运动。
3. 逐轮低速确认地址与方向；不能直接四轮落地满速验证。
4. 使能目标轮子，分别测试前后、左右、旋转与组合动作。
5. 只发PING、不续租，确认授权过期停车并锁定；记录实际静止时间。
6. 正常续租时断主控链路，确认失联停车；不要只观察PC日志。
7. 运行中断电机回复/IMU线，验证巡检/新鲜度保护和故障地址。
8. 急停后发VEL/POS/SYNC，确认拒绝；重新自检通过不自动恢复旧动作。
9. 检查普通STOP能退出模式，底盘停止清除持续授权，续租失败有明确提示。
10. 验证主控卡死、任务异常、硬复位、掉电及看门狗复位时实际安全状态。
11. 进行长时间运行、总线忙和重复请求试验，记录错误计数差值与制动距离。

断线的某个驱动器可能收不到广播。完整验收必须包含驱动器自己的失联保护或独立硬件切断，而不是只验证STM32“确实发了STOP”。

## 17. 建议学习顺序与练习

### 第一阶段：理解边界和数据

读本手册第1～4章、app_config.h和project_status.h。能说清主控、STM32、驱动器分别负责什么，识别车轮地址与掩码。

练习：不看表，写出左前/右前/左后/右后地址，并解释为什么bit0不是地址1。

### 第二阶段：追启动与任务

依次读main.c、App_Init、AppTasks_StartScheduler、Control/Data任务。暂时跳过IMU文本数字格式化和第三方内核细节。

练习：画出“上电→READY→自检通过”的时间线；说明自检5秒计时为什么不从IMU上电等待之前开始。

### 第三阶段：先学纯计算，再学电机事务

先读Mecanum_CalculateWheelRpm，再读Mecanum_Drive和Mecanum_Process，最后看HandleMotorResponse、RetryOrCancel、FailStop。

练习：计算F=300、L=-100、C=200、max_rpm=20时四轮RPM，并用现有计算测试方式核对。再判断正负值对应哪些驱动方向位。自查答案：原始量为200、400、0、600，D=1000，四轮RPM为4、8、0、12。

### 第四阶段：理解协议与安全

读HostProtocol_ProcessHostInput、ExecuteFrame、CheckMotionExpiry、ProcessSafety和StopAll。状态多时按“自检、模式、授权、急停、底盘事务、待停车”分类，不要把所有变量混成一个状态。

练习：分别解释只PING、正确RENEW、错误SEQ、过期RENEW和重复POS的结果。指出哪些路径会真正发送全车停车，哪些只是取消软件事务。

### 第五阶段：读设备与BSP

IMU按Init→Process→ParseByte→DecodeFrame→发布样本→Yaw修正阅读。串口按配置表→Write→中断取字节→RX生产计数→TryReadByte阅读。

练习：手工解一帧51，计算校验和与g值；说明为什么同一字段在主控DATA大端、IMU小端并不矛盾。

### 第六阶段：读PC与测试

先读build_frame，再读SerialWorker和TestApplication发送/接收/心跳方法。界面布局函数可以最后看。

练习：从底盘停止按钮一路追到STOP入队、FIFO清理和取消授权；从RENEW拒绝应答一路追到日志提示和心跳只剩PING。

用Tests理解边界条件通常比直接上车试错更安全。先跑已有测试，再在学习副本中构造故障，不建议通过删除安全门禁来“让测试能动”。

## 18. 常见误解与排障

### 18.1 你此前状态日志的正确读法

两次日志VALID从308增到353，增加45个有效单帧；IMU_DROP都为173，没有继续增加。能确定“仍有有效帧到达”和“这两个查询之间该丢字节计数未增长”。

没有两次查询的时间间隔，不能计算频率；VALID不是完整样本数，也不能凭非零历史值判断实时在线。若仅三类帧均衡输出，45帧大致对应15组，但应以完整样本逻辑及实际输出为准。

CHECKSUM/DMA等为0表示相应累计统计未报错，不代表所有机械、安全或驱动器状态都已验收。

### 18.2 常见问题速查

| 现象 | 优先检查 |
|---|---|
| READY出现但运动返回07 | 自检是否通过、急停/底盘锁、待停车和设备健康 |
| 自检通过但电机不动 | 是否使能全部目标、驱动模式与接线、同步触发及E2/E4 |
| PING正常却500ms停车 | 持续授权勾选、动作ACK、RENEW原SEQ和期限 |
| 单电机切底盘返回05 | 全车STOP退出旧模式，再发新模式 |
| 运行中偶发05 | 底盘事务/巡检占用、发送队列忙；不要盲重发相对位置 |
| IMU有效帧一直0 | 设备与USART3波特率、输出、供电、共地、TX接PB11 |
| VALID增长但IMU不通过 | 三类完整样本是否都更新，不是只看历史VALID |
| IMU_DROP历史非零 | 比较间隔内差值，再查处理负载/线路，不直接把历史数当新故障 |
| IMU显示没有500Hz | 9600线路、设备输出、滤波和GUI合并，非仅任务周期 |
| 静止Yaw稳定但慢旋转看不出 | 静止阈值可能吸收超慢旋转，当前不是绝对航向系统 |
| 没看见所有E2/E1 | 上报容量与快照合并；不是无损记录链路 |
| 电机数据中出现6B | 看功能码决定长度，不能直接据6B截帧 |
| ESTOP后旧PASSED不能解锁 | 本地恢复要观察本次RUNNING→PASSED，下位机也要重新自检 |
| stop_pending=0但轮子还动 | 入队不等于收到/执行/静止，检查驱动器与硬件安全链 |

## 19. 目前没有实现的功能与后续接口

当前没有以下整车层功能：

- 以m/s、rad/s为单位、带几何参数的物理底盘接口。
- 四轮持续速度反馈闭环、车体速度估计与防滑补偿。
- 编码器/IMU融合里程计和带时间戳的位姿输出。
- IMU航向PID、世界坐标运动或自动车头保持。
- 路径规划、视觉识别、自动导航和障碍物避让。
- 香橙派主控应用、ROS节点、ROS话题/服务接口。
- 永久动作事务日志、跨重启去重和无限期无损传感器记录。
- 经实车验证的独立硬件急停和驱动器断线安全链。

USART2只是预留硬件接口，不是已经存在视觉功能。Emm驱动器闭环也不能替代上述整车反馈控制。

未来香橙派可复用当前主控协议，但应适配57字节状态、14字节安全载荷与RENEW。续租必须依赖控制任务确认当前动作仍有效，不能由通信线程无条件续租。本文不编写该程序。

判断下位机是否适合接入主控，应同时看：功能正确、状态可解释、故障可锁定、超时会停车、重复请求受控，以及真实硬件安全链能否在断线/掉电时生效。软件测试通过只是其中一部分。
