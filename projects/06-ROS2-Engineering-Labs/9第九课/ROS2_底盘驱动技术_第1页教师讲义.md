# 第九课：底盘驱动技术——第 1 页教师讲义

对应课件：`移动机器人底盘驱动技术——理论学习课件.pptx`。

对应页面：第 1 页，封面“底盘驱动技术”。

课程背景：NanoOmni 全向底盘、RK3588 主控、ROS 2 Humble。

## 本页教学目标

通过课程导入，让学生知道底盘驱动连接哪些模块，理解本课要追踪的两条数据流：速度指令下行和传感器反馈上行。

本页先建立整体认识。串口协议、航位推算、IMU 和里程计的具体实现，随后续 PPT 页面展开。

## 教师开场讲稿

> 前面我们学习了 ROS 2 通信、坐标变换、机器人模型和仿真。现在开始看真实机器人：ROS 2 发出一条速度指令后，底盘怎样接收并执行？电机编码器和 IMU 的数据，又怎样变成 ROS 2 能使用的里程计？
>
> 本课以 NanoOmni 全向底盘为例。主控运行 ROS 2 节点，下位机负责与电机、编码器和 IMU 等硬件交互。底盘驱动负责把双方的数据组织成约定的接口。
>
> 我们沿着两条数据流学习。一条把期望速度送到下位机，另一条把底盘反馈转换成 ROS 2 消息。理解这两条路径后，再去看串口、协议、坐标变换和里程计代码，就能知道每一部分解决什么问题。

### 贯穿案例

以“让机器人向前行驶，并检查它是否真的移动”为例，依次提出以下问题：

1. 谁产生期望速度，使用什么 ROS 2 消息？
2. 底盘驱动如何把消息编码为下位机能够解析的字节？
3. 下位机怎样控制电机，又反馈哪些测量数据？
4. 主控怎样根据反馈估计运动，并把结果提供给导航系统？

强调：发布成功只说明完成了通信链路中的一个环节。判断机器人是否按要求运动，还要结合反馈和实际观察。

## 本课学习目标

完成本课后，学生应能够：

- 说明主控、下位机、电机、编码器和 IMU 的职责。
- 追踪 `/cmd_vel` 从 ROS 2 消息到串口控制帧的处理路径。
- 解释编码器反馈、IMU 航向与航位推算之间的关系。
- 区分期望速度、反馈速度和估计位姿。
- 使用 ROS 2 命令检查话题、消息与 TF，定位驱动链路中的问题。

## 板书

```text
速度指令下行：
导航或遥控节点 → /cmd_vel → 底盘驱动 → 串口协议 → 下位机 → 电机

传感器反馈上行：
编码器、IMU → 下位机 → 串口协议 → 底盘驱动 → 里程计、IMU 消息、TF
```

讲解时在板书上分别标出“期望”和“反馈”，让学生指出哪些信息来自指令，哪些信息来自测量。

## 课堂引导问题

### 问题一：发布了速度指令，能否说明机器人已经按要求运动？

参考答案：不能。需要继续检查驱动是否收到指令、串口是否正常、下位机是否执行，以及反馈数据和实际运动是否符合预期。

### 问题二：机器人被挡住时，为什么不应直接用期望速度推算位移？

参考答案：期望速度不能代表实际运动。机器人可能堵转，也可能轮子转动但车体打滑；编码器反馈同样存在局限，需要结合其他传感器或外部观测判断。

### 问题三：底盘驱动与导航算法如何配合？

参考答案：导航模块产生运动要求，驱动负责硬件通信并提供状态数据。双方通过明确的消息、坐标系和时间约定协作。

## 课堂导入实验：用官方 turtlesim 观察指令与反馈

### 实验目标与来源

使用 ROS 2 官方 `turtlesim`，观察速度指令和位姿反馈的区别。此实验演示 ROS 2 接口关系，不包含实体底盘的串口、电机控制或编码器测量。

来源：ROS 2 Humble 官方教程 [Using turtlesim, ros2, and rqt](https://docs.ros.org/en/humble/Tutorials/Beginner-CLI-Tools/Introducing-Turtlesim/Introducing-Turtlesim.html) 与 [Understanding topics](https://docs.ros.org/en/humble/Tutorials/Beginner-CLI-Tools/Understanding-ROS2-Topics/Understanding-ROS2-Topics.html)。

### 准备条件

已安装 ROS 2 Humble 的 Ubuntu 22.04 或 WSL Ubuntu 22.04，具有可用的图形环境。以下命令在 Ubuntu 的 Bash 中执行，执行目录不限。

按需安装示例包：

```bash
sudo apt update
sudo apt install ros-humble-turtlesim
```

准备 A、B、C 三个终端，每个终端先执行：

```bash
source /opt/ros/humble/setup.bash
```

三个终端使用相同的 `ROS_DOMAIN_ID`。持续运行的命令占用当前终端，后续步骤按终端标注执行。

### 操作步骤

**终端 A：启动仿真。**

```bash
ros2 run turtlesim turtlesim_node
```

预期出现海龟窗口，保持该进程运行。

**终端 B：启动官方键盘控制节点。**

```bash
ros2 run turtlesim turtle_teleop_key
```

保持焦点在终端 B，按方向键控制海龟。

**终端 C：查看接口并观察指令。**

```bash
ros2 topic list -t
ros2 topic echo /turtle1/cmd_vel
```

在终端 B 按方向键时，终端 C 应显示 `Twist` 消息。观察后，在终端 C 按 `Ctrl+C`，再执行：

```bash
ros2 topic echo /turtle1/pose
```

回到终端 B 控制海龟，观察终端 C 中的 `x`、`y`、`theta` 如何变化。

### 结果解释与验收

`/turtle1/cmd_vel` 表达运动要求，`/turtle1/pose` 提供仿真状态。学生应能指出两个话题分别承担什么职责，并展示一次控制输入与位姿变化。

迁移到实体底盘时，仍要区分指令与反馈，但真实的里程计还涉及测量误差、积分和打滑等问题。`turtlesim/msg/Pose` 与 `nav_msgs/msg/Odometry` 的消息结构也不同。

### 常见问题与结束方法

- 找不到包：确认已安装 `ros-humble-turtlesim`，并加载 Humble 环境。
- 没有窗口：检查 Ubuntu 图形环境或 WSLg。
- 按键没有效果：把焦点切回终端 B。
- 指令话题没有输出：在终端 B 按方向键，并检查三个终端的 Domain ID 是否一致。

实验结束时，在终端 C 按 `Ctrl+C` 停止观察，在终端 B 按 `q` 退出键盘控制，在终端 A 按 `Ctrl+C` 结束仿真。
