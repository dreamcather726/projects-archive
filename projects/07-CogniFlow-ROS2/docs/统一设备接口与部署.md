# 统一设备接口与部署

本次交付是源码、配置、测试用例和静态检查；未启动 GUI、节点、模型，未构建或运行测试，未通过实机验证。
新增 MaterialLocation / MaterialState 为向后兼容的独立消息，现有 msg/srv/action 字段和语义不变。

## 1. 部署职责

上位机统一使用 `ros/robot.py:RobotClient`、`ros/telemetry.py:RobotTelemetry` 和
`ui/simulation.py:RobotView`。文件名中的 simulation 保留兼容入口，类本身不依赖模拟模式。
`SimulationClient`、`SimulationView`、`SimulationImage` 只是旧类名的导入别名。

上位机负责语音、澄清、资料、草稿、预检、人工确认、整单下发、遥测展示、查询和取消。
香橙派是唯一动作调度者，自己串行调用导航和机械臂；上位机不调用 NavigateToPose、抓取或放置等底层动作。
模拟器替代香橙派，提供同一公开接口。上位机不订阅 `/simulator/world_state` 或 JSON `/robot_status`。

`use_simulator` 仅控制模拟进程启动、来源标识和原有 WAV 回放选择。false 不再关闭遥测或执行功能。
旧命令 `ros2 run ... dashboard --ros-args -p use_simulator:=true` 仍有效，但不会自动隔离 ROS 域；
推荐使用下文 launch。旧 `/simulator/task/*` 别名只由模拟器兼容提供，默认上位机不再使用。

## 2. 两份部署配置

从工作空间根目录运行，使 received_audio、task_data 等相对路径落在预期位置。
先由用户自行构建（新增消息，必须一起构建 robot_interfaces）：

```bash
cd ~/ai-interaction-ui
source /opt/ros/humble/setup.bash
colcon build --packages-select robot_interfaces robot_simulator robot_visualization
source install/setup.bash
```

模拟：

```bash
ros2 launch robot_visualization dashboard_sim.launch.py
```

默认 ROS_DOMAIN_ID=71；工作台自动启动 AI/audio 辅助进程和模拟器。
模拟器读取同一个本地 catalog.sqlite3；自动分配工位坐标和新物料初始位置只发生在模拟器内。
真实设备：

```bash
ros2 launch robot_visualization dashboard_real.launch.py
```

默认 ROS_DOMAIN_ID=72；工作台只启动 AI/audio 辅助进程，不启动模拟器，也不自动退回模拟模式。
香橙派及其相关进程必须配置同一个 ROS_DOMAIN_ID=72。
两台机器还须完成 DDS 网络发现、统一时间基准和动态 TF 时间校验。建议采用 NTP/chrony；
不能以“topic 名称一样”代替跨机网络、时间和 TF 联调。实机不得启用模拟时钟。

配置入口是 `robot_visualization/config/simulation.yaml`、`real.yaml`。可复制到部署目录，再指定：

```bash
ros2 launch robot_visualization dashboard_real.launch.py domain_id:=72 params_file:=/absolute/path/real.yaml
```

端点、执行节点标识、各类超时、下发记录路径均在 YAML 内。改端点也可通过 ROS remapping；
状态/心跳的 source_node/node_name 是消息字段，不会随 remapping 自动改变，须与 robot_executor_node 一致。
默认执行节点标识为 `/execute_task_action_server`，可在部署配置中替换为香橙派实际的完整节点名。
模拟与真实的下发记录使用不同文件，均位于被 Git 忽略的 task_data 下。

禁止同一公开 Action 名称同时有真实和模拟服务端。默认域隔离、模拟启动前端点占用检查、
预检/下发前多服务端检查共同提供保护；DDS 发现是异步的，不能替代运维侧的域隔离。
发现外部端点时不会自动选择真实设备；不完整的模拟进程组会阻止模拟部署下发。

## 3. 公开接口表

以下频率是模拟实现及真实设备的推荐值；支持配置超时。服务使用 ROS 默认可靠/Volatile QoS。

| 接口 | 类型 | 内容与约定 | QoS / frame / 更新方式 |
|---|---|---|---|
| /task/prepare | robot_interfaces/srv/PrepareTask | 整个 TaskSpec，返回任务、revision、确认上下文及到期时间；不执行动作 | 服务；人工保存后预检 |
| /task/execute | robot_interfaces/action/ExecuteTask | 引用预检后的 task_id/revision；整单执行；Feedback/Result 携带 TaskSnapshot | 标准 Action QoS；阶段变化、低频进度、终态 |
| /task/query | robot_interfaces/srv/QueryTask | 按原 task_id/dispatch_id 查询，返回 TaskSnapshot 和 DispatchReport，found 标志必须真实 | 服务；人工查询，恢复/未知时约每2秒只读查询 |
| /task/cancel | robot_interfaces/srv/CancelTask | 恢复后的任务没有原 Action handle 时使用；success 仅代表取消受理 | 服务；显式人工操作 |
| /task/snapshot | robot_interfaces/msg/TaskSnapshot | 当前任务、revision、active_dispatch_id、event_seq、阶段和进度 | Reliable / TransientLocal / depth1；阶段变化/终态 |
| /robot/status | robot_interfaces/msg/RobotStatus | source_node、业务状态、active_task_id、active_dispatch_id、错误码和自然语言说明 | Reliable / Volatile / depth10；推荐2Hz |
| /robot/heartbeat | robot_interfaces/msg/NodeHeartbeat | node_name、boot_id、递增sequence、uptime、expected_period；只证明活性 | Reliable / Volatile / depth10；推荐2Hz |
| /robot/material_state | robot_interfaces/msg/MaterialState | 完整物料观测、known、held_object_id、boot_id、event_seq、frame_id | Reliable / Volatile / depth10；模拟10Hz，真实推荐2–10Hz |
| /map | nav_msgs/msg/OccupancyGrid | header.frame_id、尺寸、resolution、origin位置及姿态、data | Reliable / TransientLocal / depth1；启动和地图变化时 |
| /camera/image_raw | sensor_msgs/msg/Image | 支持 rgb8/bgr8/mono8/rgba8/bgra8，按step处理行填充 | SensorData（BestEffort/Volatile）；模拟10Hz |
| /odom | nav_msgs/msg/Odometry | header.frame_id 下的位置和姿态；twist的速度与采样时间 | SensorData；模拟10Hz，真实推荐10–30Hz |
| /battery_state | sensor_msgs/msg/BatteryState | percentage为0–1，负值/NaN视为未知；电压独立判断 | SensorData；推荐1–10Hz |
| /tf、/tf_static | tf2_msgs/msg/TFMessage | 地图到里程计的完整变换链 | TF2标准QoS；按定位系统发布 |

公开字段不包含 simulator=true、world_fresh 或 world_state JSON。
RobotStatus.message 仅作说明文字，不编码机器可读 JSON；额外缺失字段显示未知，不推断假值。
地图当前支持平面 origin 的偏航旋转；倾斜栅格原点或倾斜定位变换会明确提示暂不支持。
机器人位置按 odom 的采样时间查询 TF 到地图消息的 frame；缺 TF、外推或无有效时间戳时不画假定位。
地图原点的平移和旋转均参与像素转换。模拟器显式发布 map→odom 的单位静态变换；真实端不得照抄该假设。
不再在上位机自动绘制固定 A/B 工位；工位标注应来自实际地图或后续独立的工位空间数据接口。

### MaterialState

`source_node` 与执行节点标识一致；`boot_id` 与执行端心跳一致，event_seq 在该实例内递增。
`known=false` 表示持物和位置未确认，不是“空手”；只有 known=true 且 held_object_id 为空时才可显示“无”。
每个 MaterialLocation 含 object_id、station_id、carried、position_known、position。
position 统一在 MaterialState.frame_id 内；未知坐标不画到地图上。当前只叠加与地图 frame 相同的物料坐标。
真实端由实际感知/库存/机械臂反馈更新这些观测，不能由上位机根据候选或进度假造抓取成功。

## 4. 草稿、预检与执行绑定

1. 草稿服务保存 TaskDraft；首页显示完整有序动作。
2. 通用客户端将 candidate 放入 TaskSpec，来源 input_id=`draft:<draft_id>:v<revision>`，
   同时保留 source_session_id/source_context_id。调用 PrepareTask，不产生动作。
3. 仅接受匹配 request_id/task_id/confirmation_context_id 的响应。采用执行端返回的正数 revision 和有效期，
   不假设 revision=1。预检绑定当前执行节点实例；实例变化后必须重新预检。
4. 执行端若修改候选，首页展示“执行端建议调整”，禁止沿用旧确认。用户须在编辑器核对、保存新版本后重新预检。
5. 用户明确点击“确认并整单执行”，草稿审阅成功且版本/资料/实例/有效期仍匹配，才发送 ExecuteTask。
   Goal 内没有步骤数组，香橙派从 PrepareTask 保存的对应 TaskSpec 中取完整步骤。
6. 上位机先原子写入本地下发记录，再发送 Goal。重复点击和重连不得重新生成 Goal。
   窗口进程重启后读取原 task_id/dispatch_id，只做查询；记录损坏时阻止新下发，要求人工核对。
7. 任务内容和来源版本由执行端再次校验。任务 ID、下发 ID、来源版本应有服务端去重，不能只依赖界面防抖。

真实工位ID→已标定坐标、物料可取性、机械臂可用性由香橙派预检。
上位机管理的名称和语音别名不等于真实标定坐标，不能通过修改上位机 SQLite 就让未知实机工位变成可执行。

无实物时，可用现有模拟器作为“外部协议桩”验证真实配置（不会操作硬件）：

```bash
# 终端A：先source，然后仅启动协议桩；与真实配置相同的域和本地资料路径。
ROS_DOMAIN_ID=72 ros2 launch robot_simulator simulator_all.launch.py catalog_path:="$PWD/task_data/catalog.sqlite3"
# 终端B：source后启动上位机的真实配置，不会再启动一组模拟器。
ros2 launch robot_visualization dashboard_real.launch.py
```

此场景只证明公开协议互换，不是实机测试。真实设备进入域72前必须关闭这个协议桩。

## 5. 活性、查询与取消

进度和心跳分开。相同执行实例的新心跳，配合仍指向原 task_id/dispatch_id 的新鲜业务状态，
可维持长步骤活性；匹配的 Action 进度也可更新等待期限。心跳本身不证明成功、就绪或已停止。
阶段进度可以低频或只在阶段变化时发送，执行端不等待上位机回复继续。

失联、受理响应超时、投递异常、实例变化或不匹配的结果，均显示结果未知并保留原 ID。
恢复后 QueryTask 必须返回匹配的 TaskSnapshot 和 ACCEPTED DispatchReport，包含来源、revision、
dispatch_id、原 ExecuteTask.request_id/session_id/input_context_id。未知/未找到/查询超时不开放重发。
重启后的执行端若保有原记录，可用查询恢复跟踪；没有记录时保持未知，不能将“未找到”解释成“从未执行”。
当前模拟器记录在执行进程内存中，支持网络/上位机重连查询，重启模拟执行端后记录丢失，返回未找到。
这不是持久化生产调度器。真实香橙派应持久化受理和终态记录，并明确重启后停止/恢复策略，不得自动重演动作。

原 Action handle 存在时使用标准 Action cancel；恢复后使用 CancelTask 服务。
取消受理只意味着开始停止，必须等待对应停止终态。超过取消等待时间仍未确认时保持未知；
在取消等待期间看到 RUNNING 不得冒充已停止。

上位机关闭策略没有改为“断开后一定继续”：保留原行为，对本进程持有的活动 Action 尝试取消；
关闭本窗口拥有的模拟进程，外部进程保留。通过查询恢复的旧任务不会新增隐式关闭取消命令。
实机的失联/上位机关闭策略最终由香橙派和现场安全策略负责。窗口关闭不证明机器人已停。

   重启模拟执行节点后查询未找到，应保持未知，不自动重发。
5. 中断查询后恢复上位机进程：检查本地下发记录被恢复，只查询原ID。
   已运行过的来源版本不得用新task_id悄悄重演。

9. 测试bgr8/mono8、带行填充的图像、未知电量和过期数据；不得伪造零值或空手。
10. 在同一域故意启动重复执行端，预检/下发必须被阻止；真实配置不得启动或回退到模拟器。
