# 香橙派真实设备对接接口

对接草案：`1.0-draft`；任务类型版本沿用 `robot_interfaces/TaskSpec.interface_version=0.3.1`。
适用：ROS 2 Humble、单台机器人、上位机通过香橙派接入 SLAM／导航、底盘、相机和机械臂。

这是一份双方确认后实施的接口交付文件，不是设备驱动或已经接通的真实执行程序。
已有消息字段以 [robot_interfaces](../robot_interfaces/) 源码为准，通用约束见
[接口协议](接口协议.md)。本文件不修改任何 `.msg/.srv/.action`。

## 1. 部署与职责

推荐按现有“整份 TaskSpec → ExecuteTask”的契约部署：

```text
上位机：语音识别／语义解析 → 草稿编辑 → 用户确认 → 任务客户端
                                    ↕ ROS 2
香橙派：真实任务执行网关（唯一顺序调度者）
          ├─ NAVIGATE → SLAM／导航组 → 底盘
          ├─ PICK／PLACE → 机械臂／夹爪组，按需调用视觉
          └─ 汇总地图、定位、图像、部件、物料及执行状态 → 上位机
```

- 上位机提交一次已确认的有序任务；网关完成当前动作后才推进下一动作。
- 底盘原始编码器、电机和速度控制留给导航／底盘侧，上位机不直接下发轮速。
- 香橙派是统一接入口，可以运行多个 ROS 节点，无需把全部数据塞入单一 Topic。
- 调度者也可最终部署在上位机，但必须双方明确变更；不能两端同时拆解和执行同一任务。
- 真实执行端与模拟执行端分开部署；不可把 `/simulator/task/*` 当作实机接口。

## 3. 香橙派 → 上位机：遥测清单

频率为建议验收配置，不代表现有驱动已实现；双方应记录实际频率。
QoS 写为“可靠性／持久性／KeepLast 深度”。

| 名称 | 类型 | 内容与建议频率 | QoS |
|---|---|---|---|
| `/map` | `nav_msgs/msg/OccupancyGrid` | `map` 坐标系、分辨率、完整 origin 位姿、栅格；启动及更新时发布 | Reliable／TransientLocal／1 |
| `/amcl_pose` | `geometry_msgs/msg/PoseWithCovarianceStamped` | 地图坐标中的机器人位姿及协方差；建议 5～10 Hz；非 AMCL 定位提供等价入口 | Reliable／Volatile／10 |
| `/odom` | `nav_msgs/msg/Odometry` | `odom` → `base_link` 的位姿、实际速度；建议 20 Hz | BestEffort／Volatile／5 |
| `/tf` | `tf2_msgs/msg/TFMessage` | 动态坐标变换，含 map→odom、odom→base_link | Reliable／Volatile／100 |
| `/tf_static` | `tf2_msgs/msg/TFMessage` | 底盘、相机、机械臂固定外参 | Reliable／TransientLocal／1 |
| `/plan` | `nav_msgs/msg/Path` | 可选，地图坐标中的规划路径；规划变化时发布 | Reliable／Volatile／1 |
| `/camera/image_raw` | `sensor_msgs/msg/Image` | 图像、真实 encoding、step、采集时间；建议 10 Hz，尺寸双方约定 | BestEffort／Volatile／5 |
| `/camera/camera_info` | `sensor_msgs/msg/CameraInfo` | 标定内参、畸变、图像尺寸及光学坐标系；与图像匹配 | BestEffort／Volatile／5 |
| `/battery_state` | `sensor_msgs/msg/BatteryState` | 电量 [0,1]、电压、电流等；建议 1 Hz，未知测量按标准填写 | BestEffort／Volatile／5 |
| `/joint_states` | `sensor_msgs/msg/JointState` | 可选，机械臂／夹爪关节实测状态；建议 10 Hz | BestEffort／Volatile／5 |
| `/robot/status` | `robot_interfaces/msg/RobotStatus` | 单一整机汇总源；建议 5 Hz，变化时立即发布 | Reliable／TransientLocal／1 |
| `/robot/component_status` | `robot_interfaces/msg/ComponentStatus` | 部件就绪／忙碌／故障；1 Hz，变化时立即发布 | Reliable／Volatile／20 |
| `/safety/state` | `robot_interfaces/msg/SafetyState` | 唯一安全状态源；5 Hz，变化时立即发布 | Reliable／TransientLocal／1 |
| `/system/heartbeat` | `robot_interfaces/msg/NodeHeartbeat` | 关键节点活性、boot_id、sequence；1 Hz | Reliable／Volatile／50 |
| `/diagnostics` | `diagnostic_msgs/msg/DiagnosticArray` | 可选，驱动原始故障和主机诊断；建议 1 Hz | Reliable／Volatile／10 |

约定：

- 位移 m、角度 rad、速度 m/s 和 rad/s；四元数归一化，使用采集时间戳。
- 上位机地图标记使用 map 中的位姿，或用对应时刻 TF 转换后的位姿；不能直接把 odom 坐标画到地图上。
- 定位失败、TF 缺失或动态数据过期显示“未知／失联”，不得用全零代替有效定位。
- 动态遥测默认 2 秒过期，可按频率调整；地图／静态 TF 不按此时间失效。
- 状态汇总不是执行授权；安全状态按照已有协议检查新鲜度，不能由 UI 或模型生成许可。
- 发布端与订阅端 QoS 需兼容；图像支持何种编码由双方确认并由真实适配层转换。
- `/battery_state` 是实机约定；当前模拟 UI 使用 `/battery`，接入时需要适配或 remap。
- `/robot/status` 是现有类型化协议；当前模拟 `/robot_status` 的 String JSON 不是实机协议。

## 4. 上位机 ↔ 香橙派：整任务执行接口

香橙派执行网关实现下列已有类型，接收整份任务并顺序调用本地导航、抓放动作。

| 名称 | 类型及源码 | 作用 |
|---|---|---|
| `/task/prepare` | [PrepareTask.srv](../robot_interfaces/srv/PrepareTask.srv) | 校验任务、场景、部件状态，返回任务版本及待确认上下文；不启动动作 |
| `/task/execute` | [ExecuteTask.action](../robot_interfaces/action/ExecuteTask.action) | 接收已确认版本，执行 NAVIGATE／PICK／PLACE；返回反馈和终态 |
| `/task/query` | [QueryTask.srv](../robot_interfaces/srv/QueryTask.srv) | 按原 task_id／dispatch_id 查询，供超时、重连、重启恢复使用 |
| `/task/cancel` | [CancelTask.srv](../robot_interfaces/srv/CancelTask.srv) | 受理取消；也支持标准 Action 取消，两者进入同一取消流程 |
| `/task/events` | [TaskEvent.msg](../robot_interfaces/msg/TaskEvent.msg) | Reliable／Volatile／10；权威任务状态变化，含完整快照 |
| `/safety/estop` | [SetEmergencyStop.srv](../robot_interfaces/srv/SetEmergencyStop.srv) | 锁存软件停止；受理与实际停稳分开确认 |
| `/safety/reset` | [ResetEmergencyStop.srv](../robot_interfaces/srv/ResetEmergencyStop.srv) | 操作者明确复位，绑定安全 boot_id／state_seq；不恢复旧任务 |

### 4.1 完整调用顺序

1. 上位机生成 TaskSpec：版本 `0.3.1`，保留草稿来源和有序候选；为准备请求生成 request_id、confirmation_context_id。
2. 调用 PrepareTask。失败时展示原因，不发送执行 Goal；成功只表示“已准备，等待确认”。
3. 展示网关返回的实际任务与 revision。用户必须确认该准确版本；若准备期间任务被修改／规范化，应重新展示，不沿用先前确认。
4. ExecuteTask.Goal 填写返回的 task_id、revision；session_id 对齐任务来源；input_context_id 使用返回的 confirmation_context_id；confirmed_at 在有效期内；dispatch_id 标识本次下发。
5. 网关再次校验确认、安全和依赖状态。Goal 接受仅表示受理，依赖 Feedback／Result 判断执行。
6. 按任务顺序执行，当前子动作确认成功后才推进；失败停止后续步骤。
7. 超时或失联先查询原 ID；结果未知时不换 ID 自动重发。重启恢复记录或显式进入人工恢复，不能重新播放旧任务。

`ExecuteTask.Goal` 没有步骤数组；步骤已通过 PrepareTask 中的 TaskSpec 传入。
不新增第二个“确认即执行”的旁路，也不让模型直接调用硬件。

### 4.2 四步任务示例

下面仅展示 `TaskSpec.candidate` 的完整内容，不是完整 PrepareTask 请求，不可直接作为执行命令。
时间戳为占位，实际发送时填写有效 ROS 时间；A/B/box_1 必须对应实机配置。

```yaml
stamp: {sec: 0, nanosec: 0}
task_type: 3                 # TaskCandidate.SEQUENCE
object_id: ""
pickup_station_id: ""
dropoff_station_id: ""
destination_station_id: ""
return_required: false
return_station_id: ""
steps:
  - {stamp: {sec: 0, nanosec: 0}, task_type: 1, object_id: "", pickup_station_id: "", dropoff_station_id: "", destination_station_id: station_a, return_required: false, return_station_id: ""}
  - {stamp: {sec: 0, nanosec: 0}, task_type: 4, object_id: box_1, pickup_station_id: station_a, dropoff_station_id: "", destination_station_id: "", return_required: false, return_station_id: ""}
  - {stamp: {sec: 0, nanosec: 0}, task_type: 1, object_id: "", pickup_station_id: "", dropoff_station_id: "", destination_station_id: station_b, return_required: false, return_station_id: ""}
  - {stamp: {sec: 0, nanosec: 0}, task_type: 5, object_id: box_1, pickup_station_id: "", dropoff_station_id: station_b, destination_station_id: "", return_required: false, return_station_id: ""}
```

步骤类型定义见 [TaskStep.msg](../robot_interfaces/msg/TaskStep.msg)。数量按草稿可变，当前项目上限 256 步；超过拒绝，不截断。

### 4.3 反馈、完成、取消

完整字段见 [TaskSnapshot.msg](../robot_interfaces/msg/TaskSnapshot.msg)。

- Feedback.task 与 TaskEvent.snapshot 来自同一执行状态；task_id、dispatch_id、revision 必须匹配。
- `step` 使用便于显示的描述，例如 `2/4 抓取 box_1 @ station_a`；现有消息没有独立的步骤序号字段，不私自追加字段。程序恢复使用任务快照和持久化执行记录，不能依赖解析中文描述。
- `progress` 为 [0,1]，未知为 -1；根据已完成动作和有效反馈计算，不用定时器耗时冒充进度。未成功终结时不发 1。
- 状态沿用 PENDING_CONFIRMATION=0、RUNNING=1、CANCELING=2、SUCCEEDED=3、FAILED=4、CANCELED=5。
- Result.success=true 必须对应所有步骤完成、快照 SUCCEEDED、error_code 为空；ROS Action 同时为 SUCCEEDED。
- 业务失败对应 FAILED／Action ABORTED；确认停止后的取消对应 CANCELED／Action CANCELED。终态不可被迟到反馈覆盖。
- `pickup_completed`／`dropoff_completed` 在本任务全部相应动作确实完成时置 true；多次搬运不等同于当前是否持物。返回动作未要求时 return_completed=false。
- 取消受理后先进入 CANCELING；等导航和机械臂确认停止及必要的持物处置完成，再返回 CANCELED。无法确认停止时保持未确认并报告 CANCEL_NOT_CONFIRMED，不能直接声称已停。
- 导航／机械臂超时按执行组约定处理，保留实际位置和持物状态；上位机失联后的本地停止策略由香橙派实现，不依赖 UI 在线。

## 5. 香橙派内部的动作适配：执行组需要交付什么

这一层由香橙派执行网关调用，接口名和机械臂类型尚需设备组填写；不是仓库已提供的驱动。

| 动作 | 网关提供 | 执行组必须返回／保证 |
|---|---|---|
| NAVIGATE | 工位对应的 map 目标位姿及本次动作关联 | 接受／拒绝、当前位置／剩余距离、成功／失败／取消；约定停车位置和朝向误差 |
| PICK | object_id、取货工位，按设备需要提供经验证的抓取位姿 | 目标有效、动作状态、真实持物证据、失败原因、停止确认 |
| PLACE | 持有的 object_id、放货工位／放置位姿 | 动作状态、释放及放置结果、失败原因、停止确认 |

导航采用 Nav2 时通常使用 `/navigate_to_pose`、`nav2_msgs/action/NavigateToPose`，实际名称由导航组确认。
Humble 的 Goal 为 pose + behavior_tree，Result 载荷是 Empty；须同时读取标准 ROS Action 终态，不能期待其中存在 success 或错误字符串。
Feedback 可使用 current_pose、distance_remaining 等；零剩余距离或 Goal 已接受不能代替最终成功。

机械臂组交付时填写：

| 项目 | 实际值 |
|---|---|
| 抓取／放下 Action 名称、包名、完整 `.action` | 待提供 |
| Goal 各字段、坐标系、抓取／放置姿态来源 | 待提供 |
| Feedback／Result、拒绝与错误码、取消语义 | 待提供 |
| 判定已抓住／已释放的传感器及条件 | 待提供 |
| 无物料身份识别能力时如何确认 object_id | 待提供；不能把“夹爪闭合”直接视为抓对目标 |
| 持物时断网、急停、故障的处理 | 待提供；不能默认松爪释放 |

`FollowJointTrajectory`／夹爪运动完成只代表底层运动结果；需要设备侧业务适配判断是否真正抓住、是否完成放置。
没有机械臂接口定义前，不使用虚构的 `/pick` 或 `/place` 类型冒充可运行接口。

## 6. 工位、物料及视觉数据

### 6.1 工位交付表

导航组负责标定停车位姿，机械臂／视觉组负责抓放位姿；集成人员维护版本化配置。
当前上位机资料仅有 ID／名称／别名／启用状态，不具备导航坐标存储和下发能力。

| 字段 | 示例／含义 |
|---|---|
| station_id、name、aliases | station_a、A工位、A点；与上位机白名单一致 |
| map_id、map_revision、frame_id | 对应现场地图，frame_id=map |
| navigation_pose | 真实 x/y/z 和四元数 x/y/z/w；不是模拟默认坐标 |
| position_tolerance_m、yaw_tolerance_rad | 由导航及机械臂共同验收的停车误差 |
| pickup_pose／place_pose 或配方 ID | 由机械臂组定义，注明坐标系、标定版本和适用物料 |
| 可用动作、配置版本 | 是否支持 PICK／PLACE；配置变更使旧准备结果失效 |

### 6.2 物料状态扩展（待双方确认并实施）

已有 RobotStatus／TaskSnapshot 都没有完整物料位置和持物可信度字段。
建议新增遥测 `/robot/material_state`，类型 `std_msgs/msg/String`，JSON schema `1.0`，
单一网关汇总发布；建议 Reliable／Volatile／10、5 Hz、变化立即发布。
这是本文件提出的扩展，当前仓库没有发布者／订阅者，不能据此声称已有真实物料接口。

```json
{
  "schema_version": "1.0",
  "stamp": {"sec": 1793700000, "nanosec": 0},
  "source_node": "/robot_execution_gateway",
  "boot_id": "example-boot-id",
  "sequence": 1,
  "task_id": "example-task-id",
  "dispatch_id": "example-dispatch-id",
  "held_object_known": true,
  "held_object_id": "box_1",
  "objects": [
    {"object_id": "box_1", "location_known": true, "state": "CARRIED", "station_id": "", "evidence": "verified_pick_result"}
  ]
}
```

- stamp 为本次状态生成时间；持物和位置结论必须有未过期的传感器／动作证据。证据失效后改为未知，不能仅刷新 stamp 把旧结论当新测量。
- boot_id 每次启动更换，sequence 每次发布递增；消费者丢弃同一来源旧序号，重启先重新核对物理状态。无活动任务时 task_id／dispatch_id 为空。
- held_object_known=true 且 held_object_id 为空表示“已确认空手”；false 表示“持物未确认”，此时 held_object_id 为空，不得理解为空手。
- 对象 state 限 AT_STATION／CARRIED／UNKNOWN；location_known=false 时 state=UNKNOWN、station_id 为空。
- AT_STATION 必须带有效 station_id；CARRIED 的 station_id 为空，且必须与已确认的 held_object_id 一致。当前单夹爪最多一个 CARRIED。
- evidence 是设备可解释的证据来源；抓取失败／取消时不能靠原计划推测物料位置，需核对实际状态。
- 默认 2 秒未接收有效更新显示未知；这不是现有模拟 `/simulator/world_state`，不复用 simulator=true 标记。

视觉若用于自主抓取，还需交付实际识别消息定义、object_id 对应规则、目标 PoseStamped／协方差或质量指标、采集时间、有效期及相机到机械臂的变换。
只有图像不能直接形成可靠抓取目标；若使用固定工位抓取配方，也应明确配方适用范围。

## 7. 已有界面的实际接入缺口

- `SimulationClient` 只在 use_simulator=true 时创建，调用 `/simulator/task/*`；目前没有实机任务客户端。
- 模拟图像仅处理 rgb8；真实 bgr8／mono／压缩流需转换。真实地图需处理完整 origin 朝向及 TF。
- 模拟 UI 直接使用 odom 的 x/y；真实地图必须改接 map 定位或 TF 转换结果。
- 模拟状态要求 `/robot_status` JSON 中 simulator=true；真实 `/robot/status` 类型不同，不能直接连接现有模拟槽位。
- 当前 UI 尚未显示完整实机 RobotStatus、SafetyState，也没有本文件提出的物料扩展处理。
- 模拟执行器没有真实驱动、实机持久化恢复及完整安全管理。真实执行网关必须另行实现；不能把模拟计时改名后部署为真实执行。

因此本次文件可用于分工和签订联调约定，不能通过改一个开关完成实机接入。

## 8. 双方交付及验收

香橙派集成人员交付：实际接口名称与类型、消息包源码／版本、启动方法、namespace／QoS、
工位和物料清单、故障码、取消和断网策略，以及包含地图／定位／图像／状态的 rosbag2。
同一份 robot_interfaces 在双方同步构建，不独立改字段。

建议按顺序验收：

1. 只读联通：发现节点、Topic／Action 类型正确；地图、定位、相机、电池和部件状态可接收。
2. 静态配置：station_a／station_b 与地图一致；朝向、坐标系、停车误差和抓放配方完成确认。
3. 单步：分别验收导航到站、抓取成功及失败、放下成功及失败、各自取消停止。
4. 四步：导航 A → 抓 box_1 → 导航 B → 放下；位置、持物和任务进度来自真实反馈。
5. 异常：定位丢失、目标不存在、抓空、放置失败、取消未停、断网、重启和重复 dispatch；不得继续推进或自动重发。
6. 重连：按原 task_id／dispatch_id 查询恢复；未确认物料状态不宣告空手或完成。

以下命令供双方在实际 Humble 环境手动读取检查，不会发送运动任务：

```bash
ros2 node list
ros2 topic list -t
ros2 action list -t
ros2 service list -t
ros2 interface show robot_interfaces/action/ExecuteTask
ros2 topic info /map --verbose
ros2 topic echo /map --qos-reliability reliable --qos-durability transient_local --once
ros2 topic echo /battery_state --qos-reliability best_effort --once
ros2 run tf2_ros tf2_echo map base_link
```

本文件不提供可直接下发真实运动的 CLI 示例。首次运动由设备组在其已验收的启动和停止条件下手动联调。
