# ai交互界面接口协议

版本：`0.3.1`。适用环境：PC Linux 虚拟机、ROS 2 Humble。

本文件对应仓库内 `robot_interfaces/msg`、`srv`、`action` 的实际定义。节点行为、持久化、超时与设备控制仍需开发，接口文件本身不会执行这些约束。

0.3.0 新增可变步骤列表、草稿审阅服务和长录音；0.3.1 将草稿拆成 NAVIGATE/PICK/PLACE 动作，搬运确定性展开为四步，详细接口与验收步骤见[任务草稿与长任务](任务草稿与长任务.md)。草稿人工确认不代替下述 ExecuteTask 的机器人执行授权。

## 1. 统一回复格式

“至少两个消息”按每条回复中至少两个必填字段处理：

| 字段 | 类型 | 约定 |
|---|---|---|
| `success` | `bool` | 本次业务操作是否成功；不能用 ROS 通信成功代替业务成功 |
| `message` | `string` | 必须非空；成功写清已完成什么，失败写清原因及可采取的操作 |
| `error_code` | `string` | 成功为空字符串；失败为固定错误码，便于程序判断 |
| `stamp` | `builtin_interfaces/Time` | 响应生成时间 |
| `request_id` | `string` | 原样回传对应请求的 ID，禁止重新生成 |

例如准备任务成功（仅表示待确认）：

```yaml
stamp: {sec: 1793491201, nanosec: 120000000}
request_id: "prepare-001"
success: true
message: "任务已准备，请确认从 station_a 搬运到 station_b。"
error_code: ""
```

例如准备失败：

```yaml
stamp: {sec: 1793491201, nanosec: 120000000}
request_id: "prepare-001"
success: false
message: "放料工位 station_b 未配置，请选择有效工位。"
error_code: "UNKNOWN_STATION"
```

以上只展示共同字段，完整响应还包含接口定义中的业务字段。RecognizeAudio 的共同响应字段位于 response.result（RecognizedText）内；ProcessAudio 的受理字段位于 response.receipt（RequestStatus）内，不在顶层重复定义。不拆成两个独立数据包，避免成功标志与说明错配。Action Feedback 只描述进行中的阶段，不用 `success` 提前宣告最终完成；Action Result 才携带完整结果。

Topic 没有原生请求／响应。音频和文字接收方须在 `/ai/request_status` 发布 `RequestStatus` 业务回执，原样携带输入 `request_id`：`RECEIVED + success=true` 表示输入已受理，`REJECTED + success=false` 表示输入被拒绝；最终识别结果、任务结果另行返回。回执缺失只能显示“未确认是否受理”，不能猜测成功或自动创建新 ID 重发。

## 2. 时间与关联标识

- 所有自定义 `.msg` 及 Service Request／Response、Action Goal／Result／Feedback 都有 `stamp`。发送方设置为该数据生成时间，转发已有数据时保留源时间；嵌套任务与候选的 `stamp` 保留自身创建时间。
- `Time` 包含秒 `sec` 和纳秒 `nanosec`，`0 <= nanosec < 1000000000`。通过 `node.get_clock().now().to_msg()` 赋值。时间不能用作唯一 ID。
- 实机各节点使用同步的系统时间；仿真各节点统一 `use_sim_time=true` 和同一个 `/clock`。禁止混用系统时间、仿真时间和字符串时间。界面显示时再转为本地日期时间。
- 未收到有效仿真时钟时不接受任务确认。超时等待使用单调时钟；确认到期按统一 ROS 时钟检查，时钟回退或大幅跳变须使旧确认失效。时间戳用于新鲜度和追踪，不能证明用户授权。
- `request_id` 为每次逻辑操作生成的全局唯一字符串，建议 UUID。重试同一逻辑请求保留 ID 与业务内容；同一 ID 绑定不同内容返回 `REQUEST_ID_CONFLICT`。收到回复按 ID 关联，不按到达顺序关联。
- `session_id` 表示会话，`input_context_id` 表示输入当时的上下文；`input_id` 表示用户输入，`task_id` 表示业务任务，`dispatch_id` 表示一次执行尝试。它们与 ROS Goal UUID 分开保存。
- 音频输入统一映射为 `input_id="audio:" + segment_id`，文字 ID 使用 `text:` 前缀。同一输入重发保留 ID；两次相同文字仍是两次不同输入。
- 实现节点应校验字段、枚举、时间顺序及长度。`stamp`、录音起止时间、识别完成时间应处于同一时钟域；未来时间、过期数据或来源缺失的数据禁止触发运动。

## 4. 音频、识别与解析

录音控制复用标准 `std_srvs/srv/Trigger`：Request 为空，Response 为 bool success、string message，不增加自定义字段。当前简化接收节点仅订阅音频，由命令行／客户端直接调用设备端 `/audio/start_recording`、`/audio/stop_recording`。历史版本的 `/interface/*` 异步转发与三秒超时未在当前版本保留，不能据此认为现在存在超时保护；客户端须自行限制等待，超时仅表示结果未知，禁止自动重试或猜测录音状态。Trigger 没有 error_code 字段，也没有 request_id 或 stamp。

香橙派须实现两个服务并串行处理设备状态转换：开始成功说明麦克风已进入采集；停止成功说明采集停止并已发布 `/audio/segments`，不保证 PC 已收到。重复开始不得清空或重启当前缓冲；重复停止不得重复发布旧片段，没有活动录音时返回清楚说明。未收到开始完成答复前不要并发提交相反命令，超时后由操作者核对或请求停止。设备开始时锁定当前会话和输入上下文，为片段生成关联 ID；未取得有效上下文须拒绝开始。达到配置的录音上限（默认120秒、最多300秒）自动停止并发送片段；空音频或设备错误返回失败，不生成假录音。此约定需由设备端实现，本仓库只实现 PC 请求与接收。


真实采集入口为工作空间根目录下的 `ros2 run ai_interface microphone_sender_node`，使用 PulseAudio 的 parecord，提供开始／停止服务，并发布真实原始 PCM。开始回执只表示采集进程已创建，设备随后失败由日志报告；停止回执成功表示采集已停并已发布数据，不代表接收落盘。无效设备、无数据、停止异常或无订阅者不发布假音频，失败消息前缀为 AUDIO_CAPTURE_FAILED／AUDIO_DEVICE_UNAVAILABLE。设备参数默认为 @DEFAULT_SOURCE@；session_id 与 input_context_id 参数在开始时锁定，默认生成的标识仅用于独立传输测试，不能替代有效业务确认上下文。录音起止时间按结束时刻与实际帧数估算，非硬件时间戳。命令、依赖和 WSL 实测记录见 README。

`AudioSegment` 包含会话／片段／上下文、采集起止时间、采样率、声道、编码和数据。首版固定 `encoding=pcm_s16le`、`sample_rate=16000`、`channels=1`，最长300秒、最大9600000字节。数据长度必须为 2 的倍数，并与实际采集时长相符。`PlayAudio` 使用相同格式，但仍保持每段10秒上限；长播报由 TTS 分成有序片段串行播放。

接口工程师侧现有接收入口为 `ros2 run ai_interface audio_receiver_node`，订阅 `/audio/segments` 并在 `output_dir` 参数目录保存 WAV；运行命令见 README。它校验四个关联 ID、录音起止时间、格式及时长（容差 50 ms），关闭 WAV 文件后将来源信息和路径打包转交 ai_edge（见第 13 节）。校验／保存失败统一返回 AUDIO_RECEIVE_FAILED。输出文件名包含北京时间、微秒与 UUID；成功保存回执不代表 ASR 成功。

`RecognizedText` 原样回传输入的 `request_id`、会话、片段、上下文和采集时间，另带 `recognized_at`：

| `status` | `success` | `text` | `error_code` | 后续行为 |
|---|---|---|---|---|
| `SUCCESS=0` | true | 非空 | 空 | 可进入解析 |
| `NO_SPEECH=1` | false | 空 | `NO_SPEECH` | 提示未检测到有效语音，不解析、不准备 |
| `FAILED=2` | false | 空 | 如 `ASR_FAILED` | 说明失败原因，不解析、不准备 |

每个片段只发布一次逻辑最终识别结果；重复投递须去重。采集节点在录音开始时锁定会话和上下文，ASR 不得在完成时改绑新的上下文。

`ParseTask` Goal 包含输入标识、文字、最多 20 条 `DialogueTurn` 历史、部分候选及工位／物料白名单。DialogueTurn 包含 stamp、role（USER=0／ASSISTANT=1）、text。本轮 text 最多16384字符，历史每条最多4096字符；实现节点仍须设置模型总上下文与推理超时上限。

| `outcome` | `success` | `error_code` | 结果与后续行为 |
|---|---|---|---|
| `READY=0` | true | 空 | 类型化候选完整且通过校验，可请求准备 |
| `NEED_CLARIFICATION=1` | false | `MISSING_FIELDS` | 返回 `missing_fields` 和 `clarification_question`，等待补参 |
| `UNSUPPORTED=2` | false | `UNSUPPORTED_TASK` | 明确告知不支持，不创建运动任务 |
| `FAILED=3` | false | 如 `INVALID_MODEL_OUTPUT` | 明确失败原因，不创建运动任务 |
| `CANCELED=4` | false | `CANCELED` | 解析已取消，不创建运动任务 |

`READY` 和 `NEED_CLARIFICATION` 表示本轮解析正常结束，可对应 ROS Action `SUCCEEDED`；业务 `success` 仅在候选完整时为 true。`UNSUPPORTED`／`FAILED` 对应 `ABORTED`，主动取消对应 `CANCELED` 且 `success=false, error_code=CANCELED`。客户端同时处理标准 Action 状态与业务结果。

`TaskCandidate` 只允许 `NAVIGATE=1` 或 `TRANSPORT=2`，`UNKNOWN=0` 仅供未完成的候选使用：

- 导航：`destination_station_id` 必填，物料、取放工位为空。
- 搬运：`object_id`、`pickup_station_id`、`dropoff_station_id` 必填，导航目的工位为空。
- `return_required=true` 时 `return_station_id` 必填；false 时返回工位为空。
- 所有工位和物料都必须命中配置白名单；模型不得生成执行许可、底层运动指令或修改程序生成的 ID。

## 5. 准备、确认、执行

1. 交互节点先按 `(session_id,input_id)` 登记并持久化输入，只消费一次。查询和明确取消指令在模型调用之前分流。
2. 解析 READY 后生成 `TaskSpec`，保留来源会话、输入与上下文。生成独立 `confirmation_context_id`，调用 `PrepareTask`。
3. 调度节点校验任务、白名单、来源去重和上下文，将确认上下文与任务／版本绑定并持久化。成功响应返回权威任务、非零 `revision`、原样确认上下文和 `confirmation_expires_at`。拒绝响应中的默认任务、版本和时间不可使用。
4. `TaskDraft.input_context_id` 使用准备响应中的确认上下文。界面展示权威摘要及版本；语音提示播放完毕后才开放语音确认窗口。
5. 用户明确确认后发送 `ExecuteTask` Goal，携带任务、版本、`dispatch_id`、会话、确认上下文与 `confirmed_at`。调度节点原子核验绑定、到期时间及运行条件，并保证同时最多一个运动任务。
6. 准备成功不等于开始执行；Goal 接受不等于完成搬运。只有最终 `TaskSnapshot.state=SUCCEEDED` 且所有要求的步骤确已完成时，执行 Result 才能 `success=true`。

业务状态为 `PENDING_CONFIRMATION=0`、`RUNNING=1`、`CANCELING=2`、`SUCCEEDED=3`、`FAILED=4`、`CANCELED=5`。具体执行步骤写入 `step`，例如导航取料、抓取、导航放料、放置、返回。

`pickup_completed`、`dropoff_completed`、`return_completed` 报告真实完成情况。要求返回时，返回失败仍使整单失败，但不得抹掉物料已放置的事实。业务 FAILED 对应 Action ABORTED；CANCELED 对应 Action CANCELED。

修改参数须作废旧候选，重新准备和确认。新候选、取消、过期、时钟异常或交互节点重启都关闭旧确认上下文；恢复后不能复用口头许可。迟到 ASR、旧按钮、含糊回复及模型输出的“已确认”均不能确认新任务。

## 6. 拒绝、查询、取消与恢复

ROS 标准 Action Goal 接受／拒绝响应不能添加业务 `message`。被拒绝的 Goal 不产生自定义 Result，因此不能等 Result 获取原因。

- 执行 Goal 的接受／拒绝决定在响应前保存为 `DispatchReport`，通过 `QueryTask` 查询。记录绑定 `dispatch_id + task_id + revision`；`ACCEPTED` 对应 success=true，`REJECTED` 对应 success=false 与具体错误。
- `UNKNOWN` 的 success=false 只表示没有成功结论，`error_code=DISPATCH_UNKNOWN`，不得当作确定拒绝。写记录失败须拒绝并告警；查询不到原因时显示“下发结果未确认”。
- `ParseTask`、`Speak`、`PlayAudio` 在 Goal 拒绝时由提供节点在 `/ai/request_status` 发布 `REJECTED` 回执，回传原请求 ID 与具体原因；回执丢失时显示原因未确认，不伪造 Result。
- `QueryTask` 至少指定 `task_id` 或 `dispatch_id` 之一。显式指定的记录全部找到时 success=true，即使查到的是失败任务或被拒绝的下发记录。部分找到或均未找到时 success=false，但各 `found=true` 的记录仍有效；找不到的字段不可使用。
- 查询错误使用 `TASK_NOT_FOUND`、`DISPATCH_NOT_FOUND` 或 `RECORD_NOT_FOUND`；执行拒绝原因读取 `dispatch.error_code/message`，任务失败原因读取 `task.error_code/message`，三者不混用。两个 ID 同时指定时必须匹配，否则返回 `INVALID_REQUEST`。
- `CancelTask.success=true` 仅表示取消受理；正在执行的任务进入 CANCELING，等所有活动子动作停止并完成安全处置后才到 CANCELED。准备中的任务可直接作废。持有 Goal Handle 的客户端也可用标准 Action 取消入口，两条入口共用业务处理。
- 重复取消正在取消的任务返回受理；已取消返回成功并说明；其他终态返回 `TASK_ALREADY_FINISHED`，不能伪装成取消成功。
- 下发超时或节点重启先查原 `task_id/dispatch_id`，不得换 ID 自动重发。相同来源相同业务内容返回原任务；来源或请求 ID 内容冲突须拒绝。重复 dispatch ID 不能创建新的 ROS Goal。
- 任务、输入关联、下发决定与事件序号必须跨重启保存。恢复后查询权威快照，再消费 Topic；同一任务按递增 `event_seq` 去重。终态不可被迟到反馈覆盖。

`Speak.success=true` 要等全部音频播放结束；只完成文本合成不能宣告播报成功。录音节点在播放时暂停或抑制回录；播报取消须传播到活动的 PlayAudio，确认播放停止后才返回取消结果。

## 7. 错误码与通信约定

首版错误码包括：`INVALID_REQUEST`、`REQUEST_ID_CONFLICT`、`INPUT_ID_CONFLICT`、`TASK_ID_CONFLICT`、`NO_SPEECH`、`AUDIO_DEVICE_UNAVAILABLE`、`AUDIO_FORMAT_UNSUPPORTED`、`ASR_FAILED`、`MISSING_FIELDS`、`UNSUPPORTED_TASK`、`UNKNOWN_STATION`、`UNKNOWN_OBJECT`、`LLM_UNAVAILABLE`、`INVALID_MODEL_OUTPUT`、`PARSE_TIMEOUT`、`TTS_FAILED`、`PLAYBACK_FAILED`、`TASK_SERVICE_UNAVAILABLE`、`CONFIRMATION_EXPIRED`、`REVISION_MISMATCH`、`CONTEXT_MISMATCH`、`ROBOT_BUSY`、`TASK_NOT_FOUND`、`DISPATCH_NOT_FOUND`、`RECORD_NOT_FOUND`、`DISPATCH_UNKNOWN`、`TASK_ALREADY_STARTED`、`TASK_ALREADY_FINISHED`、`DEPENDENCY_UNAVAILABLE`、`STALE_DATA`、`NAVIGATION_FAILED`、`GRASP_FAILED`、`PLACE_FAILED`、`EXECUTION_TIMEOUT`、`CANCEL_NOT_CONFIRMED`、`CANCELED`、`RECOVERY_REQUIRED`。

首版建议配置：输入有效期 15 秒、确认窗口 30 秒、Service 等待 3 秒、解析等待 30 秒、下发结果查询每秒一次最多 3 次。运行节点须将这些值作为 ROS 参数，采用同一配置；超过等待只表示结果未知，不能推断运动未开始。持久化失败、关键依赖异常时禁止执行。

既有交互、音频与任务事件 Topic 使用 Reliable、Volatile、KeepLast(10)。新增状态和标准传感器 Topic 的 QoS 见第 9～11 节。历史消息不替代持久化；事件缺失或恢复后走 QueryTask。模型推理、设备播放不得阻塞查询、取消、急停与界面刷新回调。

## 8. 验证与验收

编译命令见根目录 README。接口生成成功只验证类型及依赖，不证明节点功能或真实硬件可用。

后续节点至少验证以下场景：

| 场景 | 必须满足 |
|---|---|
| 正常输入 | 各回复 ID 对应、时间有效，success/message/error_code 一致 |
| 无语音、识别失败或格式错误 | 返回明确状态和原因，不解析、不准备、不执行 |
| 缺参或非法模型输出 | 澄清或拒绝，不生成运动任务 |
| 同输入重放、重复请求与内容冲突 | 复用原记录或拒绝，不重复执行 |
| 旧上下文、旧版本、过期确认、时钟跳变 | 拒绝执行，可查询原因 |
| 机器人忙碌或并发确认 | 最多接受一个运动任务 |
| Goal 被拒绝或响应丢失 | 查询下发记录，不等待不存在的 Result，不换 ID 自动重发 |
| 取消尚未停稳 | 仍为 CANCELING，不提前宣告 CANCELED |
| 播报失败或取消 | 返回实际结果，不把合成完成当播放完成 |
| 节点重启、事件重复或迟到 | 查询快照、按序去重，终态不回退 |

ROS 2 类型组织与生成配置参考官方 [Humble 自定义消息／服务教程](https://github.com/ros2/ros2_documentation/blob/humble/source/Tutorials/Beginner-Client-Libraries/Custom-ROS2-Interfaces.rst)及 [Action 教程](https://github.com/ros2/ros2_documentation/blob/humble/source/Tutorials/Intermediate/Creating-an-Action.rst)。

与项目目录上层的 V1.0 草案相比，已统一 success/message、request_id 和 stamp；NO_SPEECH 有固定错误码，PrepareTask 明确确认上下文绑定。0.2.0 保留 0.1.0 的接口名称、字段类型和原有枚举数值，仅追加字段、枚举和接口，并更新 TaskSpec 的默认版本。ROS 2 类型定义发生变化，不保证二进制或线缆兼容；所有发布端、订阅端和服务／Action 客户端、服务端须同步重新构建，不能只更新服务端。

## 9. 可视化与标准数据接口

以下为本项目统一接入名称。已有 SLAM、Nav2、相机驱动的话题名称不同时，通过部署配置 remap 对接；本包不生成这些标准类型、不实现数据转发节点。`nav2_msgs`、`control_msgs`、`trajectory_msgs` 留给真正使用对应 Action 的业务包声明依赖，当前不复制导航或机械臂运动指令。

| Topic | 标准类型 | 数据与坐标约定 | 建议 QoS |
|---|---|---|---|
| `/map` | `nav_msgs/msg/OccupancyGrid` | SLAM／地图服务 → 界面；header.frame_id=`map`，占据值 -1 未知、0 空闲、100 占据，其他为概率值 | Reliable / TransientLocal / 1 |
| `/amcl_pose` | `geometry_msgs/msg/PoseWithCovarianceStamped` | AMCL → 界面；map 坐标系定位及协方差；使用 SLAM 定位时由其等价输出 remap 到本入口 | Reliable / Volatile / 10 |
| `/odom` | `nav_msgs/msg/Odometry` | 底盘里程计；header.frame_id=`odom`，child_frame_id=`base_link`；twist 按子坐标系解释 | BestEffort / Volatile / 5 |
| `/plan` | `nav_msgs/msg/Path` | 导航规划器 → 界面；map 坐标系路径，空 poses 清除旧路径 | Reliable / Volatile / 1 |
| `/tf` | `tf2_msgs/msg/TFMessage` | 动态变换 map→odom→base_link→机械臂／相机链 | Reliable / Volatile / 100 |
| `/tf_static` | `tf2_msgs/msg/TFMessage` | 固定外参；同一子坐标系只有一个权威父节点 | Reliable / TransientLocal / 1 |
| `/camera/image_raw` | `sensor_msgs/msg/Image` | USB 相机驱动 → 界面；真实 encoding、step、宽高，header.frame_id 为相机光学坐标系 | BestEffort / Volatile / 5 |
| `/camera/image_raw/compressed` | `sensor_msgs/msg/CompressedImage` | 可选 image_transport 压缩传输；format 与内容一致，不自定义字节流 | BestEffort / Volatile / 5 |
| `/camera/camera_info` | `sensor_msgs/msg/CameraInfo` | 相机内参、畸变、尺寸，与图像同一光学坐标系并按时间匹配 | BestEffort / Volatile / 5 |
| `/joint_states` | `sensor_msgs/msg/JointState` | 机械臂及可用轮关节的真实位置／速度／力矩；数组为空表示该项未知，否则长度与 name 一致 | BestEffort / Volatile / 5 |
| `/battery_state` | `sensor_msgs/msg/BatteryState` | 电压、电流、温度、电量；未知量按标准用 NaN，percentage 范围 [0,1] | BestEffort / Volatile / 5 |
| `/diagnostics` | `diagnostic_msgs/msg/DiagnosticArray` | 底盘、机械臂、SLAM、导航、相机、主机系统的标准诊断 | Reliable / Volatile / 10 |

使用标准 header.stamp；TFMessage 使用各 TransformStamped.header。位移单位米、角度弧度、速度米／秒及弧度／秒，四元数归一化；相机光学坐标 x 向右、y 向下、z 向前。界面按数据采集时间查询 TF，禁止把 odom 位姿当作 map 位姿。无 TF、未定位、地图不匹配或数据过期显示未知／不可用，不使用全零默认值冒充定位。

标准流没有 `success` 或 `request_id`，也不增加无意义的业务回执。其可用性通过 DiagnosticArray 和 ComponentStatus 报告。相机断开后旧帧必须标记过期；相机开启不表示已标定。图像不能以 Reliable 阻塞运动控制。订阅端 QoS 须与实际发布端兼容：例如 BestEffort 发布端不能匹配要求 Reliable 的订阅端；地图发布端若不提供 TransientLocal，须调整双方配置并另行保证首帧获取。

上述话题频率由驱动配置。界面默认 2 秒未更新的动态位姿、路径、图像、关节、电池和状态视为过期，路径可按规划器发布周期单独配置；地图和静态 TF 不按两秒失效，须结合定位／地图提供者健康状态。QoS 缓存不证明当前设备在线。

## 10. 运行、部件状态、错误与心跳

| Topic | 自定义类型 | 发布者与用途 | QoS |
|---|---|---|---|
| `/robot/status` | `RobotStatus` | 单一状态汇总节点 → 界面，机器人总体状态与活动任务 | Reliable / TransientLocal / 1 |
| `/robot/component_status` | `ComponentStatus` | 部件管理／驱动节点 → 汇总与界面，每条一个 component_id | Reliable / Volatile / 20 |
| `/safety/state` | `SafetyState` | 唯一安全管理节点 → 所有运动消费者及界面 | Reliable / TransientLocal / 1 |
| `/system/errors` | `ErrorReport` | 故障检测节点 → 界面／日志，错误发生、更新和解除事件 | Reliable / Volatile / 50 |
| `/system/heartbeat` | `NodeHeartbeat` | 各关键节点 → 监控节点，标识本次启动与活性 | Reliable / Volatile / 50 |

`RobotStatus`：stamp、source_node、state、active_task_id、active_dispatch_id、error_code、message。状态 UNKNOWN=0、IDLE=1、EXECUTING=2、STOPPING=3、ESTOP=4、FAULT=5、RECOVERING=6；无活动任务时两个 ID 为空。ESTOP 优先于 FAULT、STOPPING 和 EXECUTING；只有依赖已就绪且安全状态新鲜时才能 IDLE。它是展示汇总，不代替 SafetyState 或调度器执行许可。

`ComponentStatus`：stamp、source_node、component_id、state、enabled、error_code、message。component_id 使用固定标识 `chassis`、`arm`、`system`、`camera`、`localization`、`navigation`、`asr`、`llm`、`tts`；同一标识只有一个权威发布者。状态 UNKNOWN=0、STARTING=1、READY=2、BUSY=3、DEGRADED=4、FAULT=5、OFFLINE=6。enabled 仅表示部件使能，不代表允许运动。READY/BUSY 且无异常时错误码为空；未知、降级或故障须说明原因。实际关节、速度、硬件故障码、CPU／内存／温度等测量仍用标准话题和 diagnostics，不在这里重复编码。按 1 Hz 周期并在变化时立即发布，避免只缓存最后一个部件导致其他部件永远缺失。

`TaskSnapshot.progress`：float32，未知为 -1，已知范围 [0,1]。由调度器按执行步骤及真实反馈计算，不能根据耗时伪造；只在 SUCCEEDED 时为 1。失败／取消保留最后实际进度（未知仍为 -1）。TaskEvent 和 ExecuteTask Feedback 使用同一个快照，无需新增重复任务进度 Topic。相同 task_id 的 event_seq 跨重启严格递增，事件与快照的 stamp、task_id、event_seq 必须对应；终态后不再修改完成标志。

`ErrorReport`：stamp、source_node、boot_id、event_seq、error_id、request_id、task_id、dispatch_id、severity、active、error_code、message、recovery_required。severity 为 WARN=1、ERROR=2、FATAL=3；0 非法。error_id 在同一次故障的发生、更新、解除中保持不变，解除使用 active=false，保留原 error_code 和关联标识，不能把解除事件的错误码清空。无业务请求时关联 ID 为空。按 `(source_node, boot_id, event_seq)` 去重；event_seq 每次发布递增，重启更换 boot_id。恢复状态以新鲜 diagnostics、组件状态和 SafetyState 为准，事件流不作为当前全部故障清单；跨重启未解除故障重新报告。recovery_required 表示需要人工处置，解除该错误不自动恢复运动。

`NodeHeartbeat`：stamp、node_name（完全限定 ROS 节点名）、boot_id（每次进程启动的新 UUID）、sequence（每次心跳递增）、uptime（单调运行时长）、expected_period（正 Duration）、state、error_code、message。状态 UNKNOWN=0、STARTING=1、RUNNING=2、DEGRADED=3、STOPPING=4。默认周期 1 秒，监控端以本地单调接收时刻计算，3 秒未收到判为 HEARTBEAT_TIMEOUT；具体阈值按预期周期配置，范围由监控端限制，发送方不能声明无限等待。重复或倒退序号不刷新在线期限。新 boot_id 标记重启、使旧确认失效；退休 boot_id 的迟到消息不重新激活旧进程。心跳在线不等于设备就绪，关键节点缺失须禁止新执行并由安全管理策略停止已有运动。

状态、心跳和故障事件是遥测，不使用 `success`；正常状态错误码为空，异常状态非空，message 始终非空。它们没有原生请求，不强加 request_id；ErrorReport 和 SafetyState 的 request_id 仅在存在因果请求时填写。

## 11. 软件急停与复位

| Service | 类型 | 请求 | 响应 |
|---|---|---|---|
| `/safety/estop` | `SetEmergencyStop` | stamp、request_id、reason | stamp、request_id、success、message、error_code、safety |
| `/safety/reset` | `ResetEmergencyStop` | stamp、request_id、reason、expected_boot_id、expected_state_seq | stamp、request_id、success、message、error_code、safety |

`SafetyState` 完整字段：stamp、source_node、boot_id、state_seq、request_id、software_estop_latched、hardware_estop_known、hardware_estop_active、motion_inhibited（默认 true）、stopped_confirmed、reset_allowed、error_code、message。boot_id 每次安全管理节点启动更换；state_seq 每次**安全状态变化**递增，周期性重发同一状态不增加序号。初始状态不允许运动；hardware_estop_known=false 不能解释为硬件急停已释放。没有硬件检测能力时不得伪造 known=true，硬件安全策略须由部署方确认。request_id 为导致该次状态变化的请求 ID，无因果请求时为空；error_code 描述当前抑制原因，例如 ESTOP_ACTIVE，即使服务成功其嵌套 safety.error_code 仍可非空。

1. SetEmergencyStop 只置位软件锁存，不提供 `active=false` 旁路。请求 reason 非空；安全节点优先设置 motion_inhibited、锁存并下发停止，再返回 `success=true`。这只表示急停锁存已生效，不代表机器人已停稳，须检查 stopped_confirmed。重复请求幂等；旧激活请求也只能维持停止，不能解除安全锁。不能因急停时机器人忙碌而拒绝急停。
2. 界面必须显示真实 SafetyState；服务超时／断网表示结果未知，立即显示未确认并按原 ID 重试锁存，不能显示“机器人已停止”。软件服务不能代替独立硬件急停或安全认证回路。
3. 复位必须由操作者明确发起，携带刚审阅的 boot_id/state_seq。服务端原子校验相同状态、有效 ROS 时钟和请求新鲜度（默认 3 秒）、硬件急停已释放、停止已确认、关键依赖健康及无阻断故障；不满足分别返回 SAFETY_STATE_CHANGED、STALE_DATA、HARDWARE_ESTOP_ACTIVE、STOP_NOT_CONFIRMED、DEPENDENCY_UNAVAILABLE 或 RESET_NOT_ALLOWED。复位请求不能由 LLM 自动产生。
4. 复位只清除软件锁存；即使成功，也保留其他抑制条件，不恢复旧 Goal、旧导航或旧速度命令。急停时所有待确认上下文作废；活动任务进入安全停止，停稳后 FAILED 并记 ESTOP_ACTIVE，处置失败记 STOP_NOT_CONFIRMED，不能为急停伪造任务成功。重新执行须重新准备、确认。安全节点重启保持禁止运动，执行恢复检查后方可解除。
5. success=true 时服务顶层 error_code 为空；false 时非空。响应始终包含权威 safety；复位状态冲突也返回最新状态，界面重新展示，禁止自动换序号重试。重复相同 request_id/内容返回原逻辑结果，状态查询以 `/safety/state` 最新数据为准；同 ID 不同内容返回 REQUEST_ID_CONFLICT。
6. SafetyState 默认 5 Hz，并在变化时立即发布；运动消费者本地单调时钟超过 1 秒没有新接收、boot_id 改变、硬件状态未知或安全节点失联，一律保持／进入 motion_inhibited，不采纳缓存的“允许运动”。周期发布须更新 stamp；只有 stamp 严格递增、时钟域一致且按 ROS 时钟检查不超过 1 秒的新鲜消息才能刷新在线期限，相同 state_seq 可表示状态未变。退休 boot_id、倒退序号、旧时间戳和未来时间不能刷新期限；时钟跳变后重新进入安全恢复检查。map、组件和故障状态不能覆盖安全抑制。

追加错误码：`ESTOP_ACTIVE`、`HARDWARE_ESTOP_ACTIVE`、`STOP_NOT_CONFIRMED`、`RESET_NOT_ALLOWED`、`SAFETY_STATE_CHANGED`、`HEARTBEAT_TIMEOUT`、`COMPONENT_FAULT`、`LOCALIZATION_UNAVAILABLE`、`TF_UNAVAILABLE`、`CAMERA_UNAVAILABLE`、`VERSION_UNSUPPORTED`。固定业务码保持 string，硬件原始故障编号放 diagnostics 的 KeyValue，不把各厂商编号混作统一错误码。

## 12. 既有语音／任务接口补充约束与审查记录

| 发现的问题 | 处理与兼容性 |
|---|---|
| 无地图、定位、路径、视频的具体类型与 QoS | 第 9 节直接复用标准类型，不创建 Map／Pose／Image 重复类型 |
| 无机器人、机械臂／底盘状态与监控 | 增加 RobotStatus、ComponentStatus、ErrorReport、NodeHeartbeat；测量仍使用标准类型 |
| 无急停锁存、停止确认和防迟到复位 | 增加 SafetyState 与两个分离 Service，复位绑定安全实例和状态序号 |
| TaskSnapshot 有步骤却无进度 | 追加 progress，事件和 Action 继续共用快照 |
| DispatchReport 缺执行请求及上下文关联 | 追加 request_id、session_id、input_context_id，保持原决定枚举 |
| TaskDraft 缺准备请求关联 | 追加 request_id，指向成功准备请求 |
| 同一请求回执缺来源及操作名 | RequestStatus 追加 source_node、operation，区分多阶段输入及 Action 拒绝 |
| ASR 缺可选置信度及语言 | 追加 confidence（未知 -1）及 language（未知空），不新增识别成功判据 |
| 解析取消只能挤入 FAILED | 增加 CANCELED=4，不修改原枚举值 |
| 播报缺上下文、子播放关联和播放进度 | Speak Goal 追加 input_context_id；Feedback 追加 playback_request_id、segment_index、progress；Result 追加 played_duration；PlayAudio 追加播放帧数、总帧数和已播放时长 |
| InteractionState 无播报状态 | 追加 speaking、speech_request_id，防止播报尚未结束就确认 |
| 现有时间和任务 ID 看似重复 | 保留：包络 stamp 表示该次发布，嵌套 stamp 保留自身生成时间；包络 ID 与嵌套 ID 必须一致，不删除有校验用途的字段 |

`RecognizedText.confidence` 有效值 [0,1]，模型不提供时 -1，禁止填写虚构分数；language 使用如 `zh-CN` 的语言标签，未知为空。ASR 的 text 仍只保存真实最终识别文字，失败或静音不留旧文本。成功 text 不超过16384个字符，超过返回 INVALID_REQUEST，不截断成可能改变语义的任务。AudioSegment 的 capture_ended_at 不早于 capture_started_at，recognized_at 不早于录音结束，最终发布 stamp 不早于 recognized_at；采样时长按帧数／采样率校验。

`RequestStatus` 中 source_node 为实际受理节点、operation 为表中的公开 Topic／Action 名。相同音频 request_id 可关联 ASR 与后续业务过程；不同接收端的回执不能互相覆盖，界面按 `(request_id, source_node, operation)` 区分。每一条 RECEIVED 仅说明本节点受理，最终结果仍读取对应 Topic／Action。

`ParseTask` Goal 的 text、context、partial_candidate 和白名单沿用原字段；只有澄清续轮才能使用部分候选，不能混用别的 session/context。READY 必须 missing_fields 为空且 clarification_question 为空；NEED_CLARIFICATION 必须明确缺失字段与非空问题。CANCELED Result 使用 outcome=CANCELED、success=false、error_code=CANCELED，ROS 状态为 CANCELED。取消后迟到推理结果丢弃。Feedback stage 仅 QUEUED／INFERENCING／VALIDATING，不添加无依据的推理百分比。

确认仍由现有 ExecuteTask Goal 完成，不另设一个会与之产生双重授权的确认 Service。session_id 必须等于准备任务来源会话；input_context_id 必须等于 PrepareTask 返回的 confirmation_context_id，而非 source_context_id。confirmed_at 在准备与到期之间，服务端执行时再次检查未到期及 SafetyState 新鲜、无急停、关键部件可用。TaskSpec.interface_version 必须为 0.3.1，不支持返回 VERSION_UNSUPPORTED。PrepareTask 响应中的任务、revision、确认上下文与 TaskDraft 保持完全一致。

CancelTask.reason 必填，task_id 必须唯一指定；取消可与急停并发但不能清除急停。ExecuteTask 的 Result 与 Feedback 保持原字段，task.task.task_id 和包络 task_id 对齐，task.active_dispatch_id 与 dispatch_id 对齐；Result 中的成功／失败与最终快照一致。反馈 progress 只取嵌套快照，不另增重复字段。QueryTask 在任务失败、急停后仍能查询且不得被模型或硬件等待阻塞。

`Speak` 的 input_context_id 与 session_id 固定于 Goal，终止后客户端必须核对当前交互上下文，旧播报成功不得打开新确认窗口。voice 空值选择默认音色。Result.played_duration 是实际已播放片段时长总和；失败或取消仍可非零，不包含合成／排队耗时。Feedback.segment_index 从 0 开始，为当前串行 PlayAudio 片段；合成时 playback_request_id 为空。progress 为整段播报真实进度 [0,1] 或未知 -1，不允许把当前片段进度冒充整体完成度。所有片段确实播完才 success=true；活动子播放停止确认后才返回 CANCELED。

`PlayAudio` 的一帧是所有声道的一个采样组，total_frames = len(data)/(channels*2)，played_frames 不大于 total_frames；Result.played_duration = played_frames/sample_rate 秒，Duration 的 nanosec 归一化。完整播放才成功；失败、取消返回实际帧数和时长，不把提交给音频设备等同于播放完成。队列阶段已播帧数为 0。长文本仍切成不超过 10 秒的 PCM 片段串行播放；音频格式错误／空数据直接拒绝并通过 RequestStatus 说明。丢失播放结果显示未知，不自动重播以免重复提示。Speak／PlayAudio 的取消 Result 均 success=false、error_code=CANCELED，错误码和非空 message 在所有终态必须填写。

## 13. 接口与 AI 职责、文件任务交接

ai_interface 仅接收、验证传输格式、保存 WAV、打包并交付；ai_edge 负责读取文件、ASR、识别内容校验、语义解析、白名单校验和识别结果保存。`audio_pipeline.py` 已迁移至 ai_edge；接口侧只保留 `audio_forwarder.py`，不依赖 ActionClient、RecognizedText 或 TaskCandidate。

### 13.1 ProcessAudio：接口端 → AI 端

Request 完整字段：stamp（保留 AudioSegment 来源生成时间）、request_id、session_id、segment_id、input_context_id、capture_started_at、capture_ended_at、sample_rate、channels、encoding、audio_path。音频内容由已经写完并关闭的 WAV 承载，不在服务中重复传 PCM。audio_path 必须为 AI 端可读的绝对路径，双方共享文件目录；它不是跨机器文件上传协议。

Response.receipt 为 RequestStatus，包含 stamp、request_id、success、message、error_code、stage、source_node、operation。operation=/ai/process_audio，source_node 为 AI 接收节点。success=true、RECEIVED 只表示入队受理（含已登记的重复输入），不表示 ASR 或语义完成；拒绝使用 false、REJECTED 和具体错误。AI 服务端也发布同一受理回执到 /ai/request_status，接口端仅记录响应，不重复发布。

AI 接收入口：`ros2 run ai_edge audio_processing_node`。audio_root 默认 received_audio，相对启动目录解析；必须配置为共享音频根目录。接收端校验真实文件不超10 MiB、位于 audio_root 内、为 16000 Hz／单声道／16 位／未压缩 WAV、帧数不超4800000、字节完整，元数据与文件一致，录音起止时间有效且与时长相符（容差 50 ms）。拒绝目录外路径和缺失、截断文件，返回 FILE_NOT_FOUND 或 INVALID_AUDIO_HANDOFF。录音源、请求、会话和上下文 ID 必填。

接口端参数 auto_forward 默认 true，false 时只保存文件。发现 AI 服务及等待受理响应各最多 3 秒，使用非阻塞 future 与单调时钟；发送队列最多 10 项。失败返回 DEPENDENCY_UNAVAILABLE、FORWARD_QUEUE_FULL、FORWARD_TIMEOUT、FORWARD_FAILED 或 INVALID_AI_RECEIPT，不自动重试、不删除 WAV。超时表示受理未知，不能据此认定 AI 未开始处理。

### 13.2 AI 内部：文件 ASR → 语义解析

ai_edge 的 AudioPipeline 调用 /ai/recognize_audio，再调用 /ai/parse_task；接口节点不参与识别内容处理。RecognizeAudio Request 为 stamp、request_id、session_id、segment_id、input_context_id、capture_started_at、capture_ended_at、audio_path。Response.result 复用 RecognizedText。AI 模型服务应读取真实文件、运行真实 ASR，原样回传关联 ID 与采集时间，并填写实际识别时间、success/message/error_code/status/text/confidence/language；缺文件或格式不符分别报告 FILE_NOT_FOUND／AUDIO_FORMAT_UNSUPPORTED。

AI 编排验证关联字段、时间顺序和状态组合，只有 SUCCESS、success=true、非空文本、空错误码才推进语义解析。confidence 为 -1 或 [0,1]，recognized_at 不早于录音结束，stamp 不早于 recognized_at。合法 ASR 结果由 AI 发布到 /ai/asr_text，文字写同名 .txt；静音／失败不会进入解析。

ParseTask Goal 保留来源 request_id/session_id/input_context_id，input_id=audio:+segment_id，传入 AI 节点配置的 allowed_station_ids／allowed_object_ids。首次解析的历史和部分候选为空；NEED_CLARIFICATION 后，音频编排按 session_id/input_context_id 保存待补充候选，续轮传入 context 与 partial_candidate。AI 编排验证结果来源和 ROS Action 状态；READY 还须校验任务字段与白名单，NEED_CLARIFICATION 的 missing_fields 必须与候选实际缺项一致。空白名单不接受完整候选。实际结果写同名 .parse.json，包含关联 ID、时间、outcome、候选、缺失字段与澄清问题。不会自动调用准备或执行任务。

AI 侧服务发现和 Action Goal 接受各等 3 秒，asr_timeout 默认185秒、parse_timeout 默认300秒、范围 (0,300]。超时不推进后续阶段、不自动重试；解析超时请求取消，但取消结果仍未确认。最多 10 个活动／排队任务。按请求和来源登记最多 1024 个进程内指纹，重复不重新处理、内容冲突拒绝，满时返回 RECOVERY_REQUIRED；去重非持久化，节点重启不扫描旧文件，正式任务执行前仍须原有持久化去重与显式确认。

各阶段结果均由 AI 在 /ai/request_status 回报，对应 operation=/ai/recognize_audio 或 /ai/parse_task；NEED_CLARIFICATION 以 false/MISSING_FIELDS 表示尚不可继续。ASR_TIMEOUT、ASR_RESULT_MISMATCH、INVALID_ASR_RESULT、PARSE_GOAL_REJECTED、PARSE_RESULT_MISMATCH、PIPELINE_BUSY、PIPELINE_FAILED 归 AI 侧阶段错误。接口端只判断任务交接是否被接受，不用 ASR 结果发起第二次解析。

ASR 已通过 FunASR/SenseVoiceSmall 实现并完成本地真实推理验证；真实 LLM 适配已由第 15 节的 Ollama/qwen3.5:2b 提供，不提供虚构识别或语义结果。启动方法与共享目录参数见 README。

## 14. 真实 ASR 服务与可视化接口

RecognizeAudio 保持原字段，asr_node 提供真实实现。FunASR 在独立线程加载、推理；服务加载中返回 FAILED/ASR_NOT_READY，加载失败返回 ASR_MODEL_UNAVAILABLE，依赖无法导入返回 ASR_DEPENDENCY_MISSING（模型健康中报告）。存在活动推理返回 ASR_BUSY；默认180秒超时返回 ASR_TIMEOUT，线程实际完成前仍不受理新推理。请求路径在 audio_root 内，WAV 格式和采集元数据继续按第 13 节校验；缺文件返回 FILE_NOT_FOUND，格式不符返回 AUDIO_FORMAT_UNSUPPORTED。

实际文字返回 SUCCESS/true、空错误码；全零 PCM、模型 nospeech 标记或无有效文字返回 NO_SPEECH/false、空 text；推理异常返回 FAILED/ASR_FAILED。SenseVoice 语言／情绪／事件标签不属于用户语句，会从 text 去除，实际识别词句不改写。超过16384字符返回 ASR_OUTPUT_TOO_LONG，不截断。confidence 未提供时为 -1，language 尽量由模型标签确定。模型成功结果仅由编排器发布 /ai/asr_text，避免服务端和编排器重复广播。

模型健康复用 /robot/component_status 的 ComponentStatus，component_id=asr，按 1 Hz 周期及加载完成时发布 STARTING/READY/BUSY/FAULT；节点心跳复用 /system/heartbeat 的 NodeHeartbeat。此处的就绪仅表示 ASR 模型可用，不是机器人运动许可。

新增 /ai/audio_state（AudioProcessingState）、/ai/parse_result（TaskParseReport）、/ai/query_audio（QueryAudio）。阶段中保留 request/session/segment/context、文件路径、operation、source_node、boot_id、event_seq。事件序号在本进程的同一请求内递增，重启更换 boot_id；快照、识别与解析只在内存保留，最多与去重登记相同的 1024 个请求。Topic 为 Reliable/Volatile/KeepLast(10)，晚加入或缺失事件须通过 QueryAudio 查询，不用一条缓存状态代替所有任务。

QueryAudio Request：stamp、request_id（本次查询）、target_request_id（待查音频请求）。Response：stamp、request_id、success/message/error_code、found、state、asr_available/asr、parse_available/parse。成功仅表示找到处理记录，即使该记录识别失败；无记录返回 AUDIO_NOT_FOUND，缺 ID 返回 INVALID_REQUEST。found=false 或 available=false 的默认嵌套字段不可使用。录音交接因格式错误而未入 AI 队列时没有快照，查看 RequestStatus 的拒绝原因。

阶段：QUEUED=0、WAITING_ASR=1、RECOGNIZING=2、WAITING_PARSE=3、PARSING=4、READY=5、NEED_CLARIFICATION=6、FAILED=7、CANCELED=8、NO_SPEECH=9、ASR_COMPLETED=10。READY 是语义候选完整，不是已经准备或执行；ASR_COMPLETED 仅在 enable_semantic=false 时表示本轮 ASR 完成。enable_semantic 默认 true；仅验收 ASR 时使用 false，完整语义步骤见第 15 节。

TaskParseReport 复用 ParseTask Result 的实际字段与 outcome 数值，用于被动订阅，不改变 Action 定义，也不是 TaskDraft。模型失败／澄清仍可得到合法的 false 语义报告；畸形或来源不匹配结果只发布阶段失败，不伪造候选。

具体 UI 对接、命令和交互约束见《可视化交互组_音频接口.md》。UI 只显示、请求录音及查询，不在订阅识别结果时重复触发 ASR、语义或机器人执行。

## 15. Ollama 千问 2B 语义节点

`ai_edge/parse_task_node` 实现现有 `/ai/parse_task` Action，默认模型 `qwen3.5:2b`。FunASR 仍负责语音转文字；该节点只接受文字，生成单个导航／搬运或 SEQUENCE 有序列表候选。0.3.0 的新增字段见前述说明，原枚举编号保留，ai_interface 不调用模型。

Goal 输入限制：四个来源标识非空、各不超过 256 字符；text 1～16384字符；context 最多 20 条，text 与历史总计不超过24000字符；白名单各最多 128 个去重、无首尾空格的非空 ID，每个 ID 最多 128 字符。最终提示词（含 schema、示例、历史和白名单）UTF-8 编码不超过16000字节，为32768 token上下文和输出预留余量，超限返回 INVALID_REQUEST。partial_candidate 只允许在显式历史的同一会话上下文中续轮，调用方负责历史归属。音频编排的进程内待澄清缓存最多 32 个上下文、默认等待 300 秒；只保存最近 6 条且合计不超过 800 个 UTF-8 字节的历史，完整候选另存。提问前开始的音频不作为回答，续轮不能改写已知字段；取消、重新开始或 READY 后清除对应缓存。重启后不恢复待补充任务，详见[多轮任务澄清](多轮任务澄清.md)。

Ollama `/api/chat` 使用 stream=false、think=false、temperature=0 和 JSON schema。模型输出再次接受独立字段类型、白名单、任务互斥和必填检查；不以 schema 约束代替业务校验。程序产生结果中的时间戳和所有关联 ID，模型无法修改它们。缺少 ID 留空并返回 NEED_CLARIFICATION/MISSING_FIELDS；不支持的任务使用 UNSUPPORTED/UNSUPPORTED_TASK。完整候选 READY 只表示可以进入准备流程，不代表已确认、已准备或已执行。

QUEUED、INFERENCING、VALIDATING 使用既有 Feedback；READY 与 NEED_CLARIFICATION 对应 SUCCEEDED，UNSUPPORTED 与 FAILED 对应 ABORTED，取消对应 CANCELED。Goal 参数不合法或已有推理时直接拒绝，并通过 /ai/request_status 发布 REJECTED、原 request_id、source_node 与 operation=/ai/parse_task，不伪造 Action Result。

参数：model 默认 qwen3.5:2b；ollama_url 默认 http://127.0.0.1:11434；request_timeout 默认290秒，范围 (0,290]。编排 parse_timeout 默认300秒。节点并发上限 1，后台线程执行 HTTP；取消／超时立即结束 ROS 等待，底层网络返回前保留忙碌槽位，迟到结果丢弃，不自动重试或自动下载模型。节点启动日志只表示 Action 已提供，不表示权重已加载；首个请求可能触发 Ollama 冷加载。

错误码沿用 LLM_UNAVAILABLE、INVALID_MODEL_OUTPUT、UNKNOWN_STATION、UNKNOWN_OBJECT、MISSING_FIELDS、UNSUPPORTED_TASK、INVALID_REQUEST、PARSE_TIMEOUT、CANCELED；新增 LLM_MODEL_UNAVAILABLE（HTTP 404，常见为模型未安装）与 LLM_BUSY（活动推理未完成）。错误发生后仍可处理后续请求。

单独调用文字 Action 只返回 Feedback/Result；音频编排统一保存 .parse.json，并通过已有 /ai/parse_result、/ai/audio_state 和 /ai/query_audio 提供可视化输出，不重复订阅 ASR 或创建另一条处理链。节点不调用 PrepareTask、ExecuteTask，不执行模型给出的底层控制内容。
