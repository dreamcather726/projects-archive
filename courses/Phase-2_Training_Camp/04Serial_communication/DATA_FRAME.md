# 固定二进制串口数据帧

## 1. 协议格式

正式设备通信统一使用 6 字节固定帧：

```text
55 05 CMD DATA CHECKSUM FF
```

| 字节位置 | 字段 | 说明 |
|---:|---|---|
| 0 | 帧头 | 固定为 `0x55` |
| 1 | 帧长度 | 固定为 `0x05` |
| 2 | 指令类型 | 表示 LED、歌曲、呼吸灯等功能 |
| 3 | 指令数据 | 一个数据字节，范围 `0x00～0xFF` |
| 4 | 校验位 | 8 位加法校验 |
| 5 | 帧尾 | 固定为 `0xFF` |

`0x05` 表示帧头之后还有 5 个字节：长度、指令、数据、校验和帧尾。
因此整帧共有 `1 + 5 = 6` 个字节。

## 2. 加法校验

校验规则统一为：

```text
CHECKSUM = LENGTH + CMD + DATA，只保留低 8 位
```

帧头和帧尾不参与计算。结果超过 `0xFF` 时去掉进位。

用户给出的示例：

```text
55 05 01 FF 校验位 FF
```

计算过程：

```text
0x05 + 0x01 + 0xFF = 0x105
0x105 去掉进位后得到 0x05
```

所以完整数据帧是：

```text
55 05 01 FF 05 FF
```

协议最重要的是发送端、接收端和文档使用完全相同的校验范围。

## 3. 指令类型和指令数据

| 指令类型 | 数据 | 功能 |
|---:|---:|---|
| `0x01` | `0x00～0xFF` | 设置 LED PWM 亮度 |
| `0x02` | `0x01` | 播放《两只老虎》 |
| `0x02` | `0x02` | 播放《小星星》 |
| `0x03` | `0x00 / 0x01` | 停止/启动呼吸灯 |
| `0x04` | `0x02～0x64` | 设置呼吸灯每步延时 2～100 ms |
| `0x05` | `0x00` | PING 通信测试 |
| `0x7F` | 错误码 | 错误应答 |
| `0x81～0x85` | 状态数据 | 对相应指令的成功应答 |

指令类型和指令数据必须组合解释。例如 `02 01` 与 `03 01` 的数据都是
`01`，但前者表示歌曲 1，后者表示启动呼吸灯。

## 4. 完整数据帧示例

| 数据帧 | 功能 |
|---|---|
| `55 05 01 FF 05 FF` | LED 亮度 255 |
| `55 05 01 00 06 FF` | LED 关闭 |
| `55 05 02 01 08 FF` | 播放《两只老虎》 |
| `55 05 02 02 09 FF` | 播放《小星星》 |
| `55 05 03 01 09 FF` | 启动呼吸灯 |
| `55 05 03 00 08 FF` | 停止呼吸灯 |
| `55 05 04 14 1D FF` | 呼吸灯每步延时 20 ms |
| `55 05 05 00 0A FF` | PING 测试 |

## 5. 发送数据帧

各正式实验使用相同的 `SerialFrame.h` 和 `SerialFrame.cpp`。头文件放函数声明，
源文件放具体实现。`.ino` 中只需要包含：

```cpp
#include "SerialFrame.h"
```

发送数据时调用：

```cpp
sendFrame(0x01, 0xFF);
```

`sendFrame()` 会自动填写帧头、长度、校验位和帧尾，最后调用：

```cpp
Serial.write(frame, FRAME_SIZE);
```

正式二进制帧必须使用 `write()`。`print(0x55)` 会把数值转换成文字
`85`，不是发送一个值为 `0x55` 的原始字节。

## 6. 接收数据帧

主程序只需读取解析后的指令和数据：

```cpp
if (readFrame()) {
  byte command = getFrameCommand();
  byte data = getFrameData();
}
```

这样不需要使用取地址或引用。`readFrame()` 按以下顺序工作：

1. 缓冲区少于 6 字节时先不读取，等待数据到齐。
2. 读取第一个字节，不是 `0x55` 就丢弃并继续寻找帧头。
3. 找到帧头后依次读取长度、指令、数据、校验和帧尾。
4. 检查长度是否为 `0x05`。
5. 检查帧尾是否为 `0xFF`。
6. 重新计算加法校验。
7. 全部正确后才把指令和数据交给主程序。

这个基础版本仍能等待被分开发送的数据，并能跳过正确帧前的干扰字节，但代码比状态机
版本更容易在课堂上逐行讲解。

## 7. 应答规则

成功应答的指令类型等于请求指令加 `0x80`：

| 请求 | 成功应答 |
|---:|---:|
| `0x01` | `0x81` |
| `0x02` | `0x82` |
| `0x03` | `0x83` |
| `0x04` | `0x84` |
| `0x05` | `0x85` |

例如 LED 亮度 255 执行成功后，应答：

```text
55 05 81 FF 85 FF
```

错误应答使用指令 `0x7F`：

| 错误码 | 含义 |
|---:|---|
| `0x01` | 不支持的指令 |
| `0x02` | 指令数据不合法 |

长度、校验或帧尾错误时直接丢弃，不发送应答，避免设备对线路噪声不断回复。

## 8. 为什么不能收到数据就立即执行

串口没有“整帧到达”提示。一条 6 字节数据帧可能被拆成几次收到，两条帧也可能
连续进入缓冲区。因此程序必须先保存、校验，再执行。

正确顺序：

```text
寻找帧头 → 检查长度 → 收满整帧 → 检查帧尾
→ 检查校验 → 检查数据范围 → 执行指令 → 发送应答
```

任何一步失败都不能执行外设动作。

## 9. 工程使用规则

1. 发送端和接收端必须使用同一版本的协议和指令表。
2. 校验正确后仍要检查指令是否存在、数据是否在安全范围。
3. 发送端收到成功应答前，不能默认指令已经执行。
4. 实际项目应设置应答超时和有限次数重发，禁止无限重发。
5. 控制电机、加热器等负载时，通信失败必须进入预先规定的安全状态。
6. 可以统计未知指令、校验错误和超时次数，便于故障诊断。

## 10. 加法校验的能力边界

加法校验计算简单，适合课堂手算和本协议要求，也能发现许多单字节错误。但不同位置的
错误可能互相抵消，检测能力弱于 CRC。

可靠性要求更高时，可以保留现有帧结构，把校验升级为 CRC-8 或 CRC-16，并增加设备
地址、协议版本、帧序号、应答超时和重发次数限制。
