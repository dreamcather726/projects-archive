# 实验 2：自定义传感器状态消息与安全监控

## 1. 实验目标与最终效果

本实验不是只把两个节点“运行起来”，而是建立一条可以被观察、验证和故障注入的完整数据链路：

```text
0.5 秒定时器
    ↓
sensor_publisher ── /sensor/status ──> safety_monitor
    发布完整采样                         判断数值异常
    计算状态码                           检测数据超时
              ↘ ros2 topic 工具 ↗
                 观察和诊断
```

完成后应能看到以下效果：

- `sensor_publisher` 每 0.5 秒发布一次，即理论频率约为 2 Hz。
- 四组距离和温度循环出现，状态依次为正常、警告、危险、危险。
- `safety_monitor` 收到每条消息并按状态码输出不同级别日志。
- 第三个终端能查看消息定义、端点、QoS、消息值、频率和带宽。
- 停止发布者后，监控节点在约 1.5～2.0 秒后报告一次“数据超时”。

## 2. 为什么要做这个实验

机器人传感器通常不只产生一个数值，还需要同时表达采样时间、坐标系、数据来源和状态。若分别使用 `/distance`、`/temperature`、`/status` 三个 `Float32` 或整数话题，接收端很难证明三条消息属于同一次采样，启动和丢包时还可能错配。

自定义 `SensorStatus` 把同一次采样的字段放进一条消息，使它们共享同一个时间戳。这个设计会直接影响后续的 rosbag 记录、多传感器同步、可视化、故障诊断和跨语言节点通信。

本实验还专门区分两种故障：

- **数据内容异常**：消息持续到达，但距离过近或温度过高。
- **数据新鲜度异常**：最后一条消息可能完全正常，但传感器已经停止更新。

实际机器人中，第二种故障往往更危险。订阅回调只有在新消息到达时才执行，所以必须另设定时器作为软件看门狗。

## 3. 实验文件与每个文件的作用

```text
ros2_ws/src/
├── sensor_interfaces/
│   ├── msg/SensorStatus.msg       # 消息字段与常量，是通信协议
│   ├── CMakeLists.txt             # 调用 rosidl 生成各语言接口代码
│   └── package.xml                # 声明生成期、运行期及 std_msgs 依赖
└── sensor_monitor_py/
    ├── sensor_monitor_py/
    │   ├── sensor_publisher.py    # 产生模拟数据并发布
    │   └── safety_monitor.py      # 订阅、分类告警、检查超时
    ├── setup.py                   # 注册两个 ros2 run 可执行入口
    ├── setup.cfg                  # 指定脚本安装位置
    └── package.xml                # 声明 rclpy 和接口包运行依赖
```

把接口包与业务包分开后，其他 Python 或 C++ 节点也能依赖同一接口，而不必依赖这个模拟发布器。`.msg` 不是运行时直接读取的配置文件；构建时会根据它生成 Python 类和底层类型支持，所以修改后必须重新构建。

## 4. 消息定义逐行解释

文件 `sensor_interfaces/msg/SensorStatus.msg`：

```text
std_msgs/Header header
string source
float32 distance_m
float32 temperature_c

uint8 STATUS_OK=0
uint8 STATUS_WARNING=1
uint8 STATUS_DANGER=2
uint8 status
```

| 定义 | 含义 | 为什么需要 |
|---|---|---|
| `std_msgs/Header header` | 嵌套一个含时间戳和坐标系名的标准消息 | 让一次采样具备“何时、在哪个坐标系”的语义 |
| `string source` | 数据源名称 | 多传感器或多机器人中用于区分来源 |
| `float32 distance_m` | 距离，单位米 | 字段名携带单位，避免米和厘米混用 |
| `float32 temperature_c` | 温度，单位摄氏度 | 与距离一起构成同一次采样 |
| `STATUS_OK=0` | 状态常量：正常 | 发布和订阅端共享同一数字含义 |
| `STATUS_WARNING=1` | 状态常量：警告 | 避免业务代码中散落无法解释的数字 `1` |
| `STATUS_DANGER=2` | 状态常量：危险 | 后续添加其他语言节点时仍保持一致 |
| `uint8 status` | 每条消息实际携带的状态码 | 值应与前三个常量的约定对应 |

注意，前三个 `STATUS_...` 是常量，不是每条消息中三个额外字段。`ros2 topic echo` 会把 `status` 打印成 `0`、`1` 或 `2`，不会自动显示常量名称。

## 5. 代码运行逻辑

### 5.1 发布者如何产生数据

发布者创建代码：

```python
self._publisher = self.create_publisher(
    SensorStatus, '/sensor/status', qos_profile_sensor_data
)
```

三个参数分别是：

- `SensorStatus`：消息类，决定话题类型为 `sensor_interfaces/msg/SensorStatus`。
- `/sensor/status`：绝对话题名；开头 `/` 表示不随节点命名空间改变。
- `qos_profile_sensor_data`：传感器数据 QoS 预设，偏向低延迟和最新数据。

定时器代码：

```python
self._timer = self.create_timer(0.5, self._publish_sample)
```

- `0.5` 是周期，单位秒，不是频率。理论频率为 `1 ÷ 0.5 = 2 Hz`。
- `self._publish_sample` 是回调函数对象，不能写成 `self._publish_sample()`，否则会在构造节点时立即调用。
- 定时器只让回调周期性具备执行机会，并不提供硬实时保证，所以要用 `ros2 topic hz` 实测。

四组模拟数据和判断结果如下：

| 距离 | 温度 | 命中条件 | 状态值 | 监控结果 |
|---:|---:|---|---:|---|
| 1.80 m | 31.0 ℃ | 均未越限 | 0 | 正常 |
| 0.90 m | 44.0 ℃ | 距离 `< 1.00` 或温度 `> 40.0` | 1 | 警告 |
| 0.35 m | 38.0 ℃ | 距离 `< 0.50` | 2 | 危险 |
| 1.20 m | 63.0 ℃ | 温度 `> 60.0` | 2 | 危险 |

代码先判断危险，再判断警告。这一顺序很重要：`0.35 < 1.00` 同时满足警告条件，但更严重的危险分支先执行，所以最终状态是危险。

每条消息还会设置：

- `header.stamp`：使用节点 ROS 时钟记录发布时间；启用仿真时间后可跟随 `/clock`。
- `header.frame_id = 'front_laser'`：说明距离数据在前激光坐标系下表达。
- `source = 'simulated_front_sensor'`：说明数据来自本实验的模拟前向传感器。

### 5.2 监控节点如何判断异常

订阅者使用与发布者相同的类型、话题名和传感器 QoS。消息到达时 `_on_status()`：

1. 记录本节点收到消息的时间。
2. 清除此前的超时报告状态。
3. 根据 `status` 选择 `info`、`warning` 或 `error` 日志。

监控节点另有一个 0.5 秒定时器调用 `_check_timeout()`。如果距离最后一次接收已经超过 1.5 秒，它输出一次错误，并用 `_timeout_reported` 防止每 0.5 秒重复刷屏。

因此停止发布者后，报警不一定恰好在 1.500 秒出现。看门狗每 0.5 秒检查一次，叠加调度误差后，通常会在约 1.5～2.0 秒观察到。

## 6. 构建实验：每条命令的作用和效果

在第一个终端执行：

```bash
source /opt/ros/jazzy/setup.bash
cd <课程仓库>/ros2_course/unit_02_topics_and_messages/experiments/01_sensor_status/ros2_ws
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install
source install/setup.bash
```

### 6.1 `source /opt/ros/jazzy/setup.bash`

把 ROS 2 Jazzy 的命令、包索引和环境变量加载到当前 Shell。成功时通常没有输出。可用下面的命令验证：

```bash
ros2 --help
printenv ROS_DISTRO
```

第二条应输出 `jazzy`。每个新终端都是独立环境，所以每开一个终端都要重新 source。

### 6.2 `cd <...>/ros2_ws`

进入包含 `src` 的 colcon 工作空间根目录。尖括号是占位符，不要原样输入。执行后可用 `pwd` 验证当前位置，用 `ls src` 应看到 `sensor_interfaces` 和 `sensor_monitor_py`。

### 6.3 `rosdep install --from-paths src --ignore-src -r -y`

这条命令读取包清单并安装缺失的系统依赖：

- `--from-paths src`：扫描 `src` 下的包。
- `--ignore-src`：工作空间源码中已经存在的包不再从系统安装。
- `-r`：某个依赖失败时继续检查其余依赖，并在最后报告结果。
- `-y`：安装时自动回答 yes，适合已经确认依赖内容的课程环境。

全部依赖已有时，常见结果是提示依赖已成功安装。若提示 rosdep 尚未初始化、软件源不可用或缺少权限，应先解决该错误，不能假设后续构建一定成功。

### 6.4 `colcon build --symlink-install`

构建工作空间中的两个包：

- `build/`：构建过程的中间文件。
- `install/`：生成的消息类型、Python 包和可执行入口。
- `log/`：构建日志。
- `--symlink-install`：对 Python 等可链接资源使用符号链接，修改 Python 源文件后通常不用每次复制安装；但修改 `.msg` 或构建元数据仍必须重新构建。

成功结尾类似：

```text
Starting >>> sensor_interfaces
Finished <<< sensor_interfaces [...]
Starting >>> sensor_monitor_py
Finished <<< sensor_monitor_py [...]

Summary: 2 packages finished [...]
```

接口包应先于依赖它的 Python 包完成。出现 `Failed <<<` 或 `Aborted <<<` 时构建未成功，应查看其上方第一处错误，而不是只看最后一行。

### 6.5 `source install/setup.bash`

把本次构建结果叠加到当前终端环境。成功时通常没有输出。验证方法：

```bash
ros2 pkg prefix sensor_interfaces
ros2 pkg executables sensor_monitor_py
```

前者应指向当前工作空间的 `install`，后者应列出：

```text
sensor_monitor_py safety_monitor
sensor_monitor_py sensor_publisher
```

`ros2 run` 后的两个位置参数分别是：

日志前通常还有时间戳，具体格式可能因环境而异。看到日志只能证明发布回调已运行并调用了 `publish()`，不能单独证明订阅者已经收到。

### 7.2 终端 2：启动监控节点

```bash
source /opt/ros/jazzy/setup.bash
cd <实验目录>/ros2_ws
source install/setup.bash
ros2 run sensor_monitor_py safety_monitor
```

预期随发布数据循环看到：

```text
[INFO] [safety_monitor]: 传感器状态正常
[WARN] [safety_monitor]: 警告：距离=0.90 m, 温度=44.0 C
[ERROR] [safety_monitor]: 危险：simulated_front_sensor 距离=0.35 m, 温度=38.0 C
[ERROR] [safety_monitor]: 危险：simulated_front_sensor 距离=1.20 m, 温度=63.0 C
```

若发布者有日志而监控节点始终没有日志，依次检查：

1. 两个终端是否都 source 了相同 ROS 发行版和工作空间。
2. `ROS_DOMAIN_ID` 是否一致。
3. `ros2 topic info /sensor/status --verbose` 是否发现两端。
4. 类型和 QoS 是否一致。
5. 监控进程是否仍在运行、有无 Python 异常。

## 8. 第三个终端：逐项验证，而不是只“跑命令”

先准备环境：

```bash
source /opt/ros/jazzy/setup.bash
cd <实验目录>/ros2_ws
source install/setup.bash
```

### 8.1 验证接口结构

```bash
ros2 interface show sensor_interfaces/msg/SensorStatus
```

参数 `sensor_interfaces/msg/SensorStatus` 由“包名/接口类别/接口名”三部分构成。命令会展示 `.msg` 结构及嵌套类型的说明；它不要求发布者正在运行。

验证重点：四个可变业务字段和三个状态常量是否存在。若刚修改过 `.msg`，这里仍显示旧结构，说明尚未重新构建或当前终端尚未重新 source。

### 8.2 验证话题名称与类型

```bash
ros2 topic list -t
ros2 topic type /sensor/status
```

`list -t` 中应包含：

```text
/sensor/status [sensor_interfaces/msg/SensorStatus]
```

`type` 应输出：

```text
sensor_interfaces/msg/SensorStatus
```

`list -t` 适合发现全局情况，`type` 适合脚本或人工精确查询某个话题。话题存在只证明 ROS 图发现到了端点，不等于当前一定有消息流动。

### 8.3 验证端点和 QoS

```bash
ros2 topic info /sensor/status --verbose
```

参数说明：

- `/sensor/status`：要查询的最终话题名。
- `--verbose` 或 `-v`：显示每个端点的节点名、命名空间、GID 和 QoS；它是开关，不需要跟 `true`。
- `--no-daemon`：可选，绕过 `ros2 daemon` 缓存并直接查询；怀疑图信息没有及时刷新时使用。
- `--spin-time <秒>`：可选，直接查询时等待 DDS 发现的时间；例如 `--spin-time 1.0`。

需要绕过 daemon 时可执行：

```bash
ros2 topic info /sensor/status -v --no-daemon --spin-time 1.0
```

这些选项只改变 CLI 怎样取得图信息，不会改变发布者或订阅者本身的 QoS。完整选项以本机 `ros2 topic info --help` 输出为准。

本实验应至少看到：

```text
Type: sensor_interfaces/msg/SensorStatus
Publisher count: 1
Node name: sensor_publisher
Node namespace: /
Topic type: sensor_interfaces/msg/SensorStatus
Endpoint type: PUBLISHER
GID: ...
QoS profile:
  Reliability: BEST_EFFORT
  History (Depth): UNKNOWN
  Durability: VOLATILE
  Lifespan: Infinite
  Deadline: Infinite
  Liveliness: AUTOMATIC
  Liveliness lease duration: Infinite

Subscription count: 1
Node name: safety_monitor
Node namespace: /
Topic type: sensor_interfaces/msg/SensorStatus
Endpoint type: SUBSCRIPTION
GID: ...
QoS profile:
  Reliability: BEST_EFFORT
  History (Depth): UNKNOWN
  Durability: VOLATILE
  Lifespan: Infinite
  Deadline: Infinite
  Liveliness: AUTOMATIC
  Liveliness lease duration: Infinite
```

逐项含义：

- `Type`：话题使用的接口。两端都必须是完全相同的类型。
- `Publisher count: 1`：发现一个发布端点。若为 0，`echo` 不会收到新数据。
- `Node name`：拥有该端点的节点，可接着用 `ros2 node info /sensor_publisher` 深查。
- `Node namespace: /`：节点位于根命名空间，所以完整节点名是 `/sensor_publisher` 或 `/safety_monitor`。
- `Endpoint type`：说明这一组记录属于发布端还是订阅端。
- `GID`：DDS/RMW 端点的全局标识。每个端点不同是正常的；它主要供底层追踪，不是话题名，也不应写进代码。
- `Reliability: BEST_EFFORT`：尽力传递，可能丢个别样本但不因重传旧数据增加延迟，适合连续传感器流。
- `History (Depth): UNKNOWN`：当前命令和 RMW 没有报告出确定的历史/深度值，不表示深度为零。代码使用的传感器预设通常是 KEEP_LAST、深度 5。
- `Durability: VOLATILE`：只处理匹配建立后的新消息，新订阅者不会要求补发启动前的旧消息。
- `Lifespan: Infinite`：没有由 DDS 设置样本自动过期时间；业务代码仍可自行判定超时。
- `Deadline: Infinite`：没有声明 DDS 层的最大消息间隔。本实验的 1.5 秒超时由代码实现。
- `Liveliness: AUTOMATIC`：端点活跃性由中间件自动维护。
- `Liveliness lease duration: Infinite`：没有有限租约来自动判定失活，不等同于监控节点的 1.5 秒看门狗。
- `Subscription count: 1`：只运行监控节点时应为 1。开启持续 `echo` 后通常会暂时变为 2，因为 CLI 也创建了订阅者。

从这份输出应得出的核心判断是：发布者与订阅者都已被发现，而且两端显示的可靠性和持久性一致。若仍收不到数据，就要转向检查节点执行、回调异常、Domain ID 或网络，而不是只看话题名。

终端最后出现的 `tao@tao:~/...$` 是 Shell 提示符，表示命令已结束并等待下一条输入，不是 ROS 输出字段。

### 8.4 查看一条完整消息

```bash
ros2 topic echo /sensor/status --once
```

- `echo` 会创建临时订阅者并把消息转成可读文本。
- `/sensor/status` 是话题名。
- `--once` 表示收到一条后退出；不加时会持续打印，按 `Ctrl+C` 停止。

预期形态：

```yaml
header:
  stamp:
    sec: 1720000000
    nanosec: 123456789
  frame_id: front_laser
source: simulated_front_sensor
distance_m: 1.8
temperature_c: 31.0
status: 0
---
```

秒和纳秒值会随运行时间变化，第一条恰好是哪一组样本也不固定。应检查字段完整性和关系，而不是照抄具体数字。`---` 是消息分隔标记。

### 8.5 测量实际频率

```bash
ros2 topic hz /sensor/status
```

命令会持续订阅并统计，几秒后输出类似：

```text
average rate: 2.000
        min: 0.499s max: 0.501s std dev: 0.00100s window: 10
```

- `average rate`：观测窗口内平均接收频率，实验目标约 2 Hz。
- `min/max`：相邻消息周期的最小值和最大值，目标接近 0.5 秒。
- `std dev`：周期抖动的标准差，越大说明间隔越不稳定。
- `window`：当前统计使用的样本数量或窗口规模，不是 QoS 深度。

刚启动时样本少，数值波动较大。观察 5～10 秒后再判断，并用 `Ctrl+C` 结束。它测到的是 CLI 订阅端实际收到的频率；BEST_EFFORT 丢包或机器负载高时，可能低于发布定时器的理论值。

### 8.6 测量消息带宽

```bash
ros2 topic bw /sensor/status
```

它会持续估算接收带宽、平均消息大小和窗口消息数。具体数字受字符串长度、序列化和工具统计方式影响，本实验数据很小，重点是学会读结果。该值不一定包含完整 DDS/UDP 协议开销，因此不能直接当成网卡抓包流量。

带宽命令在后续图像和点云实验更重要：如果图像尺寸或帧率翻倍，带宽通常会显著增加，可能引起网络拥塞和丢帧。

## 9. 故障实验：主动改变系统再观察

### 9.1 停止发布者，验证数据超时

在终端 1 按 `Ctrl+C` 停止 `sensor_publisher`，保持终端 2 的 `safety_monitor` 运行。

预期变化：

1. 监控节点不再收到状态回调。
2. 约 1.5～2.0 秒后输出一次：

   ```text
   [ERROR] [safety_monitor]: 数据超时：已经 1.x 秒没有收到新消息
   ```

3. 因 `_timeout_reported` 为真，错误不会每 0.5 秒重复刷屏。
4. 再执行 `ros2 topic info /sensor/status --verbose` 时，发布者数量应变为 0，订阅者仍为 1。

这个实验说明 `VOLATILE`、`Lifespan: Infinite` 和业务超时是三件不同的事。消息中间件没有替程序设置 1.5 秒过期规则，是监控代码主动比较最后接收时间。

### 9.2 手动注入一条危险消息

保持原发布者停止、监控节点运行，在终端 3 执行：

```bash
ros2 topic pub --once /sensor/status sensor_interfaces/msg/SensorStatus \
  "{header: {frame_id: front_laser}, source: manual_test, distance_m: 0.2, temperature_c: 30.0, status: 2}"
```

参数含义：

- `pub`：创建临时发布者。
- `--once`：发布一条后退出。
- `/sensor/status`：目标话题。
- `sensor_interfaces/msg/SensorStatus`：必须与订阅端一致的类型。
- 最后的 YAML：构造消息字段。未填写的 `stamp` 使用默认零值。

预期监控终端输出一次来自 `manual_test` 的危险日志。它证明订阅和告警逻辑可以独立于原模拟发布者工作。

命令行发布者也需要与订阅者完成发现，因此 `--once` 可能不会瞬间退出。若把原发布者也保持运行，系统会短暂出现两个发布者，消息可能交错，这反而可以用来观察多发布者现象。

### 9.3 制造 QoS 不兼容并观察

本单元先做观察，不要求记住完整兼容矩阵。可以先查看本机 CLI 支持的 QoS 参数：

```bash
ros2 topic echo --help
```

在后续第 6 单元中，再使用 `--qos-reliability`、`--qos-durability` 等选项有控制地改变订阅端策略。实验时应同时保留 `info --verbose` 输出，建立“现象—端点配置—原因”的证据链。

## 10. 节点的 ROS 通用参数

`sensor_publisher.py` 和 `safety_monitor.py` 暂未声明业务参数，但所有 ROS 2 节点都能接收常见 ROS 通用参数。查看帮助：

```bash
ros2 run sensor_monitor_py sensor_publisher --ros-args --help
```

常用形式：

```bash
# 修改节点名
ros2 run sensor_monitor_py sensor_publisher \
  --ros-args -r __node:=front_sensor_publisher

# 重映射话题
ros2 run sensor_monitor_py sensor_publisher \
  --ros-args -r /sensor/status:=/robot_01/sensor/status

# 修改日志级别
ros2 run sensor_monitor_py sensor_publisher \
  --ros-args --log-level debug
```

- `--ros-args`：其后内容交给 ROS 参数解析器。
- `-r`：`--remap` 的短写。
- `__node:=...`：改变本次运行的节点名，不修改源代码。
- `旧话题:=新话题`：改变节点实际连接的话题。
- `--log-level debug`：设置日志过滤级别；本代码没有 debug 日志时不会凭空产生更多业务信息。

由于源码使用绝对话题名 `/sensor/status`，仅给节点加命名空间并不会自动把它变成 `/robot_01/sensor/status`，还需要显式重映射。这一点是本实验理解绝对名和相对名的关键。

## 11. 进阶任务的详细做法与验收现象

### 11.1 把阈值改为 ROS 参数

目标是让 `min_distance` 和 `max_temperature` 无需改源代码即可配置。建议把警告阈值与危险阈值分别命名，避免一个参数含义不清，例如：

```text
warning_distance_m
danger_distance_m
warning_temperature_c
danger_temperature_c
```

节点代码需要 `declare_parameter()` 声明默认值，再用 `get_parameter().value` 读取。完成后可这样运行：

```bash
ros2 run sensor_monitor_py sensor_publisher --ros-args \
  -p warning_distance_m:=1.2 \
  -p danger_distance_m:=0.6
```

- `-p` 是 `--param` 的短写。
- `名称:=值` 是参数赋值语法。
- 小数不要加成字符串引号，否则可能得到错误的参数类型。

验收时执行：

```bash
ros2 param list /sensor_publisher
ros2 param get /sensor_publisher warning_distance_m
```

并证明同一组距离数据在不同参数下产生了不同状态。

### 11.2 新增 `battery_voltage`

在 `SensorStatus.msg` 增加：

```text
float32 battery_voltage
```

推荐步骤：

1. 停止仍使用旧接口的节点。
2. 修改 `.msg`，并在发布者中赋值、订阅者中读取。
3. 在工作空间根目录重新执行 `colcon build --symlink-install`。
4. 每个运行终端重新执行 `source install/setup.bash`。
5. 用 `ros2 interface show sensor_interfaces/msg/SensorStatus` 证明新字段已生成。
6. 用 `ros2 topic echo /sensor/status --once` 证明线上消息确实携带该字段。

只完成第 5 步说明接口生成成功；第 6 步才证明发布代码也已经使用新接口。

### 11.3 同时运行两台模拟机器人

因为源码写的是绝对话题名，使用重映射最明确：

```bash
ros2 run sensor_monitor_py sensor_publisher --ros-args \
  -r __node:=sensor_publisher_01 \
  -r /sensor/status:=/robot_01/sensor/status

ros2 run sensor_monitor_py safety_monitor --ros-args \
  -r __node:=safety_monitor_01 \
  -r /sensor/status:=/robot_01/sensor/status
```

第二套把 `01` 改成 `02`。必须同时修改节点名和话题映射，否则可能出现同名节点难以诊断，或两个监控器都接入同一个数据流。

验收命令：

```bash
ros2 topic list -t
ros2 node list
ros2 topic info /robot_01/sensor/status --verbose
ros2 topic info /robot_02/sensor/status --verbose
```

两个话题都应各有一个发布端和一个订阅端。

## 12. 常见问题：现象、原因与检查证据

### 12.1 `ModuleNotFoundError: sensor_interfaces`

常见原因是接口包未构建成功、当前终端没有 source 工作空间，或 Python 节点来自另一个工作空间。检查：

```bash
ros2 pkg prefix sensor_interfaces
ros2 interface show sensor_interfaces/msg/SensorStatus
```

先确认构建成功，再 source；source 不是构建的替代品。

### 12.2 话题存在但收不到消息

```bash
ros2 topic info /sensor/status --verbose
```

按“名称 → 类型 → 端点数量 → QoS → 节点是否存活 → Domain ID/网络”的顺序检查。`Publisher count: 1` 只表示发现到端点，不保证该节点当前仍在调用 `publish()`，所以还要配合 `hz`。

### 12.3 修改 `.msg` 后字段仍不存在

旧进程已经加载旧类型支持，不能在运行中自动换协议。停止节点，重新构建，并在每个新终端重新 source。可用 `ros2 pkg prefix sensor_interfaces` 排除 source 到错误工作空间的情况。

### 12.4 `frame_id` 为空或拼写不一致

本实验纯终端输出时看似还能运行，但后续 RViz、TF2 和传感器融合无法判断数据属于哪个坐标系。检查 `echo` 中的 `header.frame_id`，并确保它与未来 TF 树中的名字一致。

### 12.5 `hz` 显示的频率不是精确 2.000

正常的小幅波动来自操作系统调度、Python 回调、终端输出和统计窗口。若长期明显偏低，再检查 CPU 负载、回调耗时、BEST_EFFORT 丢包和是否有多个数据源。不要用增大 QoS 深度来掩盖持续处理不过来的问题。

## 13. 最终验收清单

- 能说明为什么同一次采样要放在一条结构化消息中。
- 能逐行解释 `SensorStatus.msg`，包括常量和字段的区别。
- 能解释构建、source 和运行三者分别做什么。
- 发布端能稳定循环输出四组样本，监控端能产生对应日志。
- `ros2 topic info /sensor/status --verbose` 显示一个发布端和一个订阅端，并能解释每一行。
- `echo --once` 能证明字段和值正确，`hz` 能证明频率约为 2 Hz。
- 停止发布者后能观察到一次数据超时，并说明为什么不是恰好 1.5 秒。
- 能用命令行手动注入一条危险消息验证订阅逻辑。
- 能说明 `UNKNOWN` 不等于零或故障，GID 也不是需要在业务代码中使用的固定 ID。
- 能完成参数化阈值、新增电压字段或双机器人重映射中的至少一项扩展。
