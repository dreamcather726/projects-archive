# 第二单元知识点详解

## ROS 2 话题通信与消息类型

这份文档讲解 ROS 2 最常用的数据通信方式：话题。内容包括发布—订阅模型、`rclpy` 发布者与订阅者、标准消息、自定义消息、时间戳、坐标系、命名空间、重映射、QoS 初步配置和话题调试。

配套实验位于 [experiments/01_sensor_status](experiments/01_sensor_status)。

### 建议怎样学习本单元

每个知识点都按下面四个问题学习，而不是只记命令：

1. **它解决什么问题**：没有这个机制时，机器人系统会遇到什么困难？
2. **代码或命令中的每个参数是什么**：参数改变后，通信行为会怎样变化？
3. **运行后应看到什么**：终端输出中的哪些字段能证明程序正常？
4. **它与后续课程有什么关系**：以后调试 TF、Nav2、传感器或 QoS 时在哪里用到？

例如，执行 `ros2 topic info /sensor/status --verbose` 的目标不是“得到一屏文字”，而是回答三个工程问题：谁在发布、谁在订阅、双方的 QoS 是否可能通信。第 8.2 节会逐行解释这条命令和示例输出。

## 1. 话题解决什么问题

传感器会连续产生数据，例如激光雷达每秒发布多帧扫描，底盘持续发布里程计。发送端不应该等待每个接收模块处理完毕，也不应该提前知道有多少个接收者。

话题使用发布—订阅模型：

```text
               ┌──> 避障节点
激光节点 ─/scan┼──> 建图节点
               └──> RViz2
```

激光节点只负责向 `/scan` 发布 `sensor_msgs/msg/LaserScan`。避障、建图和可视化节点可以独立订阅，任一订阅者退出不会要求发布者修改代码。

这里的“解耦”有三层含义：

- **时间解耦**：发布者不必等订阅者处理完成才继续工作。
- **空间解耦**：双方不需要拿到对方的 Python 对象或网络地址，只需要约定话题接口。
- **数量解耦**：增加一个 RViz2 或记录节点时，通常不需要修改激光节点。

但解耦不等于“什么都不用约定”。话题名、消息类型、字段语义、单位、坐标系和 QoS 都属于接口契约。很多“话题存在但收不到”的问题，就是契约的某一项没有匹配。

**对后续学习的作用：**Nav2 的 `/cmd_vel`、激光雷达的 `/scan`、里程计 `/odom`、地图 `/map` 都是话题。掌握本单元后，后续看到一个复杂 ROS 2 系统时，可以先把它还原成“哪些节点通过哪些数据流连接”。

## 2. 发布—订阅模型

### 2.1 三个基本要素

- Publisher：创建和发送消息。
- Topic：具有名称、类型和 QoS 的数据通道。
- Subscription：接收消息并触发回调。

发布端与订阅端至少需要满足：

1. 解析后的话题名称一致。
2. 消息类型完全一致。
3. QoS 策略兼容。
4. DDS 发现和网络条件允许双方互相发现。

### 2.2 异步

`publisher.publish(message)` 把消息交给 ROS 2 通信层后返回。它不是一次函数远程调用，不会返回某个订阅者的处理结果。

如果业务要求“必须告诉我是否处理成功”，应考虑服务或动作，而不是等待话题订阅者回复。

一次 `publish()` 成功通常只表示消息已经交给本机 ROS 2 中间件，并不等于：

- 所有订阅者都已经收到；
- 订阅回调已经执行；
- 业务动作已经完成；
- 消息一定不会因 QoS、网络或队列压力而丢失。

因此，速度指令、传感器流和状态广播适合话题；“保存地图并返回成功/失败”更像服务；“导航到目标点，持续反馈进度并允许取消”更像动作。

### 2.3 多对多

一个话题可以有多个发布者，也可以有多个订阅者。多发布者适用于多个同类数据源，但会增加数据来源判断难度，因此消息中通常要包含来源、坐标系或命名空间信息。

`Publisher count` 或 `Subscription count` 大于 1 本身不是错误。例如 `/rosout` 天然会汇集多个节点的日志。但对 `/cmd_vel` 这类控制话题，如果多个发布者同时输出互相冲突的速度，就可能导致机器人行为跳变。以后排查“机器人为什么偶尔不听控制”时，第一步之一就是检查是否出现了意外的第二个发布者。

### 2.4 启动顺序

话题双方不要求固定启动顺序，但新订阅者能否收到发布前的数据由 Durability 等 QoS 决定。默认瞬时话题不会自动补发所有旧消息。

启动后双方还需要经过 DDS 发现。若发布者启动后立刻只发一条消息并退出，订阅者可能还没完成发现，所以看不到这条消息。这也是实验和自动化测试中常见的“偶现失败”。持续话题通常等一小段时间即可建立连接；一次性配置数据则应根据需求考虑 `TRANSIENT_LOCAL`，而不是盲目 `sleep()`。

## 3. 创建发布者

导入消息类型：

```python
from std_msgs.msg import String
```

在 Node 构造方法中创建发布者：

```python
self.publisher = self.create_publisher(
    String,
    '/robot/status',
    10,
)
```

三个主要参数：

- `String`：话题消息类型。
- `/robot/status`：话题名称。
- `10`：简写的 QoS 队列深度。

完整调用形式可以理解为：

```text
create_publisher(消息类, 话题名, QoS配置) -> Publisher对象
```

- **消息类**决定序列化格式。这里传的是类 `String`，不是对象 `String()`。
- **话题名**会结合节点命名空间和重映射规则解析成最终名称。
- **QoS配置**可以只写整数深度，也可以传 `QoSProfile`。整数 `10` 不是发布频率，也不会自动创建 10 Hz 定时器。
- **返回对象**才提供 `publish()`。它代表一个真实的 ROS 图端点，所以要在节点存活期间保存。

发布消息：

```python
message = String()
message.data = 'READY'
self.publisher.publish(message)
```

### 3.1 为什么要创建消息对象

ROS 2 消息不是任意 Python 字典。消息类规定字段名称、嵌套结构和数据类型。创建对象后才能为字段赋值并交给序列化系统。

下面三者不要混淆：

```python
String           # 生成出来的消息类，创建 publisher 时使用
String()         # 一条新的消息对象，发布前为字段赋值
message.data     # 这条消息中的具体字段
```

若字段名拼错，通常会在 Python 端很快报错；若数值超出接口类型范围，也可能在赋值或序列化时失败。`ros2 interface show <类型>` 是核对字段的权威入口。

### 3.2 为什么保存为实例属性

发布者是节点拥有的长期通信实体。保存为 `self.publisher` 可以保证生命周期清晰，也方便其他回调复用和节点销毁时统一清理。

### 3.3 发布触发方式

- 定时发布：周期状态、传感器模拟。
- 事件发布：设备有新数据时发布。
- 订阅回调中发布：对输入处理后输出。
- 服务或动作处理中发布：报告状态变化。

不要在节点构造方法中写无限循环发布，否则程序无法正常进入执行器，也无法处理其他回调。

定时发布通常由 `self.create_timer(period_seconds, callback)` 完成。`period_seconds=0.5` 表示每 0.5 秒让回调具备一次执行机会，理论频率约为 `1 / 0.5 = 2 Hz`。它不是硬实时保证；回调阻塞、CPU 忙或执行器调度都可能让实际频率降低，所以需要用 `ros2 topic hz` 实测。

## 4. 创建订阅者

```python
self.subscription = self.create_subscription(
    String,
    '/robot/status',
    self.on_status,
    10,
)
```

四个参数依次是：

- `String`：期望反序列化成的消息类型，必须与发布端完全一致。
- `/robot/status`：订阅的话题名，解析和重映射规则与发布端相同。
- `self.on_status`：收到消息时由执行器调用的函数对象，注意这里没有括号。
- `10`：订阅端 QoS 深度简写，不是“最多接收 10 条后停止”。当回调处理不过来且使用 KEEP_LAST 时，较旧的待处理样本可能被新的样本替代。

`create_subscription()` 返回订阅端点。保存为 `self.subscription` 或 `self._subscription` 能明确它应与节点共同存活。

订阅回调：

```python
def on_status(self, message):
    self.get_logger().info(f'收到状态：{message.data}')
```

消息到达后，执行器选择并调用回调。回调不是发布者直接调用的普通函数。

### 4.1 回调应保持短小

回调中适合完成：

- 校验消息。
- 更新节点内部状态。
- 执行短时间计算。
- 发布处理结果。
- 发起异步任务。

回调中不适合无条件 `sleep()`、长时间循环或等待网络返回。长回调会影响其他消息和定时器，第六单元将专门讲解。

**运行时发生的过程**可以概括为：DDS 收到字节数据 → ROS 2 按消息类型反序列化 → 执行器发现回调可运行 → 调用 `on_status(message)` → 业务代码读取字段。理解这条链路后，看到“发布频率正常但回调不及时”时，就会继续检查执行器和回调耗时，而不是只怀疑网络。

## 5. 标准消息

ROS 2 已提供许多通用接口，设计自定义消息前先查标准消息。

### 5.1 std_msgs

```text
std_msgs/msg/String
std_msgs/msg/Bool
std_msgs/msg/Int32
std_msgs/msg/Float64
std_msgs/msg/Header
```

基础消息适合简单信号和教学示例。复杂机器人接口不应把所有字段拼成字符串。

例如字符串 `"distance=0.8,temp=42"` 虽然能发送，但接收端还要自行拆分文本，无法由 ROS 2 检查字段类型和单位，也不便于 rosbag、可视化与跨语言使用。教学阶段可用 `String` 熟悉流程，工程接口应优先使用结构化消息。

### 5.2 geometry_msgs

```text
geometry_msgs/msg/Point
geometry_msgs/msg/Quaternion
geometry_msgs/msg/Pose
geometry_msgs/msg/PoseStamped
geometry_msgs/msg/Twist
geometry_msgs/msg/TransformStamped
```

`Twist` 包含：

```text
Vector3 linear
Vector3 angular
```

设置差速底盘常用速度：

```python
command = Twist()
command.linear.x = 0.3
command.angular.z = 0.5
```

单位通常是米每秒和弧度每秒，具体接口应在文档中明确。

`linear` 和 `angular` 不是数字，而是两个嵌套的 `Vector3` 消息，因此要写 `command.linear.x`，不能写 `command.linear = 0.3`。这类嵌套关系在 `Pose`、`Odometry`、`Imu` 中会大量出现。

### 5.3 sensor_msgs

- `LaserScan`：二维激光扫描。
- `Image`：原始图像。
- `Imu`：角速度、线加速度和姿态。
- `JointState`：关节名称、位置、速度和力。
- `PointCloud2`：三维点云。

这些消息不仅字段多，往往还包含时间戳、坐标系、协方差、数组步长或编码格式。后续接入真实硬件时，能收到消息只是第一步；还要确认单位、坐标轴方向、时间是否同步以及无效值如何表示。

### 5.4 nav_msgs

- `Odometry`：里程计位姿和速度。
- `Path`：由一组带时间和坐标系的位姿组成的路径。
- `OccupancyGrid`：栅格地图。

后续 Nav2 会同时使用 `/map`、`/odom`、`/cmd_vel` 和 TF。若只看话题名称而忽略消息中的 frame 和时间，常会出现“终端有数据但 RViz 显示不对”或“导航报 transform timeout”。

### 5.5 查看消息结构

```bash
ros2 interface show geometry_msgs/msg/Twist
ros2 interface show sensor_msgs/msg/LaserScan
ros2 interface show nav_msgs/msg/Odometry
```

不要依靠记忆猜嵌套字段。先用 `ros2 interface show` 查看，再编写赋值代码。

命令格式是 `ros2 interface show <包名>/<接口类别>/<接口名>`。例如 `geometry_msgs/msg/Twist` 中：`geometry_msgs` 是包，`msg` 表示消息接口，`Twist` 是类型名。执行后只显示结构定义，不要求该话题正在运行，适合写代码前查询。

## 6. Header、时间戳和坐标系

许多传感器和几何消息包含 `std_msgs/Header`：

```text
builtin_interfaces/Time stamp
string frame_id
```

### 6.1 stamp

时间戳表示数据对应的时间。传感器消息应尽量使用采样时刻，而不是算法处理结束时刻。

Python 节点填写当前 ROS 时间：

```python
message.header.stamp = self.get_clock().now().to_msg()
```

使用节点时钟的好处是，当系统启用仿真时间时，同一份代码会跟随 `/clock`。

时间戳回答的是“这份数据对应什么时候”，订阅回调中的 `now()` 回答的是“本节点什么时候处理它”。二者之差可包含采样、传输、排队和调度延迟。以后做多传感器同步、TF 查询和延迟分析时，必须区分这两个时间。

### 6.2 frame_id

`frame_id` 表示数据在哪个坐标系下表达：

```python
message.header.frame_id = 'front_laser'
```

它不是随意备注。后续 TF2、RViz 和传感器融合都依赖准确的坐标系名称。

通常 `frame_id` 不以 `/` 开头，并应与 TF 树中的 frame 名完全一致。它表达的是“数据所在坐标系”，不是话题名、节点名或传感器型号。

### 6.3 时间与坐标不能缺一

“某个点在 `laser_link` 中的位置”还需要知道它对应哪个时刻。机器人在运动时，不同时刻的变换不同。仅有坐标系而没有正确时间，可能把旧数据转换到新位置。

## 7. 话题名称

### 7.1 绝对名称

以 `/` 开头：

```text
/robot/status
```

绝对名称不受节点命名空间影响，直观但复用性较弱。

绝对名适合全系统唯一、部署结构固定的接口；但在多机器人系统中，两份相同节点都写死 `/sensor/status`，就会挤到同一话题中。

### 7.2 相对名称

```text
status
```

如果节点位于 `/robot_01` 命名空间，可能解析为 `/robot_01/status`。可复用节点优先使用相对名称，由启动配置决定部署位置。

这里的“可能”取决于节点的最终命名空间。运行后不要猜，可以用 `ros2 node info /节点名` 或 `ros2 topic list` 查看解析结果。

### 7.3 重映射

```bash
ros2 run sensor_monitor_py safety_monitor \
  --ros-args -r /sensor/status:=/robot_01/sensor/status
```

重映射改变本次运行连接的话题，不修改源码。它适合复用节点、兼容设备接口和多机器人部署。

命令参数拆解：

- `--ros-args`：从这里开始是 ROS 通用参数，而不是 `sensor_monitor_py` 程序自己的参数。
- `-r`：`--remap` 的短写。
- `/sensor/status:=/robot_01/sensor/status`：把左侧原名称替换为右侧目标名称。

运行后代码里仍写 `/sensor/status`，ROS 图中显示的却是重映射后的 `/robot_01/sensor/status`。这对后续 launch 文件和多机器人部署非常重要。

### 7.4 命名建议

- 使用小写字母、数字、下划线和层级路径。
- 名称表达数据语义，例如 `scan`、`odom`、`battery_state`。
- 不把发布者实现名称强行写入话题名。
- 不在同一系统中给不同语义的数据使用同一名称。

## 8. 话题命令行工具：命令、参数、输出与判断

命令的通用结构是：

```text
ros2 topic <子命令> [话题名] [消息类型] [数据] [选项]
```

其中 `ros2` 是总入口，`topic` 表示操作话题，`list/type/info/echo/pub/hz/bw` 是不同子命令。不同 ROS 2 发行版或 `ros2topic` 版本的可选参数可能略有差别，随时用以下命令查看本机真实支持项：

```bash
ros2 topic --help
ros2 topic info --help
ros2 topic echo --help
ros2 topic pub --help
```

`--help` 只打印帮助，不修改 ROS 图，也不要求目标话题存在。

### 8.1 列出话题和类型

```bash
ros2 topic list
ros2 topic list -t
```

- 不带参数时，每行只显示一个当前发现到的话题名。
- `-t` 是 `--show-types` 的短写，在话题后显示一个或多个类型。
- 结果来自当前 ROS 图。刚启动节点时若列表暂时没有变化，可稍等发现完成后重试。

本实验可能看到：

```text
/parameter_events [rcl_interfaces/msg/ParameterEvent]
/rosout [rcl_interfaces/msg/Log]
/sensor/status [sensor_interfaces/msg/SensorStatus]
```

前两个是许多 ROS 2 节点都会产生的系统话题，不是实验代码额外编写的业务话题。第三行同时证明 `/sensor/status` 已被发现且其类型是自定义消息。它还不能证明消息正在持续发布，需要再用 `echo` 或 `hz`。

### 8.2 查看类型和端点

```bash
ros2 topic type /sensor/status
ros2 topic info /sensor/status
ros2 topic info /sensor/status --verbose
```

三条命令由浅入深：

- `type` 只回答“这个话题使用什么消息类型”。
- `info` 回答“类型是什么、有几个发布者和订阅者”。
- `info --verbose` 进一步列出每个端点的节点身份、GID 和 QoS，是排查“为什么收不到”的关键命令。`--verbose` 也可写成常见短选项 `-v`；以本机 `--help` 为准。

`/sensor/status` 是位置参数，必须是已经解析后的话题名；`--verbose` 是可选开关，不需要再跟值。运行此命令不会订阅和打印消息内容，也不会改变通信配置，只读取当前 ROS 图。

Jazzy 中与这条查询常见的其他选项如下；日常实验通常只需要话题名和 `-v`：

| 写法 | 作用 | 什么时候使用 |
|---|---|---|
| `-v` / `--verbose` | 输出每个发布与订阅端点的详细资料 | 本实验核对节点身份和 QoS |
| `--no-daemon` | 不使用后台 `ros2 daemon` 缓存，直接创建临时节点查询 | 怀疑 CLI 图缓存没有及时更新时 |
| `--spin-time 1.0` | 直接查询时等待发现的时间设为 1.0 秒 | 节点较多或网络发现较慢时；主要与 `--no-daemon` 配合 |
| `-s` / `--use-sim-time` | 让 CLI 临时节点使用 ROS 仿真时间 | 一般不影响 `info` 的图查询结果，本实验无需设置 |
| `ros2 topic --include-hidden-topics ...` | 让 topic 命令考虑名称中含隐藏段的话题 | 查询以下划线开头的内部话题时 |

可组合为：

```bash
ros2 topic info /sensor/status --verbose --no-daemon --spin-time 1.0
```

不要为了“输出更准确”无条件把 `--spin-time` 设得很大；它只是给直接发现更多等待时间，不会修复话题名、类型、QoS 或网络配置错误。

下面逐行解释本实验的一份实际输出：

```text
Node name: sensor_publisher
Node namespace: /

Endpoint type: PUBLISHER

  Durability: VOLATILE

  Deadline: Infinite

  Liveliness lease duration: Infinite
```

| 输出行 | 本实验中的含义 | 调试和后续学习价值 |
|---|---|---|
| `Type` | ROS 图为该话题发现到的消息类型 | 发布者与订阅者必须使用同一类型；之后可把它交给 `ros2 interface show` 查看字段 |
| `Publisher count: 1` | 当前发现到 1 个发布端点 | 为 0 时没有数据源；意外大于 1 时要检查是否重复启动或存在多个控制源 |
| `Node name: sensor_publisher` | 这个端点属于名为 `sensor_publisher` 的节点 | 可继续执行 `ros2 node info /sensor_publisher` 追查该节点所有接口 |
| `Node namespace: /` | 节点在根命名空间 | 与节点名合成完全限定名 `/sensor_publisher`；多机器人中可能变成 `/robot_01` |
| `Topic type` | 该具体端点声明使用的类型 | 多类型冲突或工具报告异常时，用它逐端点核对 |
| `Endpoint type: PUBLISHER` | 下列信息属于发布端 | 它是数据源，不表示节点只发布这一个话题 |
| `GID` | DDS/RMW 为端点分配的全局标识字节串 | 主要用于区分同名节点或同一节点内的多个端点、关联底层 DDS 日志；初学阶段无需解析每个字节，也不要把它写死到程序中 |
| `QoS profile` | 以下是该端点的通信策略 | 名称和类型一致仍收不到时，重点比较发布端与订阅端的 QoS 兼容性 |
| `Reliability: BEST_EFFORT` | 尽力发送，不保证重传每个丢失样本 | 适合高频传感器的新鲜数据；网络不佳时可能丢帧。后续用 `hz` 观察接收频率 |
| `History (Depth): UNKNOWN` | 当前 CLI/RMW 没有把历史策略或深度以确定值报告出来 | `UNKNOWN` 表示“探测结果未知”，不等于深度为 0 或一定配置错误。本代码传入的 `qos_profile_sensor_data` 预设使用 KEEP_LAST、深度 5；判断时应结合源码、RMW 实现和实际通信 |
| `Durability: VOLATILE` | 只接收建立匹配之后的新数据，不为后来者保存旧样本 | 新开的 `echo` 不会自动看到启动前的数据；但发布者每 0.5 秒继续发，所以很快会看到下一条 |
| `Lifespan: Infinite` | 中间件没有按消息年龄自动使样本失效 | 它不等于数据永不超时；本实验仍由安全监控节点按 1.5 秒业务规则检查新鲜度 |
| `Deadline: Infinite` | 未声明“相邻样本必须在某期限内到达”的 DDS 合同 | ROS 中间件不会仅靠此项替本实验报告 1.5 秒超时；所以代码需要 watchdog 定时器 |
| `Liveliness: AUTOMATIC` | 活跃性通常由中间件自动维护 | 更复杂的故障检测可使用 liveliness 事件，本实验先用接收时间实现直观的软件看门狗 |
| `Liveliness lease duration: Infinite` | 没有设置有限的活跃租约时长 | 不会因租约到期自动判断发布者失活；不要把它和代码里的 1.5 秒超时混为一谈 |
| `Subscription count: 1` | 当前发现到 1 个订阅端点 | 为 0 时发布者仍能运行，但没有业务节点消费数据；本实验应为 1 |
| `Endpoint type: SUBSCRIPTION` | 下列信息属于订阅端 | 将这组 QoS 与发布端对照，不能只看其中一边 |

两组端点信息重复出现是正常的：第一组描述 `sensor_publisher` 的发布端，第二组描述 `safety_monitor` 的订阅端。两个 GID 不同也正常，因为它们是两个不同 DDS 端点。

从这份输出可以按顺序得出结论：

1. 名称存在，类型是 `SensorStatus`。
2. 发布者和订阅者各 1 个，节点发现已经完成。
3. 两端都显示 `BEST_EFFORT + VOLATILE`，这两项相互匹配。
4. 因此若 `safety_monitor` 仍无输出，下一步应看节点是否在 spin、回调是否报错、Domain ID/网络是否变化，而不是继续怀疑话题拼写。

`tao@tao:~/...$` 是 Linux Shell 提示符，表示命令已经执行完并等待下一条输入，它不属于 ROS 2 的输出。

### 8.3 查看内容

```bash
ros2 topic echo /sensor/status
ros2 topic echo /sensor/status --once
```

- 不带选项时持续订阅并打印，每条 YAML 风格消息通常以 `---` 分隔，按 `Ctrl+C` 停止。
- `--once` 收到一条后退出，适合截取证据或确认字段值，不表示要求原发布者只发一次。
- `echo` 自己会临时创建一个订阅端点，因此在它运行期间，另一个终端中的 `Subscription count` 可能从 1 变为 2；退出后会恢复。

本实验单条输出形态类似：

```yaml
header:
  stamp:
    sec: 1720000000
    nanosec: 123456789
  frame_id: front_laser
source: simulated_front_sensor
distance_m: 1.8
temperature_c: 31.0
status: 0
---
```

这里应检查：字段是否齐全、`frame_id` 是否为 `front_laser`、时间戳是否变化、数值是否按四组样本循环，以及 `status` 是否与阈值逻辑一致。常量名称不会代替线上的数值，所以看到的是 `0/1/2`；可用消息定义把它们解释为 OK/WARNING/DANGER。

### 8.4 手动发布

```bash
ros2 topic pub --once /robot/status std_msgs/msg/String \
  "{data: 'READY'}"
```

`--once` 发布一次，`--rate 10` 以 10 Hz 持续发布。

参数依次是：

- `pub`：创建一个临时命令行发布者。
- `--once`：完成发现后发布一条并退出。
- `/robot/status`：目标话题名。
- `std_msgs/msg/String`：消息类型。
- `"{data: 'READY'}"`：用 YAML 表达字段和值。

若省略 `--once`，不同版本 CLI 可能按默认频率持续发布；为了让实验结果明确，建议显式写 `--once` 或 `--rate <Hz>`。发布复杂消息前先运行 `ros2 interface show`，嵌套字段也按 YAML 层级填写。

对本实验做故障注入时，可以在停止原发布者后手动发送一条危险消息：

```bash
ros2 topic pub --once /sensor/status sensor_interfaces/msg/SensorStatus \
  "{header: {frame_id: front_laser}, source: manual_test, distance_m: 0.2, temperature_c: 30.0, status: 2}"
```

预期 `safety_monitor` 输出一次“危险”。这个实验能把“发布节点算法是否正确”和“订阅节点判断是否正确”分开验证。若原发布者未停止，两个发布源会同时存在，`Publisher count` 会临时变为 2，输出也会交错。

### 8.5 检查频率与带宽

```bash
ros2 topic hz /sensor/status
ros2 topic bw /sensor/status
```

定时器设置 0.1 秒不代表实测一定严格为 10 Hz。执行器负载、系统调度和网络都会造成偏差。

本实验定时器周期是 0.5 秒，所以理论频率为 2 Hz。`ros2 topic hz` 会先等待消息，随后滚动输出平均频率、最小/最大周期、标准差和样本窗口大小；刚开始样本少时波动较大，应观察几秒再判断。按 `Ctrl+C` 结束。

`ros2 topic bw` 会订阅数据并估算单位时间收到的数据量和平均消息大小。它测的是该观察点的接收结果，不是网络抓包得到的完整 DDS/UDP 开销，也不是发布者进程的 CPU 占用。以后处理图像、点云等大消息时，它可快速判断带宽是否可能成为瓶颈。

这些观察命令本身通常会创建额外订阅者。调试时看到订阅数量短暂增加，不要误判为业务节点重复启动。

## 9. 自定义消息

### 9.1 什么时候需要自定义消息

假设一次传感器采样需要包含：

- 采样时间。
- 坐标系。
- 设备来源。
- 距离。
- 温度。
- 状态码。

将它们拆成多个标量话题会产生时间对齐和接口管理问题，适合定义一个 `SensorStatus.msg`。

判断原则不是“字段多就自定义”，而是先找语义匹配的标准接口。只有业务含义确实没有标准表达时才新增接口。接口一旦被多个包和 rosbag 使用，改名、删字段或改类型都会影响所有使用者，因此应把消息设计当作公共 API。

### 9.2 消息文件

```text
std_msgs/Header header
string source
float32 distance_m
float32 temperature_c

uint8 STATUS_OK=0
uint8 STATUS_WARNING=1
uint8 STATUS_DANGER=2
uint8 status
```

命名中直接提示单位，例如 `distance_m`、`temperature_c`，可以降低误用风险。

逐行含义：

- `std_msgs/Header header`：嵌套标准 Header，把时间和坐标系绑定到同一次采样。
- `string source`：业务来源标识，可区分模拟器、前传感器或后传感器。
- `float32 distance_m`：32 位浮点距离，字段名明确单位为米。
- `float32 temperature_c`：摄氏温度。
- `uint8 STATUS_...=...`：消息常量，进入接口定义但不作为每条消息的可变字段传输。
- `uint8 status`：线上实际状态值，可取约定的 0、1、2。

常量让 Python、C++ 和命令行都共享同一份枚举约定；但它仍是数值协议，接收端也要考虑未知值，不能假设永远只有三个合法值。

### 9.3 接口包与业务包分离

推荐：

```text
ros2_ws/src/
├── sensor_interfaces/   # 只保存 msg/srv/action 定义
└── sensor_monitor_py/   # Python 发布者和订阅者
```

接口生成包使用 ROS 2 的接口生成构建规则；这里不会编写其他语言的业务节点。分离后多个 Python 包可以共同依赖同一接口，也可减少循环依赖。

构建时先由 `sensor_interfaces` 生成 Python/C++ 等语言支持，再构建依赖它的 `sensor_monitor_py`。这就是为什么“只有一个 `.msg` 文本文件”仍不能直接 `import`：Python 导入的实际是构建阶段生成并安装到工作空间中的模块。

### 9.4 接口包关键规则

`CMakeLists.txt` 中列出消息：

```cmake
rosidl_generate_interfaces(${PROJECT_NAME}
  "msg/SensorStatus.msg"
  DEPENDENCIES std_msgs
)
```

`package.xml` 需要声明生成器、运行时和依赖消息包。修改 `.msg` 后必须重新构建接口包，并重新加载环境。

- `find_package(rosidl_default_generators REQUIRED)` 找到接口代码生成工具。
- `rosidl_generate_interfaces(...)` 指定要生成的接口文件。
- `DEPENDENCIES std_msgs` 说明该自定义消息嵌套使用了 `std_msgs/Header`。
- `ament_export_dependencies(rosidl_default_runtime)` 让使用者在运行期找到生成的类型支持。

重新 `source install/setup.bash` 的作用是把新构建结果加入当前 Shell 环境。它不是编译命令；若 `colcon build` 失败，反复 source 不会修好接口。

### 9.5 Python 使用生成消息

```python
from sensor_interfaces.msg import SensorStatus

message = SensorStatus()
message.distance_m = 0.8
message.status = SensorStatus.STATUS_WARNING
```

常量也会生成到 Python 消息类中，业务代码不必重复写 `0`、`1`、`2`。

## 10. QoS 初步认识

QoS 决定消息历史、可靠性和持久性等策略。本单元先掌握两类常见用法：

### 10.1 深度简写

```python
self.publisher = self.create_publisher(String, 'status', 10)
```

适合普通入门示例，通常形成保留最近若干消息的默认配置。

“深度 10”可以想象成订阅回调暂时处理不过来时，中间件至多为 KEEP_LAST 历史保留最近 10 个样本。它不是磁盘缓存、发布次数、订阅者数量或 Hz。队列增大能容忍短时抖动，却会增加内存占用，并可能让订阅者处理更旧的数据。

### 10.2 传感器数据配置

```python
from rclpy.qos import qos_profile_sensor_data

self.subscription = self.create_subscription(
    LaserScan,
    '/scan',
    self.on_scan,
    qos_profile_sensor_data,
)
```

高频传感器通常优先新鲜数据和低延迟，允许丢失个别帧。发布者和订阅者必须使用兼容 QoS。详细兼容关系在第六单元讲解。

本实验发布端和订阅端都显式使用 `qos_profile_sensor_data`。在 ROS 2 Jazzy 的常见实现中，该预设使用 KEEP_LAST、深度 5、BEST_EFFORT、VOLATILE。这里最重要的不是死记数值，而是理解取舍：机器人更需要最新距离，而不是网络恢复后依次处理很久以前积压的距离。

## 11. 数据值异常与数据超时

订阅回调只能在消息到达时执行。如果发布者停止，订阅回调不会自动收到“设备已掉线”消息。

因此监控节点需要记录最后接收时间，并用独立定时器检查：

```python
def on_message(self, message):
    self.last_message_time = self.get_clock().now()

def check_timeout(self):
    if self.last_message_time is None:
        return
    age = self.get_clock().now() - self.last_message_time
```

安全判断至少包含两类：

- 内容异常：距离过近、温度过高、字段非法。
- 新鲜度异常：超过限定时间没有新消息。

只检查最后一条消息的数值正常，不能证明传感器现在仍在线。

本实验把两个时间概念刻意分开：消息内 `header.stamp` 是发布端给出的采样时间；`_last_message_time` 是监控节点本地实际收到消息的时间。看门狗使用后者，是因为它要回答“我多久没有收到新消息”。如果要检测数据在传输前就已经过期，则还要比较当前时间与 `header.stamp`，并确保两端时钟同步。

## 12. 常见错误速查

### 12.1 话题名相同但没有数据

检查类型、QoS、Domain ID 和节点是否仍在运行：

```bash
ros2 topic list -t
ros2 topic info /sensor/status --verbose
```

### 12.2 消息字段赋值失败

使用 `ros2 interface show` 检查字段名、嵌套层级和类型。不要把浮点数写入字符串字段，也不要猜测数组结构。

### 12.3 自定义消息导入失败

检查接口包是否构建成功、业务包是否声明依赖、当前终端是否重新 source。

### 12.4 修改 msg 后仍是旧结构

停止旧节点，重新构建接口包和依赖包，再重新加载工作空间。

### 12.5 发布频率比定时器设置低

检查回调耗时、CPU 负载、网络和执行器阻塞。不要用无限增加队列深度掩盖处理速度不足。

### 12.6 frame_id 为空或拼写不一致

后续 RViz 和 TF2 无法正确转换。统一坐标系命名，并让消息 frame 与实际传感器安装关系一致。
