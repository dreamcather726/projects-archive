# 实验 5：模块化异常检测与生命周期节点

## 为什么要做这个实验

普通节点创建后通常立即开始工作，但真实设备可能尚未连接、参数可能不合法，系统也可能要求多个模块按顺序启动。生命周期节点把“进程已经存在”和“业务已经激活”分开，使系统可以先配置、检查，再统一激活。

## 实验的作用

- 学会把纯 Python 算法与 ROS 2 通信代码分离。
- 观察生命周期节点的配置、激活、停用和清理。
- 理解 inactive 状态下节点仍存在，但不应发布业务输出。
- 为可恢复的驱动、感知和控制系统建立设计模板。

## 实验重点

1. `AnomalyDetector` 不依赖 ROS 2，可直接单元测试。
2. configure 阶段验证参数并创建资源，activate 后才发布。
3. deactivate 不是杀死进程，节点仍可再次激活。
4. cleanup 后应释放资源，使下一次 configure 不会重复创建。

## 运行步骤

```bash
source /opt/ros/jazzy/setup.bash
cd <课程仓库>/ros2_course/unit_05_components_and_lifecycle/experiments/01_managed_monitor/ros2_ws
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install
source install/setup.bash
ros2 launch managed_monitor_py managed_monitor.launch.py
```

新终端查看状态并执行转换：

```bash
source /opt/ros/jazzy/setup.bash
cd <实验目录>/ros2_ws
source install/setup.bash
ros2 lifecycle get /managed_monitor
ros2 lifecycle set /managed_monitor configure
ros2 lifecycle set /managed_monitor activate
ros2 topic echo /monitor/alarm
```

继续尝试：

```bash
ros2 lifecycle set /managed_monitor deactivate
ros2 lifecycle set /managed_monitor cleanup
ros2 lifecycle get /managed_monitor
```

运行纯 Python 单元测试：

```bash
colcon test --packages-select managed_monitor_py
colcon test-result --verbose
```

## 预期现象

- 节点启动后处于 `unconfigured`，没有告警输出。
- configure 成功后处于 `inactive`，资源已准备但仍不发布。
- activate 后每秒产生模拟数据，异常时发布 `/monitor/alarm`。
- deactivate 后话题停止更新，重新 activate 后恢复。
- 阈值非法时 configure 失败，节点不会进入可激活状态。

## 验收任务

1. 把阈值参数设置为负数，证明 configure 会失败。
2. 增加温度上限，并让 `AnomalyDetector` 同时检查距离和温度。
3. 为新增边界条件补充纯 Python 单元测试。
4. 说明“节点进程存在”“节点已配置”“节点正在执行业务”的区别。

## 常见问题

- 直接 activate 失败：必须先从 unconfigured 转换到 inactive。
- inactive 状态仍有数据：检查定时回调是否根据激活状态控制业务。
- 二次 configure 创建重复实体：cleanup 没有释放资源。
- 单元测试导入失败：先构建并加载工作空间，或在 colcon 中运行测试。
