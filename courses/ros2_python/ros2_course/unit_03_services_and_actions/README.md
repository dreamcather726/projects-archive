# 第 3 模块：ROS 2 服务与动作通信机制

课程材料：[知识点详解](第3章_授课讲义.md) · [实验说明与代码](experiments/01_patrol_task/实验说明.md)

## 内容范围

- 话题、服务和动作的通信语义与选择依据。
- `rclpy` 异步服务客户端与服务端。
- 支持反馈、结果和取消的动作通信。

## 详细知识点

### 1. 三种通信方式的选择

- 话题：持续数据流、发布者不等待接收方响应。
- 服务：短时请求—响应，适合快速完成的查询或设置操作。
- 动作：长时任务，支持目标、过程反馈、最终结果和取消。
- 不应使用服务执行长时间阻塞任务，也不应使用话题模拟必须确认的请求。
- 结合“读取机器人状态、重置里程计、执行巡检任务”比较三者。

### 2. 服务接口与服务端

- `.srv` 中请求与响应的分隔结构。
- 使用标准服务接口与设计自定义服务接口。
- `create_service()`、服务回调的 request/response 参数。
- 参数校验、错误信息和幂等性设计。
- 服务回调不应执行长时间阻塞操作。

### 3. 异步服务客户端

- `create_client()` 和 `wait_for_service()`。
- `call_async()` 返回 Future，而不是直接返回响应。
- 使用 `spin_until_future_complete()` 的场景与限制。
- 使用完成回调处理 Future 的结果与异常。
- 超时、服务不可用、重复请求和程序退出时的处理。
- 避免在回调内错误使用同步调用造成死锁。

### 4. 动作接口与服务端

- `.action` 的 Goal、Result、Feedback 三段结构。
- `ActionServer` 与 `ActionClient` 的角色。
- 目标接收、拒绝和合法性检查。
- 执行过程中发布反馈。
- 成功、取消、终止三类结果状态。
- 动作服务端对并发目标的处理策略。

### 5. rclpy 动作客户端

- 等待动作服务端可用。
- 异步发送目标与注册反馈回调。
- 判断目标是否被接受。
- 异步获取最终结果。
- 发起取消请求并确认取消结果。
- 正确管理多个 Future，避免回调层级混乱。

### 6. 接口设计原则

- 请求/目标只包含完成任务所需输入。
- 反馈表达可观测进度，结果表达最终业务结论。
- 明确单位、坐标系、允许范围和失败原因。
- 对未来扩展保留语义空间，但不堆积无用字段。
- 接口包单独维护，Python 节点只依赖生成后的接口。

## 课堂演示

1. 实现“设置巡检模式”服务和异步客户端。
2. 模拟服务端未启动、请求超时和参数非法三种异常。
3. 实现“移动指定距离”动作，周期返回完成百分比。
4. 在任务执行中发送取消请求，观察服务端的取消处理和最终状态。

## 实验任务

完成一个巡检任务管理器：

- 服务 `/set_patrol_enabled` 用于启停巡检功能。
- 动作 `/run_patrol` 接收目标点数量和单点停留时间。
- 动作反馈包含当前点、总点数和完成比例。
- 动作结果包含是否完成、已访问点数和失败原因。
- 客户端支持发送、观察反馈、取消和超时退出。

## 常见问题

- 把服务调用结果当作同步返回值使用。
- 服务回调长时间阻塞，导致同一执行器中的其他回调无法运行。
- 动作服务端收到取消请求但执行循环没有检查取消状态。
- 目标被拒绝后仍继续请求结果。
- 接口字段没有单位或状态语义，导致客户端和服务端理解不一致。

## 验收标准

- 能准确说明话题、服务和动作各自适用的场景。
- 服务客户端在服务未启动时不会直接崩溃或无限无提示等待。
- 动作执行期间持续返回反馈，并能正确取消。
- 异常和失败通过结构化结果返回，而不是只打印日志。
