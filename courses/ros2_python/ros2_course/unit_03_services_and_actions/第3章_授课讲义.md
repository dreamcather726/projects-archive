# 第三单元知识点详解

## ROS 2 服务、动作与异步任务

这份文档从通信语义出发，讲解如何在话题、服务和动作之间选择，并详细说明 Python 服务端、异步客户端、动作目标、反馈、结果、取消和失败处理。

配套实验位于 [experiments/01_patrol_task](experiments/01_patrol_task)。

## 1. 所有通信都用话题会怎样

先考虑三个需求：持续发布激光；清零里程计并确认是否成功；执行十分钟巡检并显示进度。尝试全部使用话题表达，可以发现以下问题：

- 清零请求如果只发一次，节点未发现时可能错过，而且调用方不知道是否成功。
- 巡检若只发“开始”话题，调用方不知道目标是否接受、执行到哪里、怎样取消。

由此引出：数据流用话题，短事务用服务，长任务用动作。

## 2. 服务通信

服务接口分为 Request 和 Response：

```text
bool enabled
---
bool success
string message
```

服务端注册回调，收到请求后填写响应。服务回调应快速返回。读取状态、修改配置、触发一次轻量操作适合服务；移动一百米、下载大文件或长期等待设备完成不适合。

服务设计需要考虑幂等性。例如连续两次请求“启用巡检”是否都成功？如果第二次启用会造成重复资源，就必须在服务端显式处理当前状态。

## 3. 异步客户端与 Future

`call_async()` 立即返回 Future。Future 表示结果将来可能完成，不能把它直接当 Response 使用。

典型流程：

1. 创建 client。
2. `wait_for_service()` 等待服务可用，并设置合理超时。
3. 构造 Request。
4. `call_async()`。
5. 通过完成回调或执行器等待 Future。
6. 捕获调用异常并检查业务字段 `success`。

“ROS 调用成功”只表示拿到了响应，不等于业务成功。业务是否成功应由响应字段表达。

## 4. 动作通信

动作接口有三段：

- Goal：希望服务端完成什么。
- Result：最终完成情况。
- Feedback：执行过程中的进度信息。

动作还有协议状态：目标可被接受或拒绝；已接受目标可能成功、取消或终止。客户端必须依次处理“发送目标 Future”“目标句柄”“获取结果 Future”。

## 5. 动作服务端的执行模型

目标回调用于快速校验，不应在这里执行任务。执行回调负责长时任务：

1. 读取目标。
2. 分阶段执行。
3. 周期发布反馈。
4. 检查取消请求。
5. 设置 succeed/canceled/abort。
6. 返回 Result。

取消是协作式的。客户端提出取消，服务端接受后仍必须在执行循环中检查并安全停止。无法立即停止的硬件操作，应定义安全取消点。

## 6. 动作客户端的完整链路

客户端需要处理：

- 服务端是否在线。
- 目标是否被接受。
- 每次反馈如何显示或更新界面。
- 最终结果和状态。
- 用户什么时候可以取消。
- 客户端退出时是否遗留仍执行的目标。

教师可以画出事件序列：发送目标 → 接收/拒绝 → 多次反馈 → 成功/取消/终止 → 结果。

## 7. 接口设计规范

- 字段名表达业务语义，写清单位。
- 反馈应能说明进度，但不能大到影响通信。
- Result 应包含失败原因，不要只在服务端打印日志。
- Goal 应包含可校验约束，例如距离必须大于零。
- 一个动作应代表一个清晰任务，不把无关行为塞进同一接口。

## 8. 死锁的初步认识

在回调中发起同步服务调用，并且客户端响应回调无法获得执行机会时，系统会互相等待。初学阶段优先使用异步调用，长时动作执行也应避免独占唯一执行线程。第 6 章将用执行器和回调组解释其根因。

## 9. 知识点检查与实验

- 为什么动作目标“接受”不等于“成功”？
- 服务端为什么不能把失败原因只写到日志？
- 取消请求被接受后，谁负责真正停止机器人？
- 服务未启动时，客户端是退出、重试还是永远等待？依据是什么？
