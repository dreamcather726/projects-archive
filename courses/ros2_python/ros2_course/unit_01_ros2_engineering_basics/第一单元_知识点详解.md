# 第一单元知识点详解

## ROS 2 工程基础：工作空间、功能包、节点、接口与构建

这份文档作为 ROS 2 第一单元的课堂主讲义，也用于课后复习。内容从 ROS 2 的整体层级开始，依次讲清工作空间、Python 功能包、节点、通信接口、消息、计算图、DDS 发现机制、`colcon` 构建和环境加载。

配套实验位于 [experiments/01_robot_heartbeat](experiments/01_robot_heartbeat)，运行方式见文末“配套实验与运行”。

## 1. ROS 2 是什么

ROS 2 的完整名称是 Robot Operating System 2。虽然名称中有 Operating System，但它不是 Ubuntu、Windows 这一类操作系统，也不会代替操作系统管理硬件和进程。

ROS 2 是一套机器人软件开发框架，主要提供以下能力：

- 把复杂机器人系统拆分为多个职责明确的节点。
- 让节点通过标准接口交换数据和请求任务。
- 让节点能够在不同进程、不同计算机之间通信。
- 提供参数、日志、录包、回放、可视化和诊断工具。
- 通过 DDS 中间件提供自动发现和服务质量配置。

例如，一台移动机器人可以拆成以下节点：

```text
激光雷达节点 ──/scan──> 避障节点 ──/cmd_vel──> 底盘驱动节点
                           │
                           └──/safety_status──> 状态显示节点
```

如果所有功能都写在一个 Python 文件中，传感器、算法、底盘和显示会紧密耦合。修改一个模块可能影响整个程序，单个异常也可能使全部功能停止。ROS 2 通过节点和通信接口降低这种耦合。

需要注意：节点是 ROS 2 计算图中的执行参与者，不应简单等同于操作系统进程。初学实验通常让一个 Python 可执行程序创建一个节点；更复杂的程序也可以在同一进程中创建多个节点。

## 2. ROS 2 五层核心关系

ROS 2 工程可以按下面五层理解：

```text
工作空间 Workspace
└── 功能包 Package
    └── 节点 Node
        └── 通信接口 Topic / Service / Action
            └── 消息与接口数据 Message / Service / Action definition
```

### 2.1 工作空间

工作空间（Workspace）是 ROS 2 项目的开发与构建范围，可以把它理解为一组相关功能包共同工作的“工程容器”。开发者在工作空间中组织源码，`colcon` 在工作空间中分析功能包依赖、执行构建并生成安装结果。

工作空间本身不是一个功能包，也不是运行中的节点。它不会出现在 `ros2 node list` 中，更不会直接发送消息。它解决的是源码放在哪里、多个包如何一起构建、构建结果安装到哪里以及当前终端使用哪一组包的问题。

一个工作空间通常包含下面四类内容：

```text
ros2_ws/
├── src/       # 功能包源码，由开发者创建和维护
├── build/     # 构建中间文件，由 colcon 生成
├── install/   # 安装结果，由 colcon 生成
└── log/       # 构建日志，由 colcon 生成
```

四个目录的关系如下：

```text
src 中的功能包源码
        │
        │ colcon 读取 package.xml 并分析依赖
        ▼
build 中完成各包构建
        │
        ▼
install 中生成可被 ROS 2 查找的包、节点入口和资源
        │
        └── log 记录构建过程和错误信息
```

工作空间具有以下作用：

1. **集中管理源码**：同一个机器人项目的接口包、驱动包、感知包和控制包可以统一放在 `src` 中。
2. **统一构建多个包**：`colcon` 会发现 `src` 下的功能包，并根据 `package.xml` 中的依赖关系确定构建顺序。
3. **隔离项目环境**：不同项目可以使用不同工作空间，避免所有自定义包都混在同一目录。
4. **形成安装结果**：源码不能直接被 `ros2 run` 当成已安装节点使用；构建后生成的入口和资源位于 `install`。
5. **支持分层覆盖**：自定义工作空间可以叠加在系统 ROS 2 环境或另一个工作空间上。

例如一个巡检机器人工作空间可以包含：

```text
patrol_robot_ws/src/
├── patrol_interfaces/      # 自定义消息、服务和动作
├── lidar_adapter_py/       # 激光数据适配节点
├── patrol_controller_py/   # 巡检控制节点
├── robot_description_py/   # URDF、Xacro 和 RViz 配置
└── patrol_bringup_py/       # 参数与 Launch 启动文件
```

这些功能包属于同一个项目，但职责不同。修改 `patrol_interfaces` 后，依赖它的控制包也需要使用重新生成的接口；`colcon` 会根据依赖关系安排构建顺序。

创建空工作空间：

```bash
mkdir -p ~/patrol_robot_ws/src
cd ~/patrol_robot_ws
```

查看 `colcon` 能识别到哪些包：

```bash
colcon list
```

构建整个工作空间：

```bash
colcon build --symlink-install
```

构建完成后加载当前工作空间：

```bash
source install/setup.bash
```

加载以后，当前终端的 ROS 2 和 Python 搜索路径才会包含该工作空间的安装结果。这个操作只对当前终端生效；新开终端需要重新加载。

一个工作空间可以建立在另一个工作空间之上：

```text
Ubuntu 系统环境
└── /opt/ros/jazzy              # ROS 2 基础环境
    └── base_robot_ws           # 通用机器人底层包
        └── patrol_project_ws   # 当前巡检项目
```

对应的加载顺序是：

```bash
source /opt/ros/jazzy/setup.bash
source ~/base_robot_ws/install/setup.bash
source ~/patrol_project_ws/install/setup.bash
```

后加载的工作空间称为 Overlay，前面的环境称为 Underlay。出现同名功能包时，当前终端通常优先找到后加载工作空间中的版本。可以使用下面的命令确认实际使用的是哪个安装位置：

```bash
ros2 pkg prefix 功能包名
```

工作空间常见误区：

- **把工作空间当成功能包**：工作空间没有自己的 `package.xml`，其中的每个功能包才有。
- **在 `src` 中执行全量构建**：通常应回到工作空间根目录执行 `colcon build`。
- **直接修改 `install` 中的代码**：这些是生成结果，下一次构建会被覆盖；应修改 `src`。
- **构建完成后忘记 source**：构建成功不等于当前终端已经认识新包。
- **把多个工作空间无序写入 `.bashrc`**：容易造成同名包版本和路径来源混乱。
- **把 `build`、`install`、`log` 当成源码提交**：它们与机器和构建环境有关，应由构建重新生成。

### 2.2 功能包

功能包（Package）是 ROS 2 中代码组织、依赖声明、构建、安装和复用的基本单元。工作空间负责管理“一组包”，功能包负责封装“一类相关能力”。

例如“自主巡检机器人”是完整项目，不适合全部堆在一个包中。可以按职责拆分：

| 功能包 | 保存内容 | 主要职责 |
| --- | --- | --- |
| `patrol_interfaces` | `.msg`、`.srv`、`.action` | 定义系统公共接口 |
| `sensor_monitor_py` | Python 节点 | 接收传感器并判断异常 |
| `patrol_controller_py` | Python 节点 | 生成巡检控制命令 |
| `robot_description_py` | Xacro、RViz 配置 | 描述机器人模型 |
| `patrol_bringup_py` | Launch、YAML | 启动和配置完整系统 |

功能包具有以下职责：

1. **组织源码**：把相关节点、Python 模块和资源放在明确目录中。
2. **声明身份**：通过 `package.xml` 给出包名、版本、说明、维护者和许可证。
3. **声明依赖**：说明构建和运行时需要哪些 ROS 2 包或系统库。
4. **定义构建方式**：Python 节点包通常使用 `ament_python`。
5. **安装节点入口**：通过 `console_scripts` 让 `ros2 run` 能找到 Python 的 `main()`。
6. **安装非代码资源**：Launch、YAML、URDF、Xacro、RViz 配置和仿真世界需要安装到包的共享目录。
7. **支持复用与分发**：其他工作空间可以依赖已经安装的功能包。

本课程主要使用两类包：

#### 2.2.1 Python 节点功能包

Python 业务节点使用 `ament_python`，典型结构为：

```text
sensor_monitor_py/
├── package.xml
├── resource/
│   └── sensor_monitor_py
├── setup.cfg
├── setup.py
├── sensor_monitor_py/
│   ├── __init__.py
│   ├── sensor_publisher.py
│   └── safety_monitor.py
└── test/
```

外层目录代表 ROS 2 功能包，内层同名目录代表可以由 Python 导入的模块包。例如：

```python
from sensor_monitor_py.detector import AnomalyDetector
```

#### 2.2.2 接口定义功能包

自定义消息、服务和动作通常集中在独立接口包中：

```text
patrol_interfaces/
├── msg/
│   └── RobotStatus.msg
├── srv/
│   └── SetPatrol.srv
├── action/
│   └── RunPatrol.action
├── package.xml
└── CMakeLists.txt
```

接口生成工具按 ROS 2 规范使用相应构建规则，但本课程的业务节点仍全部使用 Python 编写。接口包只负责定义和生成数据结构，不负责实现机器人业务。

#### 2.2.3 package.xml 的作用

每个功能包都必须有 `package.xml`。例如：

```xml
<package format="3">
  <name>sensor_monitor_py</name>
  <version>0.1.0</version>
  <description>机器人传感器安全监控</description>
  <maintainer email="teacher@example.com">Teacher</maintainer>
  <license>Apache-2.0</license>

  <buildtool_depend>ament_python</buildtool_depend>
  <exec_depend>rclpy</exec_depend>
  <exec_depend>sensor_msgs</exec_depend>

  <export>
    <build_type>ament_python</build_type>
  </export>
</package>
```

如果 Python 代码中出现：

```python
import rclpy
from sensor_msgs.msg import LaserScan
```

那么功能包应声明 `rclpy` 和 `sensor_msgs` 运行依赖。不能因为开发机器已经安装这些包，就省略依赖声明。换一台机器后，`rosdep` 需要依靠清单判断要安装什么。

#### 2.2.4 setup.py 的作用

`setup.py` 定义 Python 模块、资源和节点入口。最关键的是 `console_scripts`：

```python
entry_points={
    'console_scripts': [
        'sensor_publisher = sensor_monitor_py.sensor_publisher:main',
        'safety_monitor = sensor_monitor_py.safety_monitor:main',
    ],
}
```

以第一行为例：

```text
sensor_publisher = sensor_monitor_py.sensor_publisher : main
       │                       │                        │
       │                       │                        └── 入口函数
       │                       └── Python 模块路径
       └── ros2 run 使用的可执行入口名
```

运行：

```bash
ros2 run sensor_monitor_py sensor_publisher
```

`ros2 run` 不会按当前目录直接寻找 `sensor_publisher.py`，而是从已经加载的安装空间中找到包和注册入口。

#### 2.2.5 一个包可以包含多少节点

一个功能包可以包含一个节点，也可以包含多个高度相关的节点。例如发布模拟数据和监控数据的两个教学节点可以放在 `sensor_monitor_py` 中。

适合放在同一个包中的情况：

- 节点属于同一功能领域。
- 共享相同的 Python 业务模块。
- 版本和发布周期一致。
- 通常一起维护和分发。

适合拆成不同包的情况：

- 接口需要被多个项目共同使用。
- 驱动、算法、模型和启动配置的职责明显不同。
- 某部分需要独立替换、部署或发布。
- 包之间的依赖方向可以因此变得更清晰。

包不是越多越专业。拆分过细会增加依赖和维护成本；所有内容塞进一个包又会失去边界。判断依据是职责和复用关系。

#### 2.2.6 功能包与节点的区别

功能包是磁盘上的工程和分发单位，节点是运行时计算图中的参与者。

```text
磁盘上的功能包 sensor_monitor_py
├── sensor_publisher.py ──运行后──> /sensor_publisher 节点
└── safety_monitor.py   ──运行后──> /safety_monitor 节点
```

没有运行任何入口时，功能包仍然存在，但计算图中不会出现对应节点。关闭节点进程也不会删除功能包源码。

#### 2.2.7 常用功能包命令

```bash
ros2 pkg list
ros2 pkg prefix sensor_monitor_py
ros2 pkg executables sensor_monitor_py
colcon list
```

- `ros2 pkg list`：列出当前环境能够发现的已安装包。
- `ros2 pkg prefix`：显示当前使用的包安装位置。
- `ros2 pkg executables`：显示包注册的节点入口。
- `colcon list`：显示当前工作空间源码中可识别的包。

注意：`colcon list` 能看到源码包，不表示当前终端已经加载了它的安装结果；`ros2 pkg list` 看的是当前环境能够发现的安装包。

功能包常见误区：

- **把 Python 文件名当成功能包名**：`ros2 run` 第一个参数来自 `package.xml`。
- **把功能包名当节点名**：一个包可以启动多个名称不同的节点。
- **包中有 Python 文件就能 ros2 run**：还需要 `console_scripts` 入口并完成构建安装。
- **只在 setup.py 写依赖**：ROS 依赖还应在 `package.xml` 中正确声明。
- **新增 Launch/YAML 后找不到**：这些资源需要写入 `data_files` 并重新构建。
- **两个包互相依赖**：循环依赖会破坏清晰的构建顺序，应重新划分公共接口或业务模块。

### 2.3 节点

节点（Node）是 ROS 2 计算图中的基本参与者。节点为一组发布者、订阅者、服务、动作、参数、定时器和日志提供统一的名称与运行上下文，并负责实现某项机器人功能。

例如一个移动机器人可以包含：

```text
/lidar_driver       读取激光设备并发布 /scan
/obstacle_detector  订阅 /scan，发布 /obstacle_warning
/patrol_controller  订阅传感器和里程计，发布 /cmd_vel
/status_recorder    订阅状态并写入记录
```

#### 2.3.1 节点不是 Python 类本身

下面的类定义了“怎样创建一个节点”：

```python
class SafetyMonitor(Node):
    def __init__(self):
        super().__init__('safety_monitor')
```

只有程序执行并创建实例后，运行时计算图中才会出现 `/safety_monitor`：

```python
node = SafetyMonitor()
```

Python 文件、Node 子类、Node 对象和操作系统进程是相关但不同的概念：

| 概念 | 示例 | 含义 |
| --- | --- | --- |
| Python 文件 | `safety_monitor.py` | 磁盘上的源码文件 |
| Node 子类 | `SafetyMonitor` | 创建节点的代码模板 |
| Node 对象 | `SafetyMonitor()` | 运行期间存在的节点实例 |
| 节点名 | `/safety_monitor` | 计算图中使用的名称 |
| 进程 | `python3 ...` | 操作系统正在执行的程序 |

初学实验通常是“一个入口创建一个节点”。但是 ROS 2 允许一个 Python 进程管理多个 Node 对象，因此不能把“节点”绝对定义成“独立进程”。

#### 2.3.2 节点为什么要有明确职责

节点负责的功能应该能够用一句话说明。例如“发布激光数据”或“根据激光生成避障速度”。职责清晰带来以下好处：

- 某个传感器驱动崩溃时，其他节点仍可能继续运行或进入安全状态。
- 算法节点可以把真实传感器替换为 rosbag2 回放数据。
- 同一个监控节点可以通过重映射连接不同设备。
- 节点可以按计算量部署到不同计算机。
- 调试时可以通过计算图定位输入、输出和责任边界。

但节点也不应无限拆分。若两个小功能始终共享大量内部状态、没有独立部署价值，把它们强行分成节点会增加通信和调试成本。

#### 2.3.3 节点可以拥有的实体

一个节点可以同时拥有多个通信和调度实体：

```text
/patrol_controller
├── Subscription: /scan
├── Subscription: /odom
├── Publisher:    /cmd_vel
├── Publisher:    /patrol/status
├── Service:      /patrol/emergency_stop
├── ActionServer: /patrol_distance
├── Timer:        10 Hz 控制循环
└── Parameters:   safe_distance、forward_speed 等
```

这些实体都属于同一个节点，但通信语义不同：话题传递数据流，服务处理短请求，动作管理长任务，参数保存配置，定时器触发周期工作。

#### 2.3.4 节点名称

创建节点：

```python
super().__init__('safety_monitor')
```

计算图中的名称通常显示为：

```text
/safety_monitor
```

节点名称用于：

- `ros2 node list/info` 查询。
- 日志标识。
- 参数寻址。
- Launch 中的命名和命名空间配置。
- 诊断问题时确认信息来源。

同一系统中应尽量保持节点完整名称唯一。ROS 2 可能允许同名节点同时存在，但这会使参数、服务和命令行诊断产生歧义，并不等于后启动节点自动替换前一个节点。

#### 2.3.5 命名空间

多机器人系统可以使用命名空间：

```text
/robot_01/safety_monitor
/robot_02/safety_monitor
```

启动时设置：

```bash
ros2 run sensor_monitor_py safety_monitor \
  --ros-args -r __ns:=/robot_01
```

如果节点代码使用相对话题名 `sensor/status`，位于 `/robot_01` 命名空间后，话题可以解析为 `/robot_01/sensor/status`。这样同一份 Python 代码能够为多台机器人复用。

#### 2.3.6 节点的初始化

```python
import rclpy
from rclpy.node import Node


class RobotNode(Node):
    def __init__(self):
        super().__init__('robot_node')
        self.get_logger().info('节点已经初始化')
```

`super().__init__()` 必须执行，因为父类负责创建 ROS 2 节点句柄、名称、日志、时钟和通信实体管理能力。只定义普通 Python 类并不会自动成为 ROS 2 节点。

#### 2.3.7 节点的运行

```python
def main(args=None):
    rclpy.init(args=args)
    node = RobotNode()

    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.try_shutdown()
```

完整顺序：

1. `rclpy.init()` 初始化 ROS 2 上下文。
2. 创建 Node 对象。
3. `spin()` 让执行器等待并处理回调。
4. 收到退出信号后离开 `spin()`。
5. `destroy_node()` 释放节点实体。
6. `try_shutdown()` 关闭上下文。

#### 2.3.8 spin 与回调

节点不会因为创建了定时器或订阅者，就自动在后台执行 Python 函数。执行器必须获得运行机会：

```python
rclpy.spin(node)
```

执行器可能调度：

- 订阅回调。
- 定时器回调。
- 服务回调。
- 动作回调。
- 异步 Future 的完成回调。

如果某个回调长时间阻塞，其他回调可能延迟。执行器、回调组和并发问题将在第六单元详细讲解。

#### 2.3.9 节点内部状态

节点经常使用实例属性保存状态：

```python
self.last_distance = None
self.message_count = 0
self.enabled = False
```

实例属性使多个回调能够共享数据，但也带来两个问题：

- 数据是否仍然新鲜，例如 `last_distance` 是否来自几秒前。
- 多线程执行器下是否存在并发修改。

因此共享状态不仅要保存值，还要保存时间、来源和有效性；并发情况下还要设计回调组或同步保护。

#### 2.3.10 节点的参数

```python
self.declare_parameter('safe_distance', 0.6)
safe_distance = self.get_parameter('safe_distance').value
```

参数属于节点。它适合保存安全距离、发布周期、设备端口等运行配置，不适合代替高频话题传递连续传感器数据。

#### 2.3.11 节点日志

```python
self.get_logger().info('节点启动')
self.get_logger().warning('距离接近阈值')
self.get_logger().error('传感器数据超时')
```

日志自动包含级别、时间和节点名，比普通 `print()` 更适合多节点系统。日志内容应说明发生了什么、涉及哪个值，以及下一步如何排查。

#### 2.3.12 节点的运行状态与生命周期

普通节点创建后通常立即工作。需要受控启动的设备节点可以使用生命周期节点，将状态分为未配置、未激活、已激活等阶段。第五单元会专门讲解。

这里先区分三个概念：

- 进程存在：操作系统中程序正在运行。
- 节点存在：计算图中能够发现 Node 对象。
- 业务可用：传感器、参数和通信已经准备好，节点能够正确提供功能。

三者不能简单画等号。节点能够被 `ros2 node list` 看到，不代表传感器数据一定有效。

#### 2.3.13 节点调试命令

列出节点：

```bash
ros2 node list
```

查看一个节点的通信实体：

```bash
ros2 node info /patrol_controller
```

临时修改节点名：

```bash
ros2 run 包名 入口名 --ros-args -r __node:=新节点名
```

检查节点时要结合其他命令：

```bash
ros2 topic list -t
ros2 service list -t
ros2 action list -t
ros2 param list /节点名
```

节点常见误区：

- **节点就是 Python 文件**：文件只是源码，运行并创建 Node 对象后才有节点。
- **节点一定等于进程**：一个进程可以创建多个节点。
- **节点在线等于功能正常**：通信实体、传感器新鲜度和业务状态仍需检查。
- **一个节点只能有一个发布者**：节点可以拥有多个不同实体。
- **节点越多越模块化**：过度拆分也会增加通信与维护成本。
- **节点名、入口名、文件名必须相同**：可以不同，但命名应清晰一致，避免人为混乱。

### 2.4 通信接口

通信接口规定节点如何交换数据。最常见的是话题、服务和动作：

| 接口 | 通信方式 | 典型用途 |
| --- | --- | --- |
| Topic | 持续、异步的数据流 | 激光、图像、里程计、速度命令 |
| Service | 一次请求、一次响应 | 查询状态、清零、切换模式 |
| Action | 可反馈、可取消的长任务 | 导航、巡检、机械臂运动 |

### 2.5 消息与接口数据

消息规定传输数据的字段和类型。例如 `geometry_msgs/msg/Twist` 包含线速度和角速度。服务接口还要定义请求和响应，动作接口还要定义目标、结果和反馈。

这五层不是“一个目录套一个文件”的绝对关系。例如消息接口通常由独立接口包生成，然后被多个 Python 节点包使用。五层关系主要用于理解从工程组织到运行时通信的职责分工。

## 3. ROS 2 的软件分层

### 3.1 Python 应用代码

本课程编写的 Node 子类、回调函数、发布者和订阅者属于应用代码。它们只关注机器人业务，例如“距离小于 0.5 米时报警”。

### 3.2 rclpy

`rclpy` 是 ROS 2 的 Python 客户端库，提供：

- `Node`：节点类。
- Publisher 和 Subscription：话题发布与订阅。
- Service 和 Client：服务端与客户端。
- ActionServer 和 ActionClient：动作通信。
- Timer：周期回调。
- Parameter：参数。
- Executor 和 CallbackGroup：回调调度。
- QoSProfile：通信服务质量。

### 3.3 rcl 与 RMW

`rclpy` 下方是与语言无关的 ROS 客户端公共层。RMW 是 ROS Middleware 接口，它让上层代码不必直接绑定某一种 DDS 实现。

### 3.4 DDS

DDS 负责参与者发现、端点匹配、数据传输和 QoS 等底层能力。第一单元不要求掌握 DDS 协议细节，但必须知道以下事实：

- ROS 2 默认没有 ROS 1 式的中心 Master。
- 节点能够通过中间件自动发现其他端点。
- 话题名称、消息类型和 QoS 需要匹配或兼容。
- 网络、域编号和中间件配置都可能影响节点发现。

## 5. 工作空间

### 5.1 标准结构

```text
ros2_ws/
├── src/       # 源码目录，需要开发者创建和维护
├── build/     # 各包的构建中间文件，由 colcon 生成
├── install/   # 安装后的包、入口和资源，由 colcon 生成
└── log/       # 构建日志，由 colcon 生成
```

创建工作空间：

```bash
mkdir -p ~/ros2_ws/src
cd ~/ros2_ws
```

`src` 目录中可以继续按项目分类，但 `colcon` 必须能够在其中找到包含 `package.xml` 的功能包。

### 5.2 四个目录的区别

| 目录 | 是否手动维护 | 是否提交为课程源码 | 作用 |
| --- | --- | --- | --- |
| `src` | 是 | 是 | 保存功能包源代码 |
| `build` | 否 | 否 | 保存构建中间结果 |
| `install` | 否 | 否 | 保存可被 ROS 2 查找的安装结果 |
| `log` | 否 | 否 | 保存构建过程日志 |

不要直接修改 `build` 或 `install` 中的文件。下一次构建可能覆盖修改，而且源码仍未改变。

### 5.3 工作空间叠加

ROS 2 支持 underlay 与 overlay：

```bash
source /opt/ros/jazzy/setup.bash   # 系统 underlay
source ~/base_ws/install/setup.bash
source ~/project_ws/install/setup.bash  # 最上层 overlay
```

后加载的工作空间优先级更高。若多个工作空间包含同名包，当前终端可能使用最后加载的版本。排查版本问题时可以执行：

```bash
ros2 pkg prefix 包名
```

## 6. Python 功能包

### 6.1 创建 ament_python 包

```bash
cd ~/ros2_ws/src
ros2 pkg create robot_basics_py \
  --build-type ament_python \
  --license Apache-2.0 \
  --dependencies rclpy
```

功能包名称通常使用小写字母、数字和下划线。名称应表达功能，不使用空格和中文。

### 6.2 目录结构

```text
robot_basics_py/
├── package.xml
├── resource/
│   └── robot_basics_py
├── setup.cfg
├── setup.py
├── robot_basics_py/
│   ├── __init__.py
│   └── heartbeat_node.py
└── test/
```

外层 `robot_basics_py` 是 ROS 2 功能包目录，内层同名目录是 Python 模块目录。两者名称通常相同，但作用不同。

### 6.3 package.xml

`package.xml` 是功能包清单。常用标签：

```xml
<name>robot_basics_py</name>
<version>0.1.0</version>
<description>机器人基础节点</description>
<maintainer email="teacher@example.com">Teacher</maintainer>
<license>Apache-2.0</license>
<buildtool_depend>ament_python</buildtool_depend>
<exec_depend>rclpy</exec_depend>
```

- `buildtool_depend` 声明构建工具。
- `exec_depend` 声明运行时依赖。
- 代码导入了某个 ROS 2 包，不应只因为本机已经安装就省略依赖声明。

完整依赖有两个作用：`colcon` 能确定构建顺序，`rosdep` 能在新环境中安装缺少的软件包。

### 6.4 setup.py

`setup.py` 告诉 Python 打包工具如何安装模块、资源和命令入口：

```python
entry_points={
    'console_scripts': [
        'robot_heartbeat = robot_basics_py.heartbeat_node:main',
    ],
}
```

这一行包含三个不同名称：

- `robot_heartbeat`：`ros2 run` 使用的可执行入口名。
- `robot_basics_py.heartbeat_node`：Python 模块路径。
- `main`：进入模块后调用的函数。

修改入口后必须重新构建，因为安装空间中的命令入口需要重新生成。

### 6.5 setup.cfg

```ini
[develop]
script_dir=$base/lib/robot_basics_py
[install]
install_scripts=$base/lib/robot_basics_py
```

它让脚本安装到 ROS 2 能按照包名查找的目录。包能构建但 `ros2 run` 提示没有可执行入口时，需要检查此文件和 `console_scripts`。

### 6.6 resource 标记与 __init__.py

`resource/robot_basics_py` 是 ament 包索引标记。`__init__.py` 让内层目录成为可导入的 Python 包。两者内容可以很少，但不能随意删除。

## 7. 节点

### 7.1 节点的职责

节点通常承担一个清晰职责。例如：

- `laser_driver`：读取设备并发布扫描。
- `obstacle_detector`：订阅扫描并判断障碍物。
- `base_controller`：接收速度命令并控制电机。
- `status_logger`：记录系统状态。

“一个节点只做一件事”是设计方向，不是要求每个函数都拆成节点。拆分时要考虑运行周期、故障边界、部署位置和接口成本。

### 7.2 节点名称

节点名称用于计算图和日志。建议在同一系统中保持名称唯一，重名会使命令行诊断和参数寻址变得含糊，但不能把重名简单理解为“后启动节点自动替换前一个节点”。

查看节点：

```bash
ros2 node list
ros2 node info /robot_heartbeat
```

### 7.3 最小 rclpy 节点

```python
import rclpy
from rclpy.node import Node


class HeartbeatNode(Node):
    def __init__(self):
        super().__init__('robot_heartbeat')
        self.get_logger().info('节点已经创建')


def main(args=None):
    rclpy.init(args=args)
    node = HeartbeatNode()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.try_shutdown()
```

### 7.4 代码逐行解释

- `import rclpy`：导入 ROS 2 Python 客户端库。
- `from rclpy.node import Node`：导入节点基类。
- `class HeartbeatNode(Node)`：自定义节点继承 Node。
- `super().__init__('robot_heartbeat')`：初始化 Node，并设置运行时节点名。
- `rclpy.init()`：初始化当前进程的 ROS 2 上下文。
- `rclpy.spin(node)`：让执行器等待和处理回调。
- `destroy_node()`：释放节点创建的实体和资源。
- `try_shutdown()`：在上下文尚未关闭时安全关闭。

### 7.5 spin 不是业务死循环

`spin` 等待以下事件：

- 定时器到期。
- 订阅消息到达。
- 服务请求到达。
- 动作事件到达。
- 异步 Future 完成。

如果不进入 `spin`，节点虽然创建过，但程序可能立即结束，定时器和订阅回调也没有机会执行。

## 8. 定时器与回调

创建 1 秒定时器：

```python
self.timer = self.create_timer(1.0, self.on_timer)
```

第二个参数传入的是函数对象 `self.on_timer`，不能写成 `self.on_timer()`。加括号会在创建定时器时立即调用函数，并把返回值当回调。

```python
def on_timer(self):
    self.get_logger().info('heartbeat')
```

定时器周期不是硬实时保证。如果同一执行器中的其他回调耗时过长，定时回调可能延迟。

## 9. 日志

节点日志比普通 `print()` 更适合 ROS 2 程序，因为日志自带时间、级别和节点名：

```python
self.get_logger().debug('调试细节')
self.get_logger().info('节点正常运行')
self.get_logger().warning('数据即将超限')
self.get_logger().error('设备读取失败')
```

启动时设置日志级别：

```bash
ros2 run robot_basics_py robot_heartbeat --ros-args --log-level debug
```

日志级别应表达严重程度。正常循环不要不断输出 error，真正故障也不要只输出 debug。

## 10. 计算图

ROS 2 中正在运行的节点和它们的通信连接组成计算图。计算图是动态的：节点可以随时加入、退出，端点也可以在运行过程中创建和销毁。

常用检查命令：

```bash
ros2 node list
ros2 node info /节点名
ros2 topic list -t
ros2 service list -t
ros2 action list -t
```

图形化查看：

```bash
rqt_graph
```

计算图适合回答：“谁在发布这个话题？”“订阅者是否存在？”“节点之间是否通过预期话题连接？”它不能直接证明消息内容正确，因此还要配合 `ros2 topic echo` 等命令。

## 11. 节点发现与 ROS_DOMAIN_ID

同一 DDS 域中的参与者会交换发现信息，包括端点、话题类型和 QoS。发现需要时间，因此发布者刚启动时立即发布一次瞬时消息，稍后启动的订阅者可能收不到。

设置域编号：

```bash
export ROS_DOMAIN_ID=42
```

只有域设置兼容的节点才会互相发现。多人在同一局域网上课时，可以为不同小组分配不同 Domain ID，减少彼此节点干扰。

当两台计算机无法发现对方时，依次检查：

1. ROS 2 发行版和 RMW 配置是否兼容。
2. `ROS_DOMAIN_ID` 是否一致。
3. 是否处于可互通网络。
4. 防火墙、组播或虚拟机网络模式是否阻断发现。
5. 是否设置了只允许本机通信的环境选项。

不要看到“节点列表为空”就立刻修改 Python 代码，先检查运行环境和发现条件。

## 12. 消息与接口概览

查看消息结构：

```bash
ros2 interface show std_msgs/msg/String
ros2 interface show geometry_msgs/msg/Twist
```

Python 中创建消息对象：

```python
from std_msgs.msg import String

message = String()
message.data = 'READY'
```

消息字段具有确定类型。不能把任意字典或字符串直接当成另一个消息类型发布。

接口完整名称：

```text
功能包名 / 接口种类 / 接口名
std_msgs/msg/String
std_srvs/srv/SetBool
example_interfaces/action/Fibonacci
```

第一单元只建立整体认识。话题和消息在第二单元展开，服务与动作在第三单元展开。

## 13. colcon 构建系统

### 13.1 colcon 的职责

`colcon` 是构建编排工具。它读取 `src` 中的包和依赖，按顺序调用每个包对应的构建工具，再把结果安装到 `install`。

它不负责自动修复 Python 语法，也不代表构建成功后节点业务一定正确。

### 13.2 基本构建

```bash
cd ~/ros2_ws
colcon build
```

必须在工作空间根目录运行。第一次构建后会出现 `build`、`install`、`log`。

### 13.3 开发阶段使用符号链接

```bash
colcon build --symlink-install
```

对于 Python 源码，符号链接模式可以减少重复复制。修改已安装的 Python 模块后，停止旧进程并重新运行通常即可看到变化。

以下内容修改后仍建议重新构建并重新加载环境：

- `setup.py` 中的入口和资源安装规则。
- `package.xml` 依赖。
- 自定义消息、服务和动作定义。
- 新增 Launch、配置、URDF 等需要进入安装空间的资源。

### 13.4 构建指定包

```bash
colcon build --symlink-install --packages-select robot_basics_py
```

构建目标包及其依赖链中的包：

```bash
colcon build --symlink-install --packages-up-to robot_basics_py
```

查看实时构建输出：

```bash
colcon build --event-handlers console_direct+
```

### 13.5 安装依赖

```bash
cd ~/ros2_ws
rosdep install --from-paths src --ignore-src -r -y
```

`rosdep` 依据 `package.xml` 安装系统依赖。若清单漏写依赖，本机可能因碰巧装过而运行，新机器却会失败。

构建完成后执行：

```bash
source install/setup.bash
```

```bash
source /opt/ros/jazzy/setup.bash
cd ~/ros2_ws
```

## 15. 包名、入口名、模块名和节点名

这是第一单元最容易混淆的四个名称：

| 名称 | 示例 | 出现位置 |
| --- | --- | --- |
| 功能包名 | `robot_basics_py` | `package.xml`、`ros2 run` 第一个参数 |
| 入口名 | `robot_heartbeat` | `setup.py`、`ros2 run` 第二个参数 |
| Python 模块 | `heartbeat_node.py` | Python 包目录 |
| 节点名 | `/robot_heartbeat` | `Node` 构造、计算图和日志 |

运行命令：

```bash
ros2 run robot_basics_py robot_heartbeat
```

它不会直接寻找当前目录下的 `heartbeat_node.py`，而是从已加载的安装空间中寻找功能包注册的入口。

## 16. ROS 2 名称与命令行参数

临时修改节点名：

```bash
ros2 run robot_basics_py robot_heartbeat \
  --ros-args -r __node:=heartbeat_01
```

添加命名空间：

```bash
ros2 run robot_basics_py robot_heartbeat \
  --ros-args -r __ns:=/robot_01
```

节点完整名称将是 `/robot_01/robot_heartbeat`。命名空间在多机器人系统中用于隔离相同功能的节点和相对话题。

## 17. 常见错误速查

### 17.1 `ros2: command not found`

检查 ROS 2 是否安装，以及是否加载 `/opt/ros/jazzy/setup.bash`。

### 17.2 `Package 'robot_basics_py' not found`

依次检查：

```bash
pwd
ls src
colcon list
ls install
source install/setup.bash
ros2 pkg prefix robot_basics_py
```

### 17.3 `No executable found`

包能找到但入口不存在。检查 `setup.py` 的 `console_scripts`、`setup.cfg` 和入口函数，然后重新构建。

### 17.4 `ModuleNotFoundError`

入口已经启动，但 Python 导入失败。检查内层模块目录、`__init__.py`、模块拼写和 `package.xml` 依赖。

### 17.5 节点启动后立即退出

检查终端中的 Python traceback。也要确认程序是否进入 `rclpy.spin()`，以及构造节点时是否发生异常。

### 17.6 修改代码没有生效

确认旧节点已停止、构建时使用 `--symlink-install`。如果改了入口或安装规则，必须重新构建并重新 source。

### 17.7 两个终端看不到相同节点

检查两个终端是否加载相同环境、是否使用相同 Domain ID。跨计算机时继续检查网络和防火墙。
