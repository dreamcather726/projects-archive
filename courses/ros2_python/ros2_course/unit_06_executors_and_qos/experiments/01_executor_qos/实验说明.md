# 实验 6：慢回调、执行器并发与 QoS 不兼容

## 为什么要做这个实验

机器人中常见的“偶发卡顿”和“话题明明存在却收不到数据”，往往不是算法错误，而是回调阻塞、回调组配置或 QoS 不兼容。只阅读概念很难形成直觉，本实验用同一节点在三种配置下制造可观察差异。

## 实验的作用

- 直接比较单线程与多线程执行器下的回调延迟。
- 证明多线程执行器还需要合理的回调组才能产生并发效果。
- 观察可靠性 QoS 不兼容导致零消息接收。
- 学会用频率、计数和端点信息诊断，而不是只看“有没有报错”。

## 实验重点

1. 慢回调在单线程执行器中会阻塞所有其他回调。
2. 两个回调放在不同互斥组后，多线程执行器才有机会并发调度。
3. 发布者提供 best effort，而订阅者要求 reliable 时不兼容。
4. 增大队列不能消除回调本身的阻塞。

## 运行步骤

构建：

```bash
source /opt/ros/jazzy/setup.bash
cd <课程仓库>/ros2_course/unit_06_executors_and_qos/experiments/01_executor_qos/ros2_ws
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install
source install/setup.bash
```

终端 1 启动 20 Hz 模拟传感器：

```bash
ros2 run executor_qos_py sensor_load
```

终端 2 先运行单线程版本：

```bash
ros2 run executor_qos_py single_thread_demo
```

观察每当“慢任务开始”后，接收计数会暂停增长。然后停止并运行：

```bash
ros2 run executor_qos_py multi_thread_demo
```

慢任务执行期间，传感器回调仍会处理消息。最后测试 QoS 不兼容：

```bash
ros2 run executor_qos_py multi_thread_demo --ros-args -p request_reliable:=true
ros2 topic info /fast_sensor --verbose
```

此时发布者仍存在，但订阅计数应保持为零。

## 预期现象

- 单线程模式：慢任务的 1 秒阻塞期间没有传感器回调。
- 多线程模式：慢任务和传感器回调可交错执行。
- QoS 不兼容模式：不一定抛出 Python 异常，但无法收到消息。

## 验收任务

1. 把两个回调放回同一个互斥组，说明多线程为何失效。
2. 把发布者改成 reliable，再证明 reliable 订阅者可以连接。
3. 增加共享变量并使用锁保护，解释临界区为什么应尽量短。
4. 统计 10 秒内的发送数和接收数，比较三种配置。

## 常见问题

- 多线程仍然完全阻塞：两个回调可能处于同一互斥组。
- `request_reliable` 修改后仍收得到消息：确认旧节点已停止，使用 verbose 查看实际 QoS。
- 日志顺序偶尔变化：并发回调本来就不能依赖固定日志顺序。
- 以为 Python 多线程一定加速计算：本实验强调的是等待型回调的响应性，不是 CPU 密集计算加速。
