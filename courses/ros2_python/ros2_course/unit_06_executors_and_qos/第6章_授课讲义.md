# 第六单元知识点详解

## ROS 2 执行器、回调组与 QoS

这份文档讲解 `rclpy` 如何等待事件和调度回调，以及慢回调、并发、回调组、死锁和 QoS 兼容对机器人响应性的影响。

配套实验位于 [experiments/01_executor_qos](experiments/01_executor_qos)。

## 1. 执行器在做什么

节点创建订阅、定时器或服务后，这些对象不会自己运行回调。执行器等待底层实体就绪，再选择回调执行。`rclpy.spin(node)` 是使用默认执行器持续处理事件的便捷方式。

常见事件来源：消息到达、定时器到期、服务请求、动作事件、Future 完成和 Guard Condition。

单线程执行器一次只能执行一个回调。因此任何 `sleep()`、长计算、同步 I/O 都会延迟其他回调。

## 2. 多线程执行器不等于自动并行

`MultiThreadedExecutor` 提供多个工作线程，但回调能否同时执行还受回调组限制。默认回调组是互斥组；所有实体都留在默认组时，即使使用多线程执行器，也可能仍一次只执行一个回调。

### 互斥回调组

同组回调不能并发，适合访问同一非线程安全设备或必须串行的控制逻辑。

### 可重入回调组

允许回调并发甚至同一回调重入，适合本身线程安全并且确实需要同时处理多个请求的逻辑。

### 不同互斥组

不同组之间可并发，但每个组内部仍串行。这往往比把所有内容放入可重入组更容易推理。

## 3. 并发安全

多个回调修改同一列表、状态机或设备句柄时会产生竞争。可以使用锁，但持锁范围应只包含共享状态读写，不要持锁等待服务、网络或长计算，否则锁会把系统重新变成串行甚至造成死锁。

Python 多线程更适合 I/O 等待和提高回调响应性。CPU 密集型纯 Python 计算未必因线程增加而加速，可以考虑 NumPy、独立进程或外部加速模块。

## 4. 服务死锁示例

定时回调发起同步服务调用并等待；服务响应完成回调与定时器在同一互斥组；定时回调不结束，完成回调无法执行，于是永久等待。

解决思路：优先异步调用；或把相关实体放入允许并发的回调组并使用多线程执行器；最重要的是画出“谁在等谁”。

## 5. QoS 为什么存在

机器人数据特征不同：地图需要后来订阅者也能得到最新版本；激光雷达更在意最新帧；控制命令过期后不应继续执行；心跳需要发现期限违约。一个固定通信策略无法满足所有场景。

主要策略：

- History/Depth：保留哪些历史样本和数量。
- Reliability：可靠或尽力而为。
- Durability：只收在线后的数据，或让后来订阅者获得已保存样本。
- Deadline：期望数据更新间隔。
- Lifespan：消息有效时间。
- Liveliness/Lease Duration：端点存活声明和租约。

## 6. QoS 兼容思维

订阅者提出它最低需要的服务质量，发布者提供它能够保证的服务质量。订阅者要求 reliable，而发布者只提供 best effort 时无法匹配。

这类不兼容可能不抛出业务代码异常，因此必须查看端点：

```bash
ros2 topic info /scan --verbose
```

不要把所有话题都改为 reliable。网络不稳定、高频传感器场景中，重传旧帧可能增加延迟，影响实时决策。

## 7. 典型场景设计

- 激光/摄像头：通常使用传感器数据配置，重视新鲜度。
- 控制命令：小深度，并考虑可靠性和消息过期。
- 静态地图/配置：需要后来订阅者得到最近样本。
- 状态心跳：结合 deadline 或 liveliness 监控。
- 调试日志：根据重要性和带宽选择策略。

## 8. 测量而不是猜测

比较发送频率、接收频率、回调耗时和端到端延迟。制造慢回调、网络抖动和不同 QoS，再记录结果。只有“线程数变多了”不能证明系统更好。
