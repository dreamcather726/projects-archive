# 第 6 模块：ROS 2 执行器调度模型与 QoS 服务质量

课程材料：[知识点详解](第6章_授课讲义.md) · [实验说明与代码](experiments/01_executor_qos/实验说明.md)

## 内容范围

- `rclpy` 等待事件和调度回调的机制。
- 单线程/多线程执行器与回调组。
- QoS 策略选择、不兼容和丢包问题排查。

## 详细知识点

### 1. 回调与执行器

- 订阅、定时器、服务、动作和 Future 完成事件都可能触发回调。
- `spin()` 的作用不是死循环业务逻辑，而是让执行器等待并分派就绪回调。
- `spin_once()`、`spin_until_future_complete()` 的适用场景。
- `SingleThreadedExecutor` 的顺序执行特点。
- `MultiThreadedExecutor` 提供并发调度机会，但不自动保证线程安全或性能提升。
- 回调执行时间、触发频率、排队延迟和系统响应性的关系。

### 2. 回调组

- 默认回调组是互斥回调组。
- `MutuallyExclusiveCallbackGroup`：组内回调不并发执行。
- `ReentrantCallbackGroup`：允许组内不同实例甚至同一回调重入。
- 不同互斥组可以由多线程执行器并发调度。
- 为订阅、定时器、客户端和服务指定 `callback_group`。
- 所有实体都留在默认互斥组时，多线程执行器可能表现得仍像单线程。

### 3. 并发安全与死锁

- 共享列表、状态对象、设备接口和文件写入的竞争条件。
- 使用锁时缩小临界区，避免持锁执行网络或服务等待。
- 回调内同步等待服务或动作结果可能造成死锁。
- 优先采用异步调用和完成回调。
- CPU 密集型 Python 回调受到解释器执行模型影响；多线程更适合等待型工作，重计算应考虑进程隔离或向量化。
- 用时间戳和日志测量回调延迟，而不是凭感觉判断并发效果。

### 4. QoS 策略

- History：保留最近数据或保留全部数据。
- Depth：保留最近数据时的队列深度。
- Reliability：可靠传输与尽力而为。
- Durability：仅接收在线后数据与保留历史样本给后加入订阅者。
- Deadline：期望数据更新间隔。
- Lifespan：消息超过有效期后不再交付。
- Liveliness 与 Lease Duration：端点存活性检测。
- `QoSProfile` 与预定义传感器数据配置。

### 5. QoS 兼容与场景选择

- 发布端提供能力、订阅端提出要求的兼容关系。
- 高频激光雷达：通常重视低延迟，允许少量丢包。
- 控制命令：根据安全需求选择可靠性、深度与过期时间。
- 地图或静态配置：让后加入的订阅者能拿到最近状态。
- 状态心跳：结合 deadline/liveliness 检测异常。
- 不能只靠增大队列深度解决慢回调问题。

### 6. 诊断与验证

- `ros2 topic info --verbose` 查看端点 QoS。
- 使用发布/订阅事件回调观察 QoS 不兼容、deadline 丢失和消息丢失。
- 对比发布频率、接收频率、回调耗时和端到端延迟。
- 制造慢订阅者、突发流量和网络抖动，验证策略效果。
- 区分 DDS 层丢弃、队列覆盖与应用逻辑主动过滤。

## 课堂演示

1. 在定时回调中加入阻塞，观察订阅回调延迟。
2. 分别使用单线程、多线程执行器和不同回调组比较现象。
3. 制造服务同步等待死锁，再改为异步调用。
4. 配置不兼容 QoS，使用命令行定位“有话题但收不到消息”。
5. 对激光数据比较可靠与尽力而为策略下的延迟和接收率。

## 实验任务

实现并发安全的传感器融合节点：

- 高频激光订阅、低频状态订阅、周期诊断和异步服务客户端分别放入合适回调组。
- 使用多线程执行器运行并保护共享状态。
- 为各话题设计不同 QoS，并说明选择理由。
- 记录回调耗时、接收频率、超时次数和 QoS 事件。

## 常见问题

- 使用多线程执行器但所有回调仍在默认互斥组。
- 回调中使用 `sleep()` 或同步服务调用阻塞执行器。
- 多个回调无保护地修改同一个对象。
- 名称和类型都正确，却因 QoS 不兼容无法通信。
- 盲目增加线程数或队列深度，反而加重延迟和内存占用。

## 验收标准

- 能画出节点内各回调及其回调组关系。
- 慢回调不会阻塞必须及时处理的安全回调。
- 共享状态不存在可复现的数据竞争。
- 能根据命令行信息判断 QoS 是否兼容，并解释每项策略的业务理由。
